1. mesh in one minute

The problem. You run many Claude Code sessions at once, each in its own tmux window. You cycle through the windows to find the one waiting on you. In a team, nobody knows who is working on what, plans live in chat and nothing is recorded about how the work went.

What mesh does.

  • For you: one list of all your sessions, showing which one needs you. You jump to it with one key, send it a message, or let mesh nudge a stalled one.
  • For the team: a shared backlog of goals. Each goal gets a design, someone approves a plan of steps, and people (or their agents) pick steps in parallel or take over someone else's.
  • For analysis: every step leaves a short record in git next to the code. A batch job later reads those records to answer questions like "is this model needing more fix cycles than last month?".
Constraints it is built around: Claude Code CLI only, on subscription logins (no Agent SDK, no API keys). Only seven hooks, all of them optional to the work. TypeScript on Node 24, SQLite through node:sqlite. Sign-in works with no auth, shared tokens or any OIDC provider; Kanidm is one preset. Nothing in mesh assumes one development method: the design → plan → steps flow is data, not an engine.

3. The pieces

Claude Code session

An ordinary claude in a tmux window, on your subscription. mesh doesn't wrap or replace it.

Hooks (7)

SessionStart, UserPromptSubmit, Notification, SessionEnd: fire-and-forget curl to the daemon. Stop: a short HTTP call whose reply can hand the agent a queued message. SubagentStart/SubagentStop: fire-and-forget, to capture each subagent of a programme. They only reach the local daemon, so a dead daemon or a missing hub never blocks Claude.

Daemon mesh up

One per person, on localhost. Knows your sessions and their state, delivers messages, runs autopilot, writes trail files into repos. Its own SQLite file. Runs its own local hub (Solo) when no team hub is configured; with a team hub that is away, the steps you hold keep working.

MCP tools (8)

What agents call: mesh_next, mesh_claim, mesh_context, mesh_note, mesh_ask, mesh_release, mesh_done, mesh_plan. Served by the daemon over stdio.

Hub mesh hub

One per team. Holds goals, plans, steps, claims, messages and the event log. The single writer for shared state. SQLite.

Faces

Terminal: mesh (TUI), mesh show G1. Web: Live page, Goals board, Goal page with the step graph, Design tab to approve, Timeline.

Git repos (the ledger)

.mesh/goals/<G>/: goal.yaml, plan.vN.yaml, steps/<id>.md. Committed by the agent with its work, so they show up in the MR.

Ledger export done

mesh ledger export reads .mesh/goals/** from your checkouts, validates them and writes JSONL, one line per record.

Analysis tool (optional)

Any tool that reads JSONL, for example mesh-ai, or jq. It reads the JSONL in batch and builds whatever views you need: flow, quality, models, people. It is not in the live path.

4. How data flows

There are three lanes. Live (seconds): hooks → daemon → hub → screens. Durable (per step): mesh writes a record into the repo, the agent commits it. Analysis (batch, whenever you like): export reads git, an analysis tool reads the export. The live lane can lose its history after N days; the durable lane never does.

5. A goal from start to finish

This is the flow the real-Claude test pnpm spike e2e-m3 runs, with two people and two repos. Everything here is done unless tagged.

  1. Create. mesh goal new "IPv6 underlay" --repo payments-api --repos payments-web (or the web Goals board). The hub creates goal G1 with one step, G1.design. Event: goal.created.
  2. Design. mesh run --design G1 claims the design step and starts Claude with the other repos added (--add-dir). The agent reads the brief via mesh_context, writes docs/design/g1-….md, and proposes steps with mesh_plan. mesh writes goal.yaml and plan.v1.yaml (decision: pending) into the repo. Events: step.claimed, plan.proposed.
  3. Review the plan. The owner or an approver sees it in mesh show G1 or the web Design tab, with what changed since the last approved version.
    • Ask for changes: mesh goal revise G1 "split out the tests". The comment is delivered into the design session, which proposes v2. Event: plan.revised.
    • Approve: mesh goal approve G1. mesh rewrites plan.v2.yaml with who approved and their comment, the design step closes and steps without dependencies become ready. Events: plan.approved, step.ready. done the design step also gets its own record.
  4. Work in parallel. Anyone runs mesh next or mesh run <repo> --step G1.dplane; agents can call mesh_next/mesh_claim themselves. One holder per step. If someone stops, another can mesh take the step. Autopilot nudge pokes stalled sessions; chain hands the next ready step to an idle session.
  5. Finish a step. The agent calls mesh_done with a summary (and MR, branch). The hub computes the step's facts from its events and returns the record; the daemon writes .mesh/goals/G1/steps/dplane.md; the agent commits it with the code. Dependent steps become ready. A review or test step can reopen an earlier step (fix cycle +1). Events: step.done, step.reopened.
  6. Replan if needed. mesh goal replan G1 "agent needs a migration" reopens the design; a new plan replaces only steps not yet done. Event: goal.replan.
  7. Done. When all steps are done the goal is done. The trail is now in the repos' history, reviewed in the MRs. Event: goal.done.
  8. Analyse later done. Run mesh ledger export over the checkouts; an analysis tool (for example mesh-ai, or jq) reads the JSONL.

6. The development cycle on mesh done

In short: mesh runs the team's existing SDD cycle as a plan template: design → spec → cold spec review → implementation plan and test plan written apart → developer and test-writer working apart → combine → read-only verification against the acceptance criteria → diff review → gate → land.

mesh adds three things the current scripts don't have:

  • Isolation it enforces, so the test side never sees the code side.
  • Caps applied by the hub on rounds and fix cycles.
  • A record per step generated from structured data: verdicts, rounds, failure types, per-criterion results, model and harness. Today these are lost.

The team keeps its own spec, review, plan and evidence files.

Built (M4.5). Run it with the sdd-split template. Commands, what each agent reports and what mesh does with it are in docs/guide/cycle.md; in short:

mesh goal plan G7 --preset sdd-split --repo payments-api --acs acs.yaml
mesh run payments-api --step G7.write-tests     # its own worktree and branch
mesh step approve G7.r2                           # gates; reject --reopen; resume a parked step

Tested against real Claude Code (pnpm spike e2e-m45):

  • The blind guard refused the developer on the test side.
  • Verify failed AC-02 with an impl-bug. mesh reopened the developer's step, and the developer saw "impl-bug AC-02: FIXED marker missing", not the tester's summary.
  • The developer fixed it; verify passed in round 2; a person approved R3.
  • The records hold the verdicts, criteria, bucket and blind separation.

Why: what a typical SDD process loses without it

From studying a team running this kind of cycle with Claude Code workflows over hundreds of specs (design history in docs/analysis/).

The cycle itself works

Cold reviewer, warm on the record (3 rounds, churn breaker). Implementation and test plans written in parallel. Fail-first tests at the pre-change baseline. Read-only executor with failure buckets (spec-gap / impl-bug / test-bug / infra), 3 cycles. Mutations. A gate rule with an advisor.

The data is thrown away

The workflow script gets typed results back from each agent (verdict, blockers, failure buckets) and keeps only prose. Rounds and verdicts end up in file names, in many spellings. Plans are overwritten. Gate lines are free text.

Model per role is unknown

Every commit of a spec comes from one Claude session and one model, covering writer, reviewer, developer and tester. Agent files and commits disagree on which model ran.

Isolation is on trust

The test-planner writes in the tree where the implementation plan is being committed. The test-writer's base holds that plan. Test fixes run in the developer's worktree. The only proof is a self-declared "source read: none".

Retrofit: lessons back into the harness

  1. Every goal ends with a roll-up record: a per-goal retro with no agent and no prose.
  2. Weekly, mesh ledger export feeds a retrofit analysis (an analysis tool such as mesh-ai, or a scheduled agent routine). It compares cohorts by model, harness hash, role and stage: review rounds and churn, reconcile and fail-first misses, verify cycles and bucket mix, ACs met per cycle, time per AC, parks, human help, rework after merge, gate overturns.
  3. Findings become goals that change the harness: agents, skills, CLAUDE.md. The harness hash changes.
  4. The next cohort shows whether the change helped. Keep it or revert it, based on evidence.

7. Works without the hub, and without mesh done

The rule: the process lives in the repo's agents, skills and workflows, and nothing in them calls mesh. Saying "start programme X" works the same with or without mesh. mesh watches and helps: live view, claims, enforcement, the ledger. It is never needed to get the work done.

Two modes:

  • Team: the daemon plus a shared hub.
  • Solo: the daemon runs its own local hub, either because no team hub is configured, or because the team hub is on another network and unreachable.

Your laptop is the writer of record for its own work. The hub is a shared index that can be away for days.

Checked on 2026-11-04 with Claude Code 2.1.318. A workflow programme with mesh's hooks pointing at a dead daemon finished in 10 s, against 9 s with no hooks. Hooks only ever call the local daemon, never the hub. Since M4: a dead hub costs one call (up to 10 s), then mesh tools answer at once from local state. pnpm spike e2e-offline runs a five-agent programme four ways against real Claude Code (no daemon, hub blackholed, hub restored mid-run, Solo): each finished in 11–12 s with records of the same shape, and every agent reached the hub exactly once.

How a programme in one Claude process is captured

A programme runs as one Claude session whose workflow script starts subagents (spec-writer, reviewer, planners, developer, test-writer, test-executor). No subagent reports anything. mesh collects it:

  1. SubagentStart hook: role (agent_type), agent id, start time on mesh's clock.
  2. SubagentStop hook: end time, then the daemon reads Claude Code's own workflow files for that agent:
    • journal.jsonl: label, phase and the typed result, e.g. {"verdict":"APPROVED","blockers":0};
    • agent-<id>.meta.json: the model actually used;
    • workflows/<run>.json: start, duration, attempt.
  3. The label says which step and round it is. Labels follow <role>:<key>[:<round>], e.g. reviewer:ROW-42:r2 or test-executor:ROW-42:c3. The typed result becomes that round's data.
  4. Records wait in <git-common-dir>/mesh/pending/, shared by all worktrees and never in the working tree. The workflow's final ledger commit runs one optional line, mesh ledger stage ROW-42, so they are committed with the closing commit. Without mesh the line is skipped.

The SDD kit that ships with mesh-harness (mesh assets install: agents, the sdd-programme.js workflow and a spec template) already labels every agent and gives each a typed result, and its last step runs the optional mesh ledger stage. Any other workflow that follows the label format is recorded the same way. Nothing in it calls mesh or needs the network. Tested for real with pnpm spike e2e-kit: a toy repo, one Claude session, nine roles recorded with models and typed results, the row ready to land in 3 minutes.

How it is tested

Blackholed-hub tests for the fail-fast link, offline-then-reconnect sync with no duplicates, a complete Solo goal, a conflicting claim made while offline, and parser tests against real Claude Code files. A contract suite catches Claude Code upgrades that change those files. A real-Claude run of a programme four ways must finish every time with the same records: no daemon, hub cut, hub restored mid-run, Solo.

The harness hash done

A fingerprint of everything that shapes how the agent behaves apart from the model: the repo's CLAUDE.md and .claude/**, your ~/.claude CLAUDE.md, agents and skills, plugin names and versions, and the mesh version. One combined hash plus one per part, so you can tell "the model changed" apart from "someone edited a skill". Only hashes are stored, never file contents.

10. Use cases

Developer, daily done

Open mesh: all sessions sorted by "needs you", "stalled", "working", "idle". Enter jumps to the window. s sends a message. Autopilot nudges stalled sessions. No more cycling through tmux.

Starting work done

mesh run repoA repoB opens one Claude window per repo. mesh next shows what is ready for you; mesh run --step G1.x claims and starts it with the brief.

Team lead / owner done

Create goals, let an agent design them, approve or send back the plan from the terminal or web. See the step graph live: who holds what, which session needs someone.

Handoff done

Going home mid-step: release or let it pause. A colleague runs mesh take G1.dplane; the notes and summary come with it, and the record shows both holders.

Reviewer of an MR done

The step record is in the diff: which plan it belongs to, who approved the plan, how many fix cycles, how much human help it needed.

Split build, unbiased testing done

The sdd-split template (section 6): spec, cold review, split plans, developer and test-writer apart, read-only verify per AC, diff review, gates. mesh enforces the separation and the caps.

Programme owner done

Run many backlog rows as goals with the template, unattended. Parks show up in "needs you" with their reason; gates wait in the web. No workflow-script bookkeeping, and no typed results lost.

Harness maintainer done+

Change an agent or skill in your repo or your shared assets; its harness hash changes; compare the next weeks' cohort with the last on rounds, cycles and ACs met. Keep or revert on evidence.

Analyst done

Export the ledger and slice by model, harness hash, effort, repo, step kind, person, week. See section 11.

Quality per acceptance criterion done

Which ACs fail first time, how many rounds until met, which failure class (impl, test, spec) dominates, which steps get reworked later.

Ops done

mesh hub backup, event retention, docs; pnpm test:claude re-checks mesh's assumptions after a Claude Code upgrade.

12. Privacy and what is never stored

  • No prompt text and no agent output are stored. UserPromptSubmit carries the prompt; the daemon keeps only its id and length.
  • Sessions not holding a step never leave your laptop. The hub only hears about sessions that hold a step.
  • No transcripts are read for metrics, and no token usage is collected.
  • The git ledger has plain user names and model names (owner decision 5), matching git authorship. Summaries are written by the agent through mesh_done; everything else is generated.
  • The harness hash stores hashes only, never the content of your CLAUDE.md or skills.
  • Tests and spikes never touch your real ~/.claude: they use scratch config dirs, --settings and --mcp-config.

13. Glossary

GoalA piece of work for the team, e.g. "IPv6 underlay". Has an owner, a design step, plan versions and steps.
PlanA versioned list of steps with dependencies (a DAG), proposed by the design session, approved by a person.
StepOne unit of work in one repo, of a kind (design, implement, test, review, docs). One holder at a time.
Claim / take overBecoming the holder of a step; taking a paused step from someone else.
Fix cycleA step reopened after it was done, usually by a failing test or review.
Segment doneOne continuous stretch of work on a step by one session (one person, one model setting).
Round doneOne mesh_done on a step; a reopened step has several rounds.
Trail / ledgerThe files mesh writes under .mesh/goals/ and the agent commits.
Autopilotoff, nudge (poke stalled sessions), chain (hand the next ready step to an idle session).
Gate doneAn approval step (R1 ADR, R2 spec, R3 landing) done by a person or by a recorded rule.
Reconcile doneThe hub's check that every acceptance criterion appears in the test plan.
Fail-firstA test must fail on the code before the change; otherwise it proves nothing.
BucketThe type of a verify failure: spec-gap, impl-bug, test-bug, infra. It decides which step is reopened.
Template (preset) doneA ready-made plan shape such as sdd-split. The process is data, not engine code.
Blind step doneA step that must not see listed other steps' summaries and branches, nor be done by the same session or person.
