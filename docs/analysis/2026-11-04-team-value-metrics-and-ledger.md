# mesh-harness: team value, regression metrics and the ledger

Date: 2026-11-04. Status: **analysis for discussion**. Author: independent reviewer (critic role).

Inputs: [proposal rev 3.1](2026-11-03-mesh-harness-proposal.md), [journeys](2026-11-03-journeys-dashboard-and-analysis.md), [source analysis](2026-11-03-source-analysis.md), [implementation plan v2.4](../plan/implementation-plan.md), the mesh-harness code at commit `63cf37c` (M3), `dsh-superagent-prototype` (docs 000–008, `src/core`), and `mesh-ai` (workflows, agents, specs 0030/0036/0047/0048, ADR-0020/0021, `apps/gateway/src/{ledger,rework,metrics}`).

Evidence markers: **[code]** means I checked it in source or fixtures. **[doc]** means it is stated in a design doc but I did not check the code. **[inferred]** means my own reasoning or knowledge of Claude Code that still needs a spike.

---

## TL;DR

1. **Today's value is mostly for the individual developer**: one list of sessions sorted by "needs you", jump, nudges and delivery. The team features (claims, take-over, design approval, DAG) work end to end in tests and e2e spikes, but no team has used them for real, and M4's operational parts (backup, retention, docs, Claude contract suite) are missing.
2. **The superagent prototype and mesh-harness share a philosophy** (as little human attention as possible) but differ where it matters: an LLM router admitting work from chat vs a human approving a design and DAG. mesh-harness is right to reject the router. It should still copy **stage-table rigor**, **observe→auto** for auto-pull, and **recording which prompt/harness version each session ran**.
3. **Regression detection is about half possible today.** Fix cycles, turns, human prompts, nudges, waits and holders are captured per step. Missing: reliable model attribution, effort (sent in `Stop` but dropped), the Claude Code version, any harness version, test results, verdicts, acceptance criteria, rework links, and round history (step records are overwritten).
4. **Design rounds are miscounted if read from plan files**: a superseded proposal is saved with `decision: revised` [code]. Count `plan.revised` events instead, or add a `superseded` decision.
5. **The split-planner / blind-tester lifecycle can be drawn as a mesh DAG today, but it is not protected.** `mesh_context` hands the tester the developer's summary, branch and notes, and autopilot `chain` can hand the tester step to the session that just wrote the code [code]. Both have to change before "blind" means anything.
6. **Ledger vs stream:** mesh-harness already has the right hybrid in shape (hub events plus generated step records). It lacks a schema version, provenance fields, round history, a reader, and a rule for what goes where. The main lesson from mesh-ai: **ledger fields must be generated by code from tool arguments and events, never hand-written and parsed back** (spec 0030's verdict-header heuristics, REQ-ORM-30's `model:` regexes).
7. **Recommended rule:** if an analysis must still work after the hub database is gone, a summary of it goes in the git ledger. The stream holds high-frequency, timing, live-only and abandoned-work facts, with retention.
8. **MUST for M4 (about 1.5–2 weeks):** a `mesh.ledger.v1` schema on all trail files, per-segment provenance (model, effort, permission mode, Claude Code version, harness hash, repo commit), round history, a fix for the design-round count, and `mesh ledger export` to JSONL.
9. **SHOULD (about 2–3 weeks, M4.5):** verdict and check fields on `mesh_done`, failure class on reopen, optional `role` / `acs` / `reworks` / `blind` on plan steps, blind-step guards, a step stage table, and plan presets. All are optional data, with no new engine concepts.
10. Do this **now**: no real records are committed in product repos yet, so changing the schema costs nothing today and will cost a migration later.

### 1.2 Who benefits, and how much

- **Individual developers running 3–8 sessions** benefit most and first (M1, no hub needed). The gain is real but unmeasured: the "week of daily use" that M1a's exit asks for is not recorded as done. Comparing `waits.minutes` and nudge counts with and without `nudge` would quantify it with data mesh already collects.
- **Approvers and leads** get one place to approve, if approvals actually move out of chat.
- **Teammates sharing a goal** get claims, take-over and context. This is the least proven part: `test/m3-flow.test.ts` and `pnpm spike e2e-m3` are a demo (two users, two repos, revise, approve, done), not use.

### 1.3 Missing for real team use

| Gap | Why it matters | Where it is planned |
|---|---|---|
| Hub backup, event retention, operations docs | One SQLite file holds the team's state; the event table grows without bound | M4 4.2, 4.4 |

## 2. mesh-harness vs the DeepSeek superagent prototype

### 2.1 Comparison table

| Axis | dsh-superagent-prototype | mesh-harness (M3) | Assessment |
|---|---|---|---|
| Core principle | "Take as little human attention as possible" (`docs/000`) | The same, adopted explicitly (proposal §8) | Agree |
| Where work comes from | Sources (GitHub, Feishu) → Trigger → Thread → Eval → Ticket | A person creates a goal (`mesh goal new`); later, a GitLab import | Different scope: the prototype is an intake system, mesh is a work-coordination system |
| Who decides that work starts | Deterministic gate + LLM assessment (`observe` / `auto` accept modes) | A human approves a design and its DAG; that is the only gate | mesh is right for multi-repo feature work, where the expensive mistake is the design, not the admission |
| Authority record | Immutable **Mandate**: policy version, scope, strength, matched rules | Approved `plan` (version, `decided.by`, `decided.at`); each step has `planVersion` | Equivalent in spirit; mesh doesn't put the approval in the step record yet |
| Unit of work | Ticket (no DAG) + Assignments | Step in a DAG, with kind, repo and deps; claims | mesh is richer for coordination |
| Attention model | Ordered **stage table** per Ticket: `person/delivery`, `person/answer`, `person/review`, `person/blocked\|failed`, `working/queued`, `idle`, `working` (`src/core/stage.ts`) | Ordered state table **per session** (§3.3 of the plan) plus a per-viewer attention list (`attentionFor`: approval, question, failed, paused, stalled, needs_you) | mesh has the rigor at session level but not at step level (§2.2) |
| Proactivity | `observe` records "would accept"; `auto` acts | None. Auto-pull is a later add-on. | Copy observe→auto when auto-pull lands |
| Runtime | Owns the DSH runtime: inputs injected at the next step, long commands moved to the background, exactly-once input redelivery, "read" tracking | Does not own the runtime: hooks, `agents --json`, tmux paste, Stop `additionalContext` | mesh can only know a message was *delivered*, never that it was *read*. This is the price of Claude Code CLI on subscriptions. |
| Isolation | One directory per Ticket through a `prepare` command (usually `git worktree add`) | Sessions run in the developer's checkouts | The prototype is better here; see §4 |
| Side effects | Durable `Effects` queue written in the transaction; Outbox receipts | Hub `message` table (pull + ack) and a daemon `outbox` spool for observations | mesh already has the needed subset |
| Prompt/config versioning | Every save is an immutable version; "the host records the revisions each Session used" (`docs/004`); `policyVersion` is a hash | None recorded | **Gap that matters for §3** |
| Scale | One repo, one bot identity, one operator | Many repos, many people, Kanidm identities | mesh is broader by design |
| Metrics | None | Step facts, plus mesh-ai as the analysis plane | Neither has trend analysis yet |

### 2.2 What mesh-harness should still adopt

1. **Stage-table rigor at step level (SHOULD, S).** The prototype's panel rules (`docs/005`) are: categories are mutually exclusive and cover every case, a count equals the length of the list it links to, and a label says whom a row waits for. mesh computes step display state ad hoc in `attentionFor` and in the web. Example: a claimed step whose holder session ended less than 2 minutes ago is neither paused nor stalled. Add one pure `stepStage(step, holderSession, now)` with an ordered table, for example:
   - `person/approval`
   - `person/answer`
   - `person/permission`
   - `person/failed`
   - `person/stalled` (escalated)
   - `person/delivery` (a message failed: `message.delivered` with `state: failed` is not surfaced today [code])
   - `working`, `idle`, `paused`, `ready`, `blocked`, `done`

   Use it in the TUI, the web and attention.
2. **Observe→auto for auto-pull (COULD, S, with add-on 4).** When idle sessions may claim ready steps from any goal, start by emitting `step.would_claim` and showing it, then switch to `auto` per user.
3. **Version recording (MUST, as part of §6 R2).** The prototype records which prompt revision each session ran. mesh should record a harness hash per session segment.
4. **Mandate-like provenance in the record (MUST, trivial).** Put `plan: {version, approved_by, approved_at}` in each step record, so a record says on whose authority the work was done.

### 2.3 What mesh-harness rightly rejects

- **Router LLM and Eval.** Every admission would cost subscription quota and latency, and would need its own evals. With an approved DAG, admission is deterministic.
- **Triggers/Threads/Subscriptions from chat.** Out of scope until chat or GitLab intake is a stated need; even then, a deterministic issue → goal import comes first.
- **A general effects framework.** The hub outbox and daemon spool cover today's side effects. When GitLab writes arrive (M5), one small durable table is enough.
- **Owning the runtime.** Not possible on the Claude Code CLI without the SDK, which the subscription constraint rules out.

## 3. Detecting a model, prompt or harness getting worse

### 3.1 What exists today

The **hub `event` table** (`src/store/hub-store.ts`) has the columns `seq, id, at, type, user_id, sid, goal, step, payload`. Daemons sync `session.*` and `message.delivered` events **only for sessions holding a step** (`daemon.observe`, privacy rule Q5). Those synced events carry `step` but not `goal`, so goal queries use `step LIKE 'G17.%'`. The **step record** front matter (`core/trail.ts stepRecord`, golden snapshot `src/core/__snapshots__/trail.test.ts.snap`) has these fields:

- `goal`, `step`, `kind`, `repo`, `plan`
- `holders[]`, `sessions[]`, `models[]`
- `turns`, `human_prompts`, `nudges`, `waits{count, minutes}`, `fix_cycles`, `outcome`
- `mr`, `branch`, `started`, `finished`

Plan files carry `proposed{by, at}`, `decision` and `decided{by, at, comment}`.

### 3.2 Signal by signal

| Signal | Captured? | Where exactly | How to compute | What is missing |
|---|---|---|---|---|
| **Fix cycles** | Yes | `step.fixCycles` (hub `step.value`); record `fix_cycles`; event `step.reopened` payload `{by, reason, fixCycles}`; event `step.failed` payload `{summary, mr, reopen}` | Sum `fix_cycles` over implement steps per model | **Attribution**: the cycle is charged to the reopened step, but `models[]` is an unordered set over all sessions and rounds. **No failure class** (mesh-ai has `impl-bug / test-bug / spec-gap / infra / unclassified`, `TeamFixBucket`). A reopened `tests` step (a test bug) and a reopened `develop` step look the same. |
| **Verifier rounds** (how often a test/review step failed) | Only in events | Count of `step.failed` events per step | `SELECT step, COUNT(*) FROM event WHERE type='step.failed' GROUP BY step` | **Not in the record**: each `mesh_done` rewrites `steps/<id>.md`, so only the last round survives in HEAD; earlier ones only in git history |
| **Time per step** | Partly | Record `started` (first claim) / `finished`; events `step.claimed`, `step.done` | `finished − started` | Wall time includes nights and waits. **Active time** could come from `session.turn_started` / `session.turn_stopped` pairs, but it is not computed. **No size normaliser**: no acceptance-criteria count, no diff size. |
| **Time per AC / per spec** | No | — | — | ACs don't exist as data. mesh-ai had `ItemTime.acs` and `ac_time` medians. |
| **Design / review rounds** | Partly, with a trap | Plan files; events `plan.proposed`, `plan.revised`, `plan.approved` | Count `plan.revised` **events** (emitted only on a human revise) | `proposePlan` marks a superseded pending plan `decision: "revised", comment: "superseded"` with no `decidedBy` [code], so counting `plan.v*.yaml` files with `revised` overcounts. Review steps have only `done/fail`: no verdict scale, no findings count. MR review rounds are not captured (planned for the mesh-ai ingest). |
| **Test failures** | No | — | — | `mesh_done` has no test fields; CI isn't read. mesh-ai removed its `test-run` hook (spec 0024 → 0050) and uses Prometheus CI ingest. |
| **Human prompts** | Yes | Record `human_prompts`; event `session.turn_started{delivered}` | Per step / per model | Heuristic: `delivered = humanPrompts unchanged` between session snapshots (`daemon.ts:200`). Prompts in the session *before* the claim are not counted. A person working in a second, step-less session is invisible. |
| **Nudges / stalls / escalations** | Partly | Record `nudges`; events `session.nudged{n}`, `session.stalled`, `session.escalated` | — | Stalls and escalations are not in the record. |
| **Waits for a person** | Yes | Record `waits{count, minutes}`; event `session.waiting{needs}` | Minutes from `session.waiting` to the next `turn_started` | A wait that ends with the session ending isn't counted. `needs` (permission vs question) isn't split in the record. **Permission waits depend on `permission_mode`, which isn't recorded** (it is in the Stop and UserPromptSubmit payloads [code: fixture]). |
| **Questions** | Events only | `question.asked`, `question.answered` (with step) | Count per step, answer latency | Not in the record. |
| **Rework after merge** | No | — | — | `reworks:` was promised in the journeys doc §3.3, but `PlanStep` has no such field [code]. There is no post-merge link. |
| **Model per step** | Unreliable | `Session.model` from `SessionStart.model`, copied into `session.turn_started.payload.model` | Set in `models[]` | `SessionStart` sends `model` only sometimes (spike S2; the `background.SessionStart.resume` fixture has none [code]). A `/model` switch mid-session is not observed. |
| **Effort** | No | Present in `Stop` input as `effort: {level: "medium"}` [code: fixture] | — | `toHookEvent` drops it (`protocol/hooks.ts`) |
| **Claude Code version** | No | `claude/version.ts` reads it, for `mesh doctor` only | — | Not stored per session |
| **Harness / prompt version** | No | — | — | Nothing hashes the repo's `CLAUDE.md`, `.claude/**`, the user's `~/.claude/CLAUDE.md`, or mesh's own brief/nudge text |
| **Tokens / cost** | No | — | — | Deferred (`later.md`: OTel opt-in) |

**Two attribution problems** need an explicit rule. First, when two sessions or models touch a step (take-over, `/clear` with a model change, a human finishing the work), the facts are summed and the model is a set. Second, a fix cycle's cause (the implementation) and its detection (the tester) are in different steps.

Proposed rule: facts are kept **per segment** (one per `sid` holding the step), and a step's "primary model" is the model with the most turns. The analysis can also choose "last segment before done".

### 3.3 Minimal additions for trend analysis per model and harness

1. **Per-segment provenance (MUST).** The daemon adds `effort`, `permission_mode`, `claude_code` (version, cached from `claude --version`), `harness` (hash) and `repo_commit` (HEAD at claim) to `session.turn_started` payloads. The record gets `segments[]`.
   - **Harness hash:** SHA-256 over the repo's `CLAUDE.md` and `.claude/{agents,skills,commands,workflows,settings.json}`, the user's `~/.claude/CLAUDE.md`, and the mesh version. This is the same idea as mesh-ai's `harnessHash` (`packages/meshctl/src/ops/harness.ts`), which hashes `CLAUDE.md` and `.claude/{agents,workflows,commands}` plus model and effort.
   - The repo-side files can be rebuilt from `repo_commit`. User-level files can't (they are not in git), so the hash only identifies them.
2. **Round history (MUST).** Add `rounds[]` to the record: `{n, outcome, at, reopened_by?, class?}`.
3. **Verdict, failure class and checks on `mesh_done` (SHOULD).** All optional:
   - `verdict` (`pass|fail` for test; `approve|revise|reject` for review);
   - `findings{blocking, non_blocking}`;
   - `reopen: [{step, class}]`;
   - `checks: [{name, passed, failed, skipped}]`, marked `source: agent`. CI from GitLab stays the authority when it arrives.
4. **Size normaliser (SHOULD).** Optional plan-level `acs[]` with per-step references and per-AC outcomes. Diff stats (lines and files changed on the step's branch) are computed in batch from git, not stored.
5. **`reworks:` (SHOULD)** on goals and plan steps.
6. **Model gap (spike first).** Check whether the transcript JSONL carries a per-message model and usage [inferred]. If it does, the daemon can read **only those numeric fields locally**, which also gives token counts without sending content. Otherwise accept "model from SessionStart, else unknown", and say so in the analysis.

With these, "is model X or harness H worse?" becomes group-bys over JSONL rows keyed by (model, effort, harness hash, Claude Code version, role, repo): fix cycles per implement step, verifier rounds, human prompts and nudges per step, active minutes per AC, first-round check failures, and rework rate. Treat this as *trend detection, not proof*: samples per group are few and step size and repo confound them. Replay evals (mesh-ai spec 0036) remain the controlled test.

## 4. Opinionated lifecycle vs a generic DAG

### 4.1 The pattern (as mesh-ai runs it)

`workflow-build-feature.md` and `build-rows.js` follow the same sequence:

1. A spec with ACs and an "Interface Contracts" section is approved.
2. **impl-planner** and **test-planner** run in parallel. The test planner is told "Do NOT read any implementation source files".
3. **developer** (in an isolated worktree) and **test-writer** (fail-first, blind) run in parallel.
4. A join into **tester**, which "does not see developer's session" and classifies each failure as `impl-bug | test-bug | spec-gap | infra`, each routed to a different loop-back.
5. **reviewer** (cold), with at most 3 rounds.
6. A gate.

### 4.2 Benefits and costs

| Benefits | Costs |
|---|---|
| **Bias separation**: tests derived from the contract and ACs, not from the code, catch "the test checks what the code does" | More steps, more sessions and more seats (each lane is a Claude session on someone's subscription) |
| **Parallelism**: planning and test writing overlap with implementation | A contract has to exist and be good. A bad contract makes two lanes wrong in parallel. |
| **Contract-first**: forces the interface decision early, where a human can approve it | Integration work (merging two branches, fixing build glue) lands on the tester |
| **Measurable gates**: each node has a verdict, so failure classes and first-try pass rates become data | Overkill for small changes. mesh-ai's own lesson was "process mass" (specs of 600–1,300 lines, GATE-1 rounds). |
| Blind verification makes model comparisons fairer (a model can't grade its own homework) | "Blind" is only advisory without tool-level enforcement, which mesh deliberately doesn't have |

### 4.3 What mesh-harness can express today, and what it cannot

**Can do today [code]:**

- steps with `kind ∈ {implement, test, review, docs}` and arbitrary deps, so fork, parallel lanes and join work;
- `repo` per step;
- a failing tester reopens either `develop` or `tests` (`reopen` takes any done step in the goal);
- spec-gap loops go to a human through `mesh goal replan`;
- `mesh run --step` per lane, so each lane gets its own session.

**Cannot do:**

| Missing | Effect | Concrete evidence |
|---|---|---|
| **Roles** | No way to say "this step is for a test-planner"; metrics can only group by `kind`. There is no `plan` kind, so planner steps must be `docs` and pollute the docs metrics. | `StepKind` enum [code] |
| **Blindness** | **`mesh_context` gives every step its deps' `summary`, `branch` and `mr`, and the step's notes** (`daemon/tools.ts brief()`). A tester depending on `develop` reads the developer's own account of the code. | [code] |
| **Session separation** | **Autopilot `chain` picks "the first ready direct dependent in the same repo"** (`core/claims.ts pickNext`), so the developer's session can chain straight into `run-tests` | [code] |
| Contract artefact | No field naming the contract file that blind steps may read | — |
| ACs | No first-class ACs, so no per-AC outcome or time | — |
| Verdicts | `outcome: done/fail` only; no `revise`, no findings | — |
| Workspace isolation | Two lanes in the same repo share a checkout; `mesh run` creates no worktree | [code] `cli/mesh-commands.ts` |

### 4.4 Example plan preset in mesh-harness terms

Fields marked `#+` are **proposed** (optional, ignored by the engine except for the blind guards). Everything else is valid `mesh_plan` input today.

```yaml
# .mesh/presets/split-build.yaml, offered to the design session as a template, not an engine feature
goal: G21
design_ref: frr-dplane-ovs@design/g21:docs/design/g21-bfd-offload.md
acs:                                                   #+ plan-level, optional
  - {id: AC-1, text: "BFD sessions are offloaded when the NIC reports support"}
  - {id: AC-2, text: "Offload failure falls back to software BFD within 1 s"}
  - {id: AC-3, text: "Offload counters appear on the existing metrics endpoint"}
steps:
  - id: contract
    repo: frr-dplane-ovs
    kind: implement
    role: contract-author                              #+
    produces: {contract: include/bfd_offload.h}        #+ the only impl artefact blind steps may see
    title: Interface and compiling stubs
    brief: Write bfd_offload.h and stubs from the design. No behaviour. Push branch mesh/g21-contract.
  - id: impl-plan
    repo: frr-dplane-ovs
    kind: docs
    role: impl-planner                                 #+
    deps: [contract]
    title: Implementation plan
    brief: Plan the change AC by AC in docs/plans/g21-impl.md. No code.
  - id: test-plan
    repo: frr-dplane-ovs
    kind: docs
    role: test-planner                                 #+
    deps: [contract]
    blind: [impl-plan]                                 #+
    title: Test plan from contract and ACs
    brief: Plan blackbox tests per AC in docs/plans/g21-tests.md, through the public interface only.
  - id: develop
    repo: frr-dplane-ovs
    kind: implement
    role: developer                                    #+
    deps: [impl-plan]
    acs: [AC-1, AC-2, AC-3]                            #+
    title: Implement
    brief: Implement on branch mesh/g21-develop (own worktree).
  - id: tests
    repo: frr-dplane-ovs
    kind: test
    role: test-writer                                  #+
    deps: [test-plan]
    blind: [impl-plan, develop]                        #+
    acs: [AC-1, AC-2, AC-3]                            #+
    title: Write failing tests
    brief: Write tests on branch mesh/g21-tests against the stubs; they must fail before develop lands.
  - id: run-tests
    repo: frr-dplane-ovs
    kind: test
    role: tester                                       #+
    deps: [develop, tests]
    blind: [impl-plan, develop]                        #+ may merge develop's branch, not read its notes
    title: Merge and run
    brief: Merge mesh/g21-develop and mesh/g21-tests into mesh/g21-verify, run the suite, classify each failure.
  - id: review
    repo: frr-dplane-ovs
    kind: review
    role: reviewer                                     #+
    deps: [run-tests]
    title: Cold review
    brief: Review the merged diff against the design and ACs. Verdict approve / revise / reject.
```

**Proposed semantics of `blind: [ids]`:**

- `mesh_context` omits summaries, notes and questions of the listed steps, and keeps their branch names only when they are deps;
- `mesh_claim` refuses a session (`sid`) that held any listed step;
- `chain` never assigns such a step to that session;
- the record gets `blind: {to: [...], separated: true|false}`, computed from segment overlap.

It cannot stop an agent from running `git log -p`. That stays a prompt rule, and the record makes a violation auditable rather than impossible.

### 4.5 What each node should leave behind

| Node | Ledger fields (beyond segments and rounds) |
|---|---|
| contract | `produces.contract` path, `acs` touched |
| impl-plan / test-plan | `ref` to the plan doc; AC coverage list (`acs: {AC-1: planned}`) |
| develop | `acs` outcome (self-claimed), `checks` run locally, `fix_cycles`, `rounds[].class` from reopeners |
| tests | `acs: {AC-n: written}`, `checks` showing the tests fail first (`failed > 0` before develop) |
| run-tests | `verdict`, `checks{passed, failed, skipped}`, per-AC `pass/fail`, `reopen[{step, class}]`, `blind.separated` |

## 5. Streaming telemetry vs telemetry in the work objects

### 5.1 The two approaches

- **(a) Streaming.** Events go to a central service as they happen. mesh-ai went through three generations (instruction emits; hooks plus heartbeat daemon and reapers; `meshctl work start/done` self-report) into a gateway on Kafka, later JetStream. mesh-harness's hub `event` table is a much smaller version: deterministic hooks and RPCs, spooled with UUIDs, pulled by `GET /v1/events?after=` (the route already exists [code], `hub/app.ts`).
- **(b) Ledger.** Metadata travels inside the work objects in git, and a batch process reads it. mesh-ai parsed `Gate:` lines, review `Verdict:` headers, `progress/*.md` and `.id-ledger.tsv` into `ledger.*` events (spec 0047, ADR-0021 A4), and the ledger wins when it disagrees with `work.*` (REQ-ORM-31).

### 5.2 Comparison

| Property | Streaming (hub events) | Ledger in git |
|---|---|---|
| Robustness | Depends on the hub and the daemon spool. Data is lost if the hub DB is lost (no backup yet). | Survives any tool; but depends on the agent committing and the MR merging (abandoned MR → lost) |
| Privacy | Central and fine-grained, but restricted (service token, admins). mesh already limits it to step-holding sessions. | Visible to everyone with repo access, forever. User names and model choices become public in the repo. |
| Decoupling tooling from data | Schema tied to the producer's event vocabulary | **Strong.** Any future tool (a mesh-ai programme, a Claude workflow, a different orchestrator) can write the same record; readers depend on files, not APIs |
| Cost / weight | Low per event, but infra and retention to run | One small file per step in each MR; some review noise; almost no merge conflicts (one file per step) |
| Latency | Seconds | Hours to days (after merge plus batch) |
| Tamper-evidence / reviewability | Append-only table, but invisible to reviewers | Reviewed in the MR and kept in history. **Not tamper-proof:** the agent writes and commits its own record. |
| What only it can see | Waiting time as it happens, stalls, nudges, deliveries, presence, abandoned or never-finished steps, pending approvals | The final, reviewed state of the work: what shipped, under which plan, with which verdict |
| Failure mode seen in mesh-ai | Hooks observing agents it didn't own → churn; Kafka → JetStream churn | **Hand-written ledgers → heuristic parsers.** Spec 0030 had to accept a `Verdict` label "in any decoration among the first 30 lines" and `verdict: null`; `ledger/model.ts` regex-hunts `model:` |

### 5.3 Recommended hybrid and the rule

**Rule 1: what goes where.** A fact belongs in the **ledger** if it describes the work product and an analysis must still work when the hub database is gone:

- identity and plan provenance;
- outcome, verdicts and rounds;
- ACs;
- check summaries;
- links (MR, reworks);
- per-segment provenance and *summarised* timings.

A fact belongs **only in the stream** if any of these hold:

- it is high-frequency (turns, state transitions);
- it is time-precise (wait intervals);
- it is live-only (presence, pending approvals);
- it is about work that produced no commit (abandoned steps, sessions that never finished);
- it is private to a person (sessions without a step never leave the machine).

**Rule 2: no hand-written ledger fields.** Every ledger field is generated by mesh code from tool arguments and stream events, and has a schema. Agents never type `Verdict:` lines; they pass `verdict` to `mesh_done`.

**Rule 3: the stream is the source; the ledger is the summary.** Records are computed from events at each `mesh_done`. The batch reader joins records with the event export when available, and trusts the record when the event log has been pruned.

**Rule 4: retention.** Keep hub events for N days (e.g. 180) with backup. After that, only the ledger and aggregate exports remain.

### 5.4 Where mesh-harness stands against that

| Recommendation | Status |
|---|---|
| Stream for timings and live facts | ✅ hub `event` table, daemon spool, `/v1/events` |
| Generated (not hand-written) records | ✅ `stepRecord`, `planFile`, `goalFile` generated in `core/trail.ts` |
| Schema id/version on records | ❌ none (events have the `mesh.harness.v1` envelope only in the plan doc) |
| Provenance in records | ⚠️ `models[]` only, often empty |
| Round history | ❌ records are overwritten |
| Reader / export | ❌ mesh-ai is expected to parse markdown front matter itself (plan task 4.5) |
| Retention and backup | ❌ M4 4.2 |
| Commit guarantee | ⚠️ advisory; the hub can always regenerate (`GET /v1/goals/:id/files`, step facts from events), but there is no check that the record reached the default branch |
