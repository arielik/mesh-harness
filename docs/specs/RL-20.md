# Spec RL-20: Read-only preset check

## Status
Approved after review round 2 (`reviews/RL-20/r2-approved.md`). Revision 3 applies its
suggestions (the `bad topic` placeholder, sink checks without changing the steps, a shared warnings
function, the shape of the sink-topic presets of AC-02/AC-03). Revision 2 answered round 1 (`reviews/RL-20/r1-changes-requested.md`): every 400 of a sink
topic is a problem (B1), AC-01's chain is a valid relay (B2), and the non-blocking findings N1–N9.

Source: a request from a dashboard client that composes multi-agent presets (steps joined by `deps`,
each with a repo agent or a roster key) in a form and writes them as a preset file for a person to
commit. Builds on RL-3 (pulses, preset snapshots, `presetChecks`), RL-5 (roster keys and pins),
RL-8 (invalid-agent warnings), RL-9 (sink topics), RL-11 (`/healthz` features), RL-12 (read routes
for service tokens without on-behalf) and RL-19 (preset `kind`). Release `0.1.39`.

## Problem

1. **The only way to ask "would the hub take this preset?" is to write.** `POST /v1/pulses` runs
   the preset checks (`presetChecks` in `src/hub/service.ts`: sha256, `params.repo`, `kind`,
   `parsePreset`, `instantiate`, `validatePlan`, `validatePolicies`, exactly one first step, profiles,
   roster pins, sink topics), but only on the way to creating a pulse, which is stored, pinned,
   evented and scheduled. A client that wants to tell a person, before they commit a preset file,
   whether the hub accepts it with the params they chose has no read for it.
2. **A stored pulse does not show its plan.** `GET /v1/pulses/:id` returns the snapshot text and the
   params; a client that wants the steps parses YAML and substitutes params itself.

## Scope

In:
- `POST /v1/presets/check`: the preset checks of `POST /v1/pulses` on `{preset, params}`, writing
  nothing, answering `{ok, problems, warnings, steps?, agents?}`.
- `steps` in `GET /v1/pulses/:id` (`PulseDetail`): the stored snapshot's plan, instantiated as the
  check does (additive, computed from stored fields only; see *Open questions* 1 for why it is in).
- A new `/healthz` feature name: `preset-check`.

Out:
- Anything about cost: the reply has no cost or budget estimate.
- The checks of `POST /v1/pulses` that are not about the preset or its params: `when` (schedule,
  cron, time zone), `window`, `maxGoalAge`, `overlap`, `missed`, `topics` (the pulse's labels),
  `title` and `target` (with the on-behalf rule that a person's pulse names their own machines). The
  check's body has none of these fields.
- A CLI command (`mesh pulse add` already reports the same problems as a 422 from the create).
- Checking a preset against one stored pulse (`existing` pins of `POST /v1/pulses/:id/update`): the
  check pins as a create does.
- Any write: no pulse, slot, goal, pin, event, idempotency record or other row.

## Interface contracts

### `POST /v1/presets/check`

- Rule `member`; service scope `goals:read` (a read, though a `POST`: a preset text of up to 20 000
  characters does not fit a query string). Not wrapped for a person: a service token that sends
  `x-mesh-on-behalf-of` gets 400 `on-behalf-of is not accepted on this route` (as RL-12's reads);
  a service checks with its own token. A service token without `goals:read` → 403 `forbidden`; no
  token → 401 `login required`.
- OpenAPI tag `analysis`: every route under it computes a view and writes nothing, which is what a
  client reads the tag for; the pulse routes under `goals` all write except the two `GET`s. The
  summary says it is a read that writes nothing. The route is marked `read` in `HUB_API` (new
  optional field `read?: true`), and the OpenAPI document leaves the idempotency-key header out for
  it.
- **Writes nothing.** The hub runs it in one store transaction that only reads, emits no event, and
  **ignores the `Idempotency-Key` header** (no `idem` row is stored and no earlier answer replayed:
  each call answers from the hub's state now). The app's route table gets the same `read` flag. The
  only write a request may cause is authentication's own: like every authenticated request, a token
  last used more than a minute ago gets its `lastUsed` refreshed (`src/auth/tokens.ts`); that is not
  the route's write and is the same for any read.
- A web session (cookie) calling it is a cookie `POST`, so it must come from the hub's own origin
  (else 403 `cross-origin request refused`), as for every cookie `POST`. A bearer token is not
  affected.
- The OpenAPI document's general description changes from "POST routes accept an idempotency key
  header" to "POST routes that write accept an idempotency key header".

**Body** (`PresetCheck`, strict JSON object; `src/protocol/pulse.ts`):

| Field | Type | Meaning |
|---|---|---|
| `preset` | `PresetSnapshot` | `{name, text, sha256, source?}` exactly as `PulseCreate.preset`: `name` `^[A-Za-z0-9][A-Za-z0-9._-]{0,59}$`, `text` 1–20 000 characters, `sha256` 64 lowercase hex, `source` `{repo, commit}` optional and not used by the check |
| `params` | `PulseParams` | as `PulseCreate.params`: at most 20 keys `^[a-z][a-z0-9_]{0,39}$`, values ≤ 300 characters |
| `checkedAgents` | string[] ≤ 50, each 1–100 chars, optional | as `PulseCreate.checkedAgents` (RL-8): repo agents the caller checked itself; left out of `warnings` |

Body errors (the shared handler, same texts as every route):
- Not JSON → 400 `{error: "invalid JSON body"}`. An empty body is `{}` and fails the schema.
- Schema failure (missing `preset` or `params`, a field out of range, an unknown field such as
  `when` or `target`) → 400 `{error: "invalid request", details: ["<path>: <message>", …]}`.
- `preset.sha256` not the SHA-256 (hex) of the UTF-8 bytes of `preset.text` → 400 `{error:
  "preset.sha256 is not the SHA-256 of preset.text"}`, as `POST /v1/pulses` (the hub's rule: the
  snapshot is the text as sent, byte for byte, and the hash is checked before anything else). No
  other check runs.

There is no other body limit: the hub sets none beyond these field limits.

**Reply** 200 `PresetCheckResult` (`src/protocol/pulse.ts`), for a body that passed the checks above:

| Field | Type | Meaning |
|---|---|---|
| `ok` | boolean | `problems` is empty, so `POST /v1/pulses` with this `preset` and `params` (and valid other fields) passes the preset checks against the hub's state now |
| `problems` | string[] | what makes the create refuse, in the order below (`[]` when `ok`) |
| `warnings` | string[] | RL-8's warnings for this plan (computed as `pulseWarnings` computes them for a create by the same caller, from the pins that resolved: a roster key that does not resolve gives no warning): one line per step whose agent the roster flags invalid (`step "<id>": roster agent <key> has invalid front matter: <reason>` for a pinned roster key, `step "<id>": agent <name> in <repo> has invalid front matter: <reason>` for a repo agent the caller can see in the step's repo, except `checkedAgents`). They never make `ok` false. The repo copies are those the caller sees (`GET /v1/agents`): a service token sees only copies of machines shared with everyone, so it may get fewer repo-agent warnings than a person's create. Present (possibly `[]`) whether `ok` or not; a preset that does not instantiate gives `[]` |
| `steps` | `PlanStep[]` | only when `ok`: the plan as `POST /v1/pulses` checks it and a slot's goal gets it: `instantiate(parsePreset(name, text), {repo: params.repo, goal: "this goal", params})`, with sink topics as stored (trimmed, lowercased topic names). Placeholders are filled from the preset's own `params:` defaults, overridden by the body's `params`, then `repo` = `params.repo` and `goal` = `this goal` (a param named `goal` is overridden, as at create and fire); `{goal}` is the literal `this goal` (a slot's goal substitutes its own id, which does not exist yet). Step ids are local (`run`, not `G12.run`) |
| `agents` | `Record<string, AgentDef>` | only when `ok`: the roster keys of the plan's steps pinned exactly as `pinAgents` pins them on create: key = the step's `agent` (else `policy.agent`) as written after substitution (e.g. `agents/rev` or `agents/rev@1a2b3c4`), value `{key, source, name, hash, commit}` of the catalog definition it resolves to now. Repo agents (no `/`) are not pinned (a run reads them from its worktree), so they are not in `agents`; they appear only as `steps[].agent`. `{}` when no step uses a roster key |

The check runs the preset checks with the RL-19 `kind` check on (`kind: true`), as create and
ingest do (a preset sent in the request must have a valid kind).

**Problems, and their equivalence with `POST /v1/pulses`.** Pulse create (with the same `preset` and
`params` and otherwise valid fields) refuses for preset or params reasons in two ways, and the check
reports both as problems with the same text:

1. **422** `{error: "the preset has N problem(s): …", details: [...]}` from `presetChecks`. The
   check's `problems` starts with exactly `details`, in the same order:
   - `params.repo is required (the repo the preset's steps work in)`;
   - an invalid preset `kind` (RL-19 `presetKindProblem`);
   - `preset <name>: <parse error>` when `parsePreset` fails (YAML, schema, unknown keys) — then the
     list ends here;
   - an `instantiate` error (an unknown `{param}` in `agent`/`profile`/budget, a budget out of range,
     both prefixed `preset <name>:`, or a plan-shape error of the substituted steps without a prefix)
     — then the list ends here;
   - `validatePlan` (no steps, more than 50 steps, a reserved or repeated id, a dep on itself, an
     unknown dep, a cycle) and `validatePolicies` (RL-2/RL-4/RL-9/RL-15 policy rules);
   - `a pulse preset needs exactly one first step (no deps, not a gate); <name> has <n>`;
   - `step "<id>": unknown profile "<name>"` per unknown profile;
   - `step "<id>": <roster error>` per step whose roster key does not resolve (`agent key must be
     <source>/<name>[@<7-64 hex>]`, `no catalog source matches …`, `no agent … in catalog source …`,
     `no definition of … matches @…`, `@… matches n definitions …`).
2. **400** from `sinkTopic` for the first step whose `sink.topic` is refused, checked by create only
   when (1) found nothing: `bad topic "<topic>": <rule>` (`<topic>` is the topic after substitution, trimming and lowercasing, not the text as written) when the (trimmed, lowercased) name is not a
   valid topic name (e.g. `ci/nightly`; the plan schema allows any 1–40 characters), else `unknown
   topic <t> (define with: mesh topic add <name>)` when it is `all` or not a defined topic. The check
   instead checks every step's sink topic whenever the preset instantiated, and appends one problem
   per distinct refusal text, in step order, with that exact text (any 400 of `sinkTopic`, not only
   these two), after the problems of (1). Each `sinkTopic` call is wrapped on its own, so a refusal
   neither stops the check nor changes the steps; create, update and ingest keep stopping at the
   first refusal (`checkSinkTopics` unchanged).

So: create answers 422 ⇒ check gives `ok: false` and `problems` begins with the 422's `details`;
create answers 400 for a sink topic (either text) ⇒ check gives `ok: false` and `problems` contains that `error`;
check gives `ok: true` ⇒ create passes the preset checks (and the hub state is unchanged between
the two calls). The implementation shares the code: `presetChecks` is split into a function that
collects these problems (used by the check) and the existing throwing wrapper (create, update,
ingest), so the two cannot drift. `pulseWarnings` takes `{preset, params, agents}` instead of a
`Pulse`, so create, update and the check share it.

**Checks against state.** The check runs against the hub's state now, like create: profiles
(built-in or registered), catalog sources and definitions (roster keys), topics (sinks), and, for
`warnings`, the roster's agent copies the caller can see. The things create checks against the
caller or the machines are not in the body and not checked: `target` (machines the person owns,
on-behalf only) and the owner. `params` are opaque strings substituted into the preset text; the
hub does not resolve any param to a machine, a person or a repo, at create or here, so a param that
names a machine is just text. `params.repo` must be present; whether a machine has that repo is
decided at each slot (`no_machine`), not at create.

**Not idempotent across state changes.** A later call may answer differently: a roster key whose
catalog moved pins another hash, a profile or topic added or removed changes `problems`.

### `steps` in `GET /v1/pulses/:id`

`PulseDetail` gains `steps?: PlanStep[]`: `instantiate(parsePreset(pulse.preset.name,
pulse.preset.text), {repo: pulse.params.repo, goal: "this goal", params: pulse.params}).steps`,
computed from the stored snapshot at the read (no profile, roster or topic lookup; the pins are in
`pulse.agents`). Absent when the stored snapshot no longer parses or instantiates (it parsed when it
was saved; a later hub could refuse it). A slot's goal gets this plan with `{goal}` replaced by its
own id. Nothing else in the reply changes.

### Types (src/protocol/pulse.ts, exported from src/protocol/index.ts)

- `PresetCheck` (zod, strict): `{preset: PresetSnapshot, params: PulseParams, checkedAgents?: string[]}`.
- `PresetCheckResult` (zod): `{ok: boolean, problems: string[], warnings: string[], steps?: PlanStep[],

- `PulseDetail.steps?: PlanStep[]`.
- `HubApiRoute.read?: true` (`src/protocol/hub-api.ts`).
- `HUB_FEATURES` gains `preset-check` (sorted).

### Compatibility

- No migration (schema stays 12). No daemon or CLI change.
- Additive: one route, one optional reply field on `GET /v1/pulses/:id`, one feature name, one
  optional field in the API registry. An older hub answers the route with a plain-text 404 (the web
  fallback serves `GET` only); a client checks `features` for `preset-check` first.
- `POST /v1/pulses`, `/update` and `/v1/goals/from-preset` keep their statuses, messages and order
  of checks.

## Open questions

1. **`steps` in `PulseDetail`: in.** It is a pure function of the stored snapshot and params (no
   state, no write, no new store read), a few lines, additive, and it gives a stored pulse the same
   `steps` shape the check gives a draft, which is what the client asked for (one rendering for both).
   Left out would mean every client re-implements YAML parsing and param substitution.
2. Should a later release accept the other `PulseCreate` fields (`when`, `topics`, `target`) and
   check them too? Not now: they are not about the preset, and `target` depends on the person a
   service acts for, which this read does not take.
