# Spec RL-10: Findings name their repo (clean-audit steps land where the fix is)

## Status
Draft (approved after review round 3: its one blocker, AC-03's text, fixed; round-3 suggestions applied)

Source: operating v0.1.27. Builds on RL-2 (review records, items, fold), RL-4 (dispositions,
revert), RL-9 (clean-audit goals, finding steps, sink, item → step sync, `mesh items sink`).
Release v0.1.28.

## Problem

RL-9 puts each filed finding in the clean-audit goal of `(lineage repo, topic)`, and the finding
step's `repo` is the lineage repo: the repo the audit **ran in**. An auditor that checks other
repos (a CI auditor run from one repo that reads the pipelines of five others) therefore puts every
finding in its own repo's goal. The steps then start in the wrong checkout (`mesh run <repo> --step`
needs the step's repo), and the per-repo view ("clean the CI of repo X") misses them: findings about
repo X from the shared auditor sit in the auditor's goal, findings about repo X from X's own auditor
sit in X's goal.

An item has no field for the repo it is about. Some auditors write the repo in `key.path` by
convention, but `key.path` is a file path for every other auditor, so the hub cannot read it.

## Scope

In:
- An optional **`repo`** on a review item: the repo the finding is about. Stored on the item row.
  Not part of the fingerprint.
- The item's **target repo** decides its clean-audit goal and its finding step's `repo`, in the
  sink, the backfill and the item → step sync.
- A finding step whose item's target repo changed is **moved** to the clean-audit goal of the new
  target (by the fold that changed it, by a sink, or by `mesh items retarget`).
- **`mesh items retarget`**: set the target repo of existing items (one by one, or from
  `key.path`) and move their open finding steps.
- `mesh items` shows the target repo when it is not the lineage repo.

Out:
- Where the filer files its tracking row (unchanged: the filer's own repo and rules).
- Merging findings of different lineages about the same problem (two lineages, two steps, as RL-9).
- Checking that a target repo is in any machine's inventory (a step whose repo no machine has is
  never offered, as any step today; `mesh show` shows its repo).

## Interface contracts

Names used below (RL-9 names unchanged unless redefined here).
- **Target repo** of an item row: `row.repo` when set, else the lineage repo. Repos compare as
  exact strings, as RL-9.
- **Clean-audit goal** of `(repo, topic)`: as RL-9.
- **Finding-step id**: as RL-9 (`f-` + 16 characters of the hash of `<lineage>|<fp>`), so the id
  does not depend on the repo and a moved step keeps its local id.
- **Moved-away step**: a finding step with `movedTo` set (below). **Live finding step** of
  `(lineage, fp)`: a step with that `finding`, without `movedTo`, in a clean-audit goal that is not
  `dropped`. Every lookup of this spec and of RL-9 (rules 2–5, the item → step sync, the backfill,
  the retarget, the `requires` resolution, the `mesh show` counts) sees live finding steps only.
- **Open** step: state `ready` or `blocked`. **Held**: `claimed`, `paused`, `parked`, or `failed`.
  **Closed**: `done`, `skipped` or `dropped`.
- **Home goal** of an item and a topic: the clean-audit goal of `(target repo, topic)`. **Home
  step**: the step with id `<home goal>.f-<hash(lineage|fp)>`, whatever its state, moved-away or not.
  **Foreign step**: a live finding step of `(lineage, fp)` in another clean-audit goal of the same
  topic that is not closed.
- **Requires of an item**: the union of `requires` over all its `accepted` dispositions (any goal).
  Used by moves; the sink keeps RL-9's "in the sink stage's goal".

### Recording the repo (fold, src/hub/service.ts `submitReview`)

**Same fingerprint, two repos.** Today (RL-2) a record listing one fingerprint twice keeps the first
item and ignores the rest. RL-10 keeps that, except: two items of one record with the same
fingerprint and different `repo` (absent counts as the lineage repo) → the record is refused with
422 `item <fp> is listed for more than one repo (<r1>, <r2>, …); put the repo in its key`, the
repos distinct, in record order, as one entry of RL-2's record problems message. So an auditor that checks
several repos keeps the repo inside its keys (`path` or `symbol`); the guide says so.

**Row.** When a raising record is folded, for each item in it: with `repo`, the row's `repo` is set
to it; without, the row's `repo` is left as it is (so a repo set by `retarget` survives a record
from an auditor that does not send `repo`).

**Fold move.** When the fold changes an item's target repo (the row's target before and after
differ), the event `item.retargeted { lineage, fp, from, to, by }` is emitted (`by`, and the event
`user`: the record's submitter), and each live finding step of `(lineage, fp)` that is not closed and
whose goal's `sink.repo` is not the new target is handled as retarget step 3 (below): an open step is
moved, a held one gets the note. This runs in the record's transaction, after the item rows are
saved and before the RL-9 resolved sync of the same fold.

### Placing the home step (one rule for every path that opens a finding step)

Every path that would create, reopen or revive a finding step (sink rules 2 and 3, a move, the RL-9
revert reopen, a backfill) acts **only on the home step**, after this check:

- **Foreign step first.** If the item has a foreign step for the topic: open → it is moved (below)
  and the move is what opens the home step; held → nothing opens, and the held step gets the note
  `filed for repo <target repo>; move it with: mesh items retarget <lineage> <fp> --repo <target repo>`
  (once per call).
- **Then the home step**, by what exists:
  - none → created (RL-9 rule 2, `repo` the target repo);
  - moved-away → **revived**: `movedTo`, `summary`, `outcome`, holder fields and `roundStartedAt`
    cleared, `repo` the target repo, title, severity and brief rebuilt from the item, deps as RL-9
    rule 5 (a move: step 4 below), notes and rounds kept, `fixCycles` unchanged; event
    `step.reopened { by, reason, from }` (reason below);
  - live and closed → reopened as RL-9 rule 3 (event reason `refiled`), or for a move always (event
    reason `moved`, `fixCycles` + 1);
  - live and open or held → unchanged by the move or sink beyond RL-9 rule 4.

For a sink or backfill (not a move), a create, revive or reopen happens only when the item's latest
`accepted` is newer than the last close of **every** finding step of `(lineage, fp)` for the topic
(home or foreign, moved-away steps included; RL-9's "filed after close" test with its event-order
tie-break, applied to each; with no finding step yet, a create always happens): a sink or backfill
never revives, reopens or re-creates work a person finished elsewhere unless the item was filed
again after that.

Fields of an opened home step: `severity` and `title` from the item (RL-9 rule 2's title), the
brief rebuilt from the item; a created step's `fixCycles` is the moved step's on a move, else 0.
Event reasons: `step.reopened` reason `refiled` for a sink's reopen or revive, `moved` for a move's.

So a `(lineage, fp)` has at most one live finding step that is not closed per topic: only the home
step is ever opened, and only after any open foreign step was closed by a move. The RL-9 item → step
sync closes steps (`done`, `dropped`) in every goal; closing never breaks this.

### Moving a finding step

Move of a foreign step `S` (in clean-audit goal `A`, topic `t`, open) to target repo `n`:
1. `B` = the home goal (the clean-audit goal of `(n, t)`), created by RL-9 rule 1 if none (title
   `Clean audits: <t> on <repo name of n>`, owner `A`'s owner). If topic `t` is no longer defined, the
   move is skipped: `S` gets the note `move to <n> skipped: topic <t> is not defined` and nothing
   else changes.
2. The home step in `B` is opened as above (created, revived or reopened) and gets the note `moved from <S id>`
   (or `moved back from <S id>` when revived). Notes, rounds and history of `S` stay on `S`.
3. `S` becomes `dropped`, `movedTo` the new id, summary `moved to <new id>`; offers withdrawn;
   event `step.dropped { reason: "moved", to: <new id>, by }`. Its dependants in `A` are settled
   (RL-9: a dropped dep unblocks) and each gets the note `dep <S id> moved to <new id>`.
4. The home step's deps: the requires of the item resolved in `B` by RL-9 rule 5 (with its
   notes, e.g. `requires <fp>: not in this goal`); state `ready` or `blocked` by those deps.
5. `B` gets one `goal.sunk { from }` listing the moved steps under `added` (`from`: the sink step id,
   the fold's audit step id, or `mesh items retarget`).
6. `A` is left as it is, even with no open step (a person may `mesh goal drop` it).

Events of a move carry `user`: the caller (retarget), else `A`'s owner. A move may put a step in a
goal owned by someone else than the caller (the goal of the target repo already exists); that is
allowed, as a sink may.

### Sink (RL-9 rules, changed)

The sink groups the items filed in the goal by **target repo** and applies RL-9 rules 1–5 to each
group against the clean-audit goal of `(target repo, topic)`. All groups are decided in memory
first, then written, in the caller's transaction (RL-9: no rule fails half-way; a sink reason never
fails the caller). One `goal.sunk` per clean-audit goal that got added, moved or reopened steps.

- **Rule 1** (goal): unchanged, with the target repo in place of the lineage repo.
- **Rules 2–4** run through "Placing the home step": the foreign-step check first (an open foreign
  step is moved, and rules 3–5 do not run again on the home step in this sink; a held one stops the
  item with the note), then rule 2 (create, `repo` the target repo), a revive, rule 3 (reopen if
  filed after close) or rule 4 on the home step.
- **Rule 5** (deps): unchanged (within the step's own goal; an fp whose live step is in another goal
  gets `requires <fp>: not in this goal`).

### Item → step sync (RL-9 table, changed lookup)

The RL-9 table's closing rows (`resolved` → `done`, `dismissed`/`deferred` → `dropped`, the
revert of an `accepted` → `dropped`) and its notes apply to the live finding steps of
`(lineage, fp)` in **every** clean-audit goal (not only the lineage repo's). The row that reopens
(revert of the debrief disposition that dropped the step) reopens only the **home step** of the
topic of the goal whose step that disposition dropped, and only when it is live and `dropped`: as
RL-9 (event reason `reverted`, deps unchanged), after the foreign-step check (a held foreign step
stops it with the note). With no home step, or a moved-away one, nothing is reopened (the next sink
places the item). A dropped step in another goal stays dropped. Moved-away steps are never matched.

### Backfill: `mesh items sink` (changed)

As RL-9, grouped by target repo as the sink is (placing included; no deps). Permission: an admin,
the owner of the lineage's newest goal, or the owner of an existing clean-audit goal of the topic
whose repo is the lineage repo or a target repo of the lineage's filed items. With no entry in
`goals` (no filed item selected), `goal` is RL-9's (the lineage repo's clean-audit goal or null).
CLI output: with zero or one entry, exactly RL-9's line (`<G>: added <n>, reopened <m>`; dry run
`would add <n> to <G or a new goal>`); with two or more, one such line per entry followed by
` (<repo name>)`.

### Retarget: `mesh items retarget` (`POST /v1/items/retarget`)

`mesh items retarget <lineage> (<fp>… | --all) (--repo <r> | --from-key-path) [--dry-run]` →
`POST /v1/items/retarget` (rule `member`, scope `goals:write`, tag `goals`). Permission: an admin,
the owner of the lineage's newest goal, or the owner of a clean-audit goal that holds a live finding
step of the lineage; else 403. 404 `no items in <lineage>` when the lineage has no item; 404
`unknown item <fp> in <lineage>` for a listed fp it does not have. Nothing is written on a refused
call.

For each selected item (all items of the lineage with `--all`, in any state):
1. The new target: `repo` (trimmed), or with `from_key_path` the item's `path`. Under
   `from_key_path` an item is left out with a note when it has no `path` (`<fp>: no key path`) or its
   path does not look like a repo name: it contains `/` or ends in `.` and 1–5 letters or digits
   (`<fp>: key path <path> is not a repo name`). A repo with a group (`group/x`) is therefore
   reached only with `--repo`.
2. If the new target differs from the current target, `row.repo` is set to it; the item is listed in
   `items` (`from`, `to`) and gets the event `item.retargeted { lineage, fp, from, to, by }`. No item
   history entry is written (the history and RL-4 revert are unchanged).
3. Each live finding step of `(lineage, fp)` that is not closed and whose goal's `sink.repo` is not
   the new target (a foreign step of its topic for the new target):
   - open → moved (above) to the goal of `(new target, that goal's topic)`; listed in `moved`;
   - held → unchanged; the note `retarget to <repo>: release the step, then run the retarget again`;
     listed in `held`.
   Step 3 also runs for an item whose target did not change (so a retarget run again after a
   release moves the step).

All decided in memory, then written in one transaction. `dry_run` writes nothing and returns the
same result, except that a step in a goal still to be created is named `new:<repo>/<local id>`.

CLI output: `retargeted <n> items; moved <m> steps; held <h>`, then one line per move
`<from> → <to>`, per held step `held: <id>`, and per note `note: <text>`. With `--dry-run` the first
line starts `would retarget`. Usage errors (no lineage; neither or both of `<fp>…`/`--all`; neither
or both of `--repo`/`--from-key-path`) exit 2 with the usage on stderr and send nothing, as
`mesh items sink`.

### `mesh items` (CLI)

An item whose row has `repo` different from the lineage repo prints its path column as
`<path or -> → <repo>`. `--json` rows carry `repo` when set.

### Docs, events, schemas

Concepts (the target repo of a finding; moves), scheduled-reviews guide "Clean-audit goals"
(auditors that check other repos set `repo` on each item and keep the repo in the key; the fold
moves open steps when an auditor starts sending `repo`; retarget for items not raised again; dry-run
first), the mesh skill (`mesh_review` items may carry `repo`), `docs/events.md` (`item.retargeted`;
`step.dropped` reason `moved` with `to`; `step.reopened` reason `moved`), the API table (`/v1/items/retarget`). `pnpm schemas`
regenerates the OpenAPI document and the ledger schemas.

### Compatibility

New optional fields, one new route, no migration (`ItemRow` and steps are stored as JSON;
`SCHEMA_VERSION` stays 11). An item with `repo` is refused by an older hub (400) and by an older
daemon's `mesh_review` tool schema, so the hub ships first, then the daemons of the machines that run
the auditor, then the auditors add `repo`. Items without `repo` behave exactly as in RL-9.
