# Spec RL-22: Team attention, a service decides for a person, open questions, park by hand

## Status

`reviews/B-249/r1-spec.md`): act-for runs with the member role only (B1), the team form returns every
kind and field of mesh-ai ADR-0025 D24.1 (B2), park takes `claimed` and `paused` steps only (M1), the
codes are bounded to §Codes (M2), and the minor findings 5 to 12.

Source: an external request (mesh-ai row B-249, the hub parts of its AI-ops action items AIOPS-3,
AIOPS-5a and AIOPS-17; mesh-ai `docs/analysis/2026-11-26-ai-ops-usability-analysis.md` §8.1, §8.3,

**admin** role is honoured through act-for on the fleet pause routes only, which are not part of

## Problem

1. **A service cannot decide for a person.** `POST /v1/goals/:id/{approve,revise,replan}`,
   `POST /v1/steps/:id/{approve,reject,resume}`, `POST /v1/questions/:id/answer` and
   `POST /v1/messages` are `member` routes with no `scope` (src/protocol/hub-api.ts:269-272,
   387-389, 493-494), so `allowed()` (src/core/roles.ts:53) refuses a service token with
   `403 forbidden`. A dashboard that holds a service token can only show a command to copy.
2. **Goal create and drop by a service act as the service.** `POST /v1/goals`,
   `POST /v1/goals/from-preset` and `POST /v1/goals/:id/drop` take `goals:write` but no
   `X-Mesh-On-Behalf-Of`: a goal created by the dashboard is owned by the service account, and a
   drop is checked against the service account.
3. **No team view of attention.** `GET /v1/attention` (src/hub/app.ts:216) answers only for the
   caller (`attentionFor`, service.ts:3388) and has no scope. A dashboard that wants every open item
   (plans, gates, debriefs, questions, parked with reason, failed, paused, stuck, pulse health, the
   ready queue) for the whole team makes 2 + G + D hub reads per interval today (G open goals, D open
   debriefs) and still lacks questions asked through `mesh_ask`.
4. **No list of open questions.** Questions are written (`POST /v1/questions`) and answered, but no
   route lists them.
5. **No one can park a step by hand.** A step is parked only by a rule (round cap, churn, stall,
   reconcile; service.ts:3052). A person who wants work on a step to stop until someone looks has
   no hub action; release and take do not stop the holder.

## Scope

In:
- Three new service scopes: `goals:decide`, `questions:answer`, `sessions:message`.
- Act-for (`X-Mesh-On-Behalf-Of`) on the decision routes, the answer route, the message route,
  goal drop and both goal-create routes (§Routes). Act-for keeps today's rule: the request runs with
  the person's `member` role only (ADR-0025 D23.2), so through a service only the goal owner passes
  `canApprove`; an approver or admin who does not own the goal decides with their own login.
- `GET /v1/attention?team=1`: every open attention item of the team in one read, for a service
  token with `goals:read` or an admin.
- `GET /v1/questions?state=open`.
- `POST /v1/steps/:id/park` with a reason, and the CLI command `mesh step park` (the hand-off a
  client shows when it cannot relay).
- A stable `code` beside the unchanged `error` text on each refusal that §Codes lists. Every other
  refusal of these routes (body-schema `400`s, the goal-create refusals, `approvePlan`'s `422` roster
  problems, `say`'s `400` and `404` on a `to` it cannot resolve) stays code-less in this release.
- `via` (the service user id) in the payload of every event a request made under act-for emits.
- `/healthz` features `decide-for`, `team-attention`, `questions-list`, `step-park`.

Out:
- Fleet pause and resume, and act-for with the admin role (mesh-ai row B-250).
- Act-for with the person's `approver` role (MESH-OQ-AIOPS-14, §Open questions).
- Stopping a headless run or an interactive session; offers to a teammate's machine and their
  consent (mesh-ai row B-252). A park touches no process (§Park).
- Act-for on debrief dispositions (`/v1/steps/:id/dispositions*`), the debrief pre-read
  (`/v1/steps/:id/read`), claim, release, take, done, accept, decline, withdraw and goal assign:
  they keep refusing a service token as today.
- Any change to the personal form of `GET /v1/attention` or to the `Attention` type.
- Options on questions (the hub's `Question` has none; the team form's `hub-question` therefore
  carries no `options`), a question state other than `open`.
- A migration: no new table or column (schema stays 12).

## Requirements

- **REQ-DECIDEFOR-1** A service token MUST be refused (`403 forbidden`) on every route of §Routes
  unless the token carries that route's scope.
- **REQ-DECIDEFOR-2** A request of a service token on a route of §Routes whose header column says
  "required" MUST carry `X-Mesh-On-Behalf-Of`, else the hub MUST answer `400`
  `on-behalf-of-required` and change nothing.
- **REQ-DECIDEFOR-3** A request made under act-for MUST run with the person's `member` role only;
  it MUST NOT run with the person's `approver` or `admin` role on any route of this spec.
- **REQ-DECIDEFOR-4** Every event a request made under act-for emits MUST carry `user` = the person
  and `payload.via` = the service user id; an event of a request not made under act-for MUST NOT
  carry `payload.via`.
- **REQ-DECIDEFOR-5** The rights check of each route (§Routes, "hub check kept") MUST be evaluated
  against the person, never against the service account.
- **REQ-TEAMATT-1** `GET /v1/attention?team=1` MUST return, in one response, one item per open item
  of each of the sixteen kinds of §Team attention, with the fields §Team attention gives each kind,
  and the `users` list. An item bound to a goal MUST be returned only when that goal is not `done`
  or `dropped` and, unless `trial=include`, not a trial goal; a `hub-question` item MUST be returned
  whatever its goal's state, and with no goal when the question names no step.
- **REQ-TEAMATT-2** The personal form (`GET /v1/attention` without `team`) MUST return exactly what
  it returns in 0.1.41 for every caller that could call it in 0.1.41.
- **REQ-QLIST-1** `GET /v1/questions?state=open` MUST return every unanswered question the caller
  may see (§Open questions), oldest first.
- **REQ-PARK-1** `POST /v1/steps/:id/park` MUST move a `claimed` or `paused` step that is not a
  gate or a debrief to `parked`, with `parkedReason = "operator: <reason>"`, and MUST emit
  one `step.parked` event; it MUST NOT signal, kill or message any process other than queueing one
  inbox message to the holder session.
- **REQ-COMPAT-1** The `error` text of every refusal that 0.1.41 returns MUST NOT change; `code` is
  added beside it on the refusals of §Codes only.

## Interface contracts

### Scopes (src/protocol/hub-api.ts)

`SERVICE_SCOPES` gains, appended after `steps:assign`: `"goals:decide"`, `"questions:answer"`,
`"sessions:message"`.

Why three new scopes and not `goals:write`: `goals:write` today lets a service create goals owned
by the service account and tag them; it decides nothing for a person. Granting decisions through it
would silently give every existing goal-creating service token the power to approve plans and pass
gates in people's names. One scope per kind of write is the existing pattern (`pulses:write`,
`profiles:write`, `steps:assign`). Answering a question and writing into a person's live session
are different reaches from deciding a goal, so each has its own scope. An existing token MUST be
re-minted to gain them (`mesh hub token --service <name> --scope …`); that is deliberate.

### Routes

| Route | rule | scope | act-for | header for a service | hub check kept (against the person, as a member) |
|---|---|---|---|---|---|
| `POST /v1/goals/:id/approve` | member | `goals:decide` | yes | required | `canApprove`; a pending plan |
| `POST /v1/goals/:id/revise` | member | `goals:decide` | yes | required | `canApprove`; a pending plan |
| `POST /v1/goals/:id/replan` | member | `goals:decide` | yes | required | owner, approver or admin (today's check); goal not `done`/`dropped` |
| `POST /v1/steps/:id/approve` | member | `goals:decide` | yes | required | `canApprove`; a gate; `ready` |
| `POST /v1/steps/:id/reject` | member | `goals:decide` | yes | required | `canApprove`; a gate; `ready`; `reopen` names done steps |
| `POST /v1/steps/:id/resume` | member | `goals:decide` | yes | required | `canApprove`; `parked` or `failed` |
| `POST /v1/steps/:id/park` (new) | member | `goals:decide` | yes | required | `canApprove`; `claimed` or `paused` (§Park) |
| `POST /v1/questions/:id/answer` | member | `questions:answer` | yes | required | addressed to the person (`toUsers`); the admin override does not apply under act-for |
| `POST /v1/messages` | member | `sessions:message` | yes | required | the target session is visible to the person (MM-1 rule, unchanged) |
| `POST /v1/goals/:id/drop` | member | `goals:write` (exists) | yes | **optional** | `canApprove`; no held step |
| `POST /v1/goals` | member | `goals:write` (exists) | yes | **optional** | the owner is the person when the header is sent |
| `POST /v1/goals/from-preset` | member | `goals:write` (exists) | yes | **optional** | the owner is the person when the header is sent |
| `GET /v1/attention` (`team=1`) | member | `goals:read` | no | refused | §Team attention |
| `GET /v1/questions` (new) | member | `goals:read` | no | refused | §Open questions |

Under act-for the person is evaluated as a member (`actingFor` returns `roles: ["member"]`, unchanged),
so `canApprove` holds only for the goal owner and the answer check only for an addressed person. This
is ADR-0025 D23.1 and D23.2 ("the hub honours the person's member role only"). Acting for someone
grants less, never more.

"Optional" keeps today's behaviour for a service that sends no header on goal create and drop: the
goal is created by and owned by the service account, and a drop is checked against the service
account (it may drop the goals it owns). This differs from the analysis (§8.3 asked for the header
to be required on drop) because requiring it would break a service that drops its own goals today.
On goal create the header is OPTIONAL as ADR-0025 D23.3 requires of this row.

"Refused" means a service or a member sending `X-Mesh-On-Behalf-Of` on that read gets
`400 on-behalf-of-not-accepted` (today's `actingFor` rule for a route without `onBehalfOf`).

`HubRoute` (src/protocol/hub-api.ts) and the app's `Route` (src/hub/app.ts) gain
`onBehalfOfOptional?: true` — a write that does not require the header for a service; `app.ts`
passes `write: (route.method === "POST" && route.onBehalfOfOptional !== true) || route.onBehalfOfRequired === true`
to `actingFor`. `actingFor` itself is not changed.

The OpenAPI generator documents `X-Mesh-On-Behalf-Of` on each act-for route and says whether it is
required for a service. `node scripts/schemas.ts` regenerates `schemas/hub-api.openapi.json`.

### Act-for (unchanged mechanism)

As v0.1.29 and RL-21: a service token (role `service` without `member`) with the route's scope sends
`X-Mesh-On-Behalf-Of: <user id>`; the hub looks the id up exactly; a missing user or a service
account → `403 user-unknown`; the request runs as `{ userId: <person>, roles, via: <service> }`
with no `machineId`; a member's own token sending the header → `403 on-behalf-of-not-service`.
Idempotency keys are per `<service>><person>` (unchanged). A person who holds `approver` or `admin`
but does not own the goal is refused `403 not-approver` through a service, where their own token
would succeed (§Routes).

### Attribution (every act-for route)

- Events: `user` = the person; `payload.via` = the service user id (the existing `viaOf(actor)`
  helper, service.ts:349). Affected events: `plan.approved`, `plan.revised`, `goal.replan`,
  `gate.approved`, `gate.rejected`, `step.reopened`, `step.resumed`, `step.parked`,
  `question.answered`, `message.sent`, `goal.dropped`, `goal.created`; plus `plan.approved` from
  `from-preset`. Events that follow on their own (`step.ready`, `step.skipped`, offer events) are
  unchanged and carry no `via`.
- Stored records: `plan.decidedBy`, a gate round's `gate.by`, `question.answeredBy`, the resume
  note's user, `goal.ownerId` on create = the person. The resume note text and the gate round gain
  nothing; the event carries `via`.
- Messages to sessions (`plan_revised`, `answer`, `say`, `taken_over`, `parked`): `fromUser` = the
  person; `data.via` = the service. The text of `answer`, `plan_revised` and `parked` messages ends
  with ` (via <service>)` under act-for, so the session can tell a relayed decision; the text of a
  `say` message is the person's words and is not changed.

### Team attention: `GET /v1/attention?team=1`

Route entry: `{ method: "GET", path: "/v1/attention", rule: "member", scope: "goals:read", query:
{ team, needsYouMs, turns, trial, limit } }`. A service token with `goals:read` gains the route.

| Caller | no `team` | `team=1` |
|---|---|---|
| member (not admin), own token | personal form (today) | `403 team-forbidden` |
| admin, own token | personal form (today) | team form |
| service with `goals:read` | `400 team-required` | team form |
| service without `goals:read` | `403 forbidden` (today) | `403 forbidden` |

`team` accepts only `1` (`400 bad-query` otherwise). `needsYouMs` and `turns` take the ranges and
defaults of `GET /v1/stuck` (1800000 and 40, the client's agreed stuck thresholds) and the same
refusal texts, now with `code: "bad-query"`. `trial`: `exclude` (default) or `include`. `limit`:
1–5000, default 2000.

Response (`TeamAttention`, src/protocol/hub.ts, zod). The kind names and fields are those of ADR-0025
D24.1:

```
200 {
  generatedAt: number,                      // hub clock, ms
  thresholds: { needsYouMs: number, turns: number },
  truncated: boolean,                       // more items than `limit`; the oldest `limit` are returned
  users: string[],                          // every hub user id that is not a service account, sorted
  items: TeamAttentionItem[]                // oldest `at` first; ties by `key`
}
TeamAttentionItem {
  key: string,              // stable across reads: `<kind>:<goal|pulse|->:<step|slot|->:<question|sid|->`
  kind: "plan" | "gate" | "debrief" | "debrief-overdue" | "hub-question" | "parked" | "failed"
      | "paused" | "stalled" | "stuck-step" | "stuck-session" | "needs-you-session"
      | "slot-missed" | "pulse-blocked" | "ready-unclaimed" | "offer",
  goal: string | null,      // always present
  step: string | null,      // always present
  repo: string | null,      // always present: the step's `repo`, else the goal's `primaryRepo`, else null
  who: string | null,       // always present: the one hub user id the item waits on (table), or null
  at: number,               // when the item started waiting (table)
  text: string,             // one line, the same wording style as the personal form
  // extra fields, present only on the kinds the table names:
  goalTitle?: string, stepTitle?: string,
  planVersion?: number,                          // plan
  question?: number, toUsers?: string[],         // hub-question (no `options`: the hub has none)
  sid?: string, machine?: string, needs?: string,
  holder?: string,
  reason?: string,                               // parked: `parkedReason`; failed: the step `summary`; slot-missed: the slot reason
  sla?: { dueAt: number, breached: true, escalated: boolean },   // debrief-overdue (RL-15)
  escalatedTo?: string,                          // debrief-overdue once escalated
  turns?: number,                                // stuck-step
  forMs?: number,                                // stuck-session
  pulse?: string, slot?: string,                 // slot-missed, pulse-blocked
  stepKind?: string, mode?: string,              // ready-unclaimed (`mode` absent when the policy has none)
  targetMachine?: string                         // offer
}
```

Which items. "Open goal" means a goal that is not `done` or `dropped` and, unless `trial=include`, not
a trial goal; every goal-bound kind is over open goals only.

| kind | Open while | `who` | `at` | Extra fields |
|---|---|---|---|---|
| `plan` | goal `awaiting_approval` with a pending plan | goal owner | the plan's `proposedAt`, else goal `updatedAt` | `planVersion` (the pending plan's `version`) |
| `gate` | gate step `ready` | goal owner | step `updatedAt` | — |
| `debrief` | debrief step (`policy.mode` `debrief`) `ready` and not read in its current round (no `read`, or `read.round` ≠ rounds + 1) | `debriefAssignee` | `cycleReadyAt ?? readyAt` (stage times), else step `updatedAt` | — |
| `debrief-overdue` | a debrief past its SLA (the `overdueDebriefs` rule of RL-15; trial goals never count) | `debriefAssignee` | `sla.dueAt` | `sla`, `escalatedTo` |
| `hub-question` | question with no answer, any goal state; a question without a step has `goal`, `step` and `repo` null | `toUsers[0]` (the asking session's user, first by `ask`) | question `at` | `question`, `sid`, `toUsers` |
| `parked` | step `parked` | goal owner | `parkedAt`, else `updatedAt` | `reason` |
| `failed` | step `failed` | goal owner | step `updatedAt` | `reason` |
| `paused` | step `paused` | `holderUser` | `pausedAt`, else `updatedAt` | `holder` |
| `stalled` | `claimed` step whose holder session is `stalled` | `holderUser` | the session's `lastStopAt ?? lastEventAt` | `sid` |
| `stuck-step` | a step of the `GET /v1/stuck` step rule at the given `turns` | `holderUser`, else goal owner | the start of the turn that reached the floor (below) | `turns`, `holder` |
| `stuck-session` | a session of the `GET /v1/stuck` session rule at the given `needsYouMs` | session user | `stateSince` (the `/v1/stuck` `since`) | `sid`, `machine`, `forMs` |
| `needs-you-session` | a live session in `needs_you`, with or without a step | session user | `stateSince`, else `lastStopAt ?? lastEventAt` | `sid`, `machine`, `needs` |
| `slot-missed` | an enabled, not deleted pulse whose newest slot (the `lastSlot` rule of `GET /v1/health`, trial slots per `trial`) is `missed` | pulse owner | the slot's `at` | `pulse`, `slot`, `reason` |
| `pulse-blocked` | an enabled, not deleted pulse with a `blockedBy` (the `GET /v1/health` rule); `goal` and `step` name the blocking ones | pulse owner | the blocking goal's `createdAt` | `pulse` |
| `ready-unclaimed` | step `ready`, not a gate, not a debrief, no holder, no offer in state `offered` | null | `cycleReadyAt ?? readyAt`, else step `updatedAt` | `stepKind`, `mode` |
| `offer` | step `ready` with an offer in state `offered` | the target machine's owner | the offer's `at` | `targetMachine` |

**The turn that reached the floor.** For a `stuck-step` the hub takes the `session.turn_started`
events of the step that `turnsSinceCommit` counts (those after the last round with a commit), in `at`
order, and uses the `at` of the `turns`-th of them (1-based, `turns` the floor of this read). The
shared stuck function returns it beside `turns` as `reachedAt`; `GET /v1/stuck`'s answer is not
changed. A step that has just crossed the floor is therefore as old as the turn that crossed it, not
as old as its last commit (ADR-0025 D24.1).

The stuck rows are computed by the same function as `GET /v1/stuck`, so the two reads agree on which
sessions and steps are stuck and on their `turns` and `since` at the same thresholds. `who` names the
one person the item waits on; approvers and admins MAY also decide plans, gates, resumes and parks
with their own login (docs say so). `users` lists every hub user that is not a service account (the
`live()` filter: not `service` without `member`), whatever their items; it is the "known hub users"
list of ADR-0025 D24.1 and mesh-ai local ADR-0042. The team form shows sessions of every machine (a
service already reads them through `/v1/stuck` and `/v1/live`), which is why a member without admin
may not call it. The answer is computed in one store transaction and is not cached.

The personal form, its kinds (`approval`, `offer`, `needs_you`, …) and the `Attention` type are not
changed (REQ-TEAMATT-2). The personal kind `offer_expired` has no team kind: an expired offer leaves
the step `ready` with no open offer, which is a `ready-unclaimed` item (ADR-0025 D24.1).

### Open questions: `GET /v1/questions?state=open`

Route entry: `{ method: "GET", path: "/v1/questions", rule: "member", scope: "goals:read", query:
{ state, limit } }`. `state` is REQUIRED and accepts only `open` (else `400 bad-query`); `limit`
1–5000, default 2000.

| Caller | Questions listed |
|---|---|
| service with `goals:read`, admin | every unanswered question |
| member | unanswered questions whose `toUsers` include the caller |

Response:

```
200 { truncated: boolean, questions: OpenQuestion[] }     // oldest `at` first, ties by id
OpenQuestion { id: number, goal?: string, step?: string, repo?: string, sid?: string,
               fromUser: string, toUsers: string[], text: string, at: number }
```

`goal` and `repo` come from the question's step when it has one. Source: `store.openQuestions()`
(src/store/hub-store.ts:1482), unchanged.

### Park: `POST /v1/steps/:id/park`

Body `StepPark = z.object({ reason: z.string().trim().min(1).max(500) }).strict()`.
Rights: `canApprove(actor, goal.ownerId)` (owner, approver or admin; under act-for the owner only).
Checked in this order, inside `goalTx`:

1. Step unknown → `404 step-unknown`; goal `done` or `dropped` → `409 goal-closed`.
2. Not an approver → `403 not-approver`.
3. Gate step → `409 step-gate`; debrief step → `409 step-debrief`; already `parked` →
   `409 step-parked`; a state other than `claimed` or `paused` → `409 step-not-parkable`
   (`<id> is <state>; only a claimed or paused step is parked by hand`). A `ready` step is not
   parked: ADR-0025 D23.1 fixes the check as `claimed` or `paused`.

Effect:
- The step becomes `state: "parked"`, `parkedReason: "operator: <reason>"`, `parkedAt: now`; the
  holder fields (`holderUser`, `holderSid`, `holderMachine`, `claimedAt`, `roundStartedAt`) are
  removed, as a rule park removes them (service.ts:3053-3058). No round is added and `outcome` is
  not set, so the park counts as no attempt in rounds, efficiency or first-pass figures.
- One `step.parked` event: `user` = the actor, payload `{ reason: "operator: <reason>", operator:
  true, was: <previous state>, holder?: <previous holderUser>, via? }` (no `round`).
- When the step had a holder session, one inbox message of kind `parked` to that session:
  `MESH: @<person> parked step <id>: <reason>. Stop working on it; your notes are kept. A person resumes it (mesh step resume <id>).`
  (plus ` (via <service>)` under act-for). The daemon delivers it as any session message; no
  daemon change.
- Nothing else is touched: no process is signalled. A headless run holding the step keeps running
  until it ends; its later `mesh_done`, note or claim on the step is refused as for any step its
  session no longer holds (today's texts; `mesh_done` gets `409 <id> is parked; claim it first`), and
  the run ends as a run whose step was taken from it. Stopping the run is mesh-ai row B-252.
- `POST /v1/steps/:id/resume` (unchanged) lets the step go on: `blocked`, then `ready` when its
  dependencies are done.

Reply: `200 { step: Step }`.

CLI: `mesh step park <step> <reason…>` posts the route with the person's own token and prints
`<step> parked: operator: <reason>`; a refusal prints the hub's `error` and exits 1. It sits beside
`mesh step resume` in `src/cli/hub-commands.ts` and in `mesh --help`.

### Codes

`code` is added beside the unchanged `error` on the refusals below (the `HubError` code argument of
RL-21), and only on them. Every other refusal of these routes keeps its 0.1.41 body with no `code`:
body-schema `400`s (including park's reason), every refusal of `POST /v1/goals` and
`POST /v1/goals/from-preset` other than the act-for row, `approvePlan`'s `422` roster-pin problems,
and `say`'s `400` (`say needs a session`) and `404` on a `to` it cannot resolve. Other routes' bodies
are unchanged.

| Status | `code` | Routes | When |
|---|---|---|---|
| 401 / 403 | `login-required` / `forbidden` | all (exists) | route rule |
| 400 / 403 | `on-behalf-of-required`, `on-behalf-of-not-accepted`, `on-behalf-of-not-service`, `user-unknown` | act-for routes (exist) | `actingFor` |
| 404 | `goal-unknown` | goal approve, revise, replan, drop | no goal |
| 404 | `step-unknown` | step approve, reject, resume, park; message `toStep` | no step |
| 404 | `question-unknown` | answer | no question |
| 403 | `not-approver` | goal approve, revise, replan, drop; step approve, reject, resume, park | the rights check |
| 403 | `not-addressed` | answer | the person is not in `toUsers` (and is not an admin with their own token) |
| 404 | `plan-none` | goal approve, revise | no pending plan (or the asked version) |
| 409 | `plan-decided` | goal approve | the plan was already decided |
| 404 | `design-unknown` | replan | no design step |
| 409 | `goal-closed` | replan, drop, park | goal `done` or `dropped` |
| 409 | `goal-held` | drop | the goal has held steps |
| 409 | `not-gate` | step approve, reject | not a gate step |
| 409 | `gate-not-ready` | step approve, reject | the gate is not `ready` |
| 400 | `reopen-required` | step reject | no `reopen` |
| 409 | `reopen-unknown` | step reject | a `reopen` id is not a done step of the goal |
| 409 | `step-not-resumable` | resume | not `parked` or `failed` |
| 409 | `step-gate`, `step-debrief`, `step-parked`, `step-not-parkable` | park | §Park |
| 409 | `question-answered` | answer | already answered |
| 404 | `session-unknown` | message | the target session is not live or not visible |
| 409 | `step-unheld` | message `toStep` | the step has no holder session |
| 400 | `team-required`, `bad-query` | attention, questions | §Team attention, §Open questions |
| 403 | `team-forbidden` | attention | a member without admin asks for `team=1` |

A client maps `409` codes to "the state moved" and SHOULD refetch; the `error` text stays the
person-readable message.

### `/healthz`

`HUB_FEATURES` gains, sorted: `decide-for` (scopes, act-for on the decision, answer, message, drop
and create routes), `questions-list`, `step-park`, `team-attention`. `decide-for` is also the
goal-create act-for feature that ADR-0025 D23.3 waits for: no separate goal-create feature ships, so a
client switches goal create to act-for when `decide-for` is listed. A client MUST enable each relay
only when the hub lists its feature: an older hub refuses the service token with `403 forbidden` on
the decision routes, ignores the header's meaning on goal create (it answers
`400 on-behalf-of-not-accepted`), and answers `404` for `GET /v1/questions` and
`POST /v1/steps/:id/park`.

### Events

No new event type. `step.parked` payload gains `operator?`, `was?`, `holder?` and the events of
§Attribution gain `via?`. docs/events.md: the `step.parked` row names "or a person parked it by hand
(`operator: true`, `reason` starts with `operator: `)"; a note under the table says which events
carry `via`.

### Daemon

No daemon change. A daemon of any version delivers the `parked` message like any session message;
the session's step is then reported `notHeld` by the next sync (RL-14), as after a takeover.

### Docs

- docs/guide/auth.md: the three scopes in the scope list; the routes added to "A service acts for a
  person", with the member-only rule (an approver or admin who does not own the goal uses their own
  login), the optional header on goal create and drop, and the code table; the team attention and
  open-question reads among the service reads.
- docs/guide/concepts.md: park by hand (who, what it does, resume); team attention in one sentence.
- docs/guide/howto.md: `mesh step park`.
- docs/events.md: as §Events.
- docs/guide/operations.md: one sentence in the upgrade paragraph for this release (scopes, features,
  no migration, no daemon change, re-mint the client's service token).
- docs/plan/implementation-plan.md §5.6: the routes' rows gain their scopes.
- `node scripts/schemas.ts` regenerates the OpenAPI document.

### Compatibility

- Members' own tokens: every route behaves as in 0.1.41 except the additive `code` and the new
  routes. The personal `GET /v1/attention` is unchanged (REQ-TEAMATT-2).
- Service tokens minted before this release lack the new scopes and keep being refused on the
  decision, answer and message routes; a `goals:write` service creating or dropping goals without
  the header behaves as before; a `goals:read` service gains the team attention and open-question
  reads.
- An older client that parses `step.parked` with `reason` and `round` still reads `reason`; `round`
  is absent on a park by hand (it is OPTIONAL in docs/events.md from this release).
- A downgraded hub reads a hand-parked step as any parked step (`parkedReason` is a string) and can
  resume it.
- Older CLIs: no change needed; `mesh step park` exists only in the new CLI. Older daemons: no
  change.
- No migration (schema 12).

## Cross-repo notes (for mesh-ai B-235 and B-238)

The orchestrator records these on the mesh-ai side; they are field choices ADR-0025 D24.1 leaves to
this spec, not changes to it.

- `repo` is the item's step `repo`, else the goal's `primaryRepo`, else `null` (the hub's goal has no
  single repo).
- `who` is one id or `null`; a `hub-question` names its first addressee (the asking session's user)
  and lists every addressee in `toUsers`; `ready-unclaimed` has `who: null`.
- `hub-question` has no `options` (the hub's `Question` has none).
- `decide-for` is the goal-create act-for feature of D23.3.
- Under act-for only the goal owner passes `canApprove`: a relay of an approver who does not own the
  goal gets `403 not-approver` (gateway `403 hub-not-approver`, D23.7); the dashboard shows the
  hand-off.
