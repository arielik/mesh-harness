# Spec RL-29: Decide a review from a client, and a newer run supersedes an older open review

## Status
Draft (2026-11-27, revision 3). Revision 2 answers the cold review round 1 (mesh-ai `reviews/B-294/r1-spec.md`,
findings 1-9); revision 3 answers round 2 (`reviews/B-294/r2-spec.md`, findings 1-4); §Review history.

Source: an external request, mesh-ai row B-294 (mesh-ai programme `finding-reviews-2026-11-27`). The client's owner
decided on 2026-11-27 (mesh-ai `reviews/owner/2026-11-27-finding-reviews-decisions.md`, D1 "build A + B + C in
full"): a person decides a pulse run's findings review from the mesh-ai Work view (accept, dismiss with a reason,
defer with a date, per item; one submit finishes the review so the `file` step runs on the accepted items), and a
newer run of the same lineage supersedes an older open review, the decisions carrying over by fingerprint. The
client's decision text is mesh-ai local ADR-0025, Amendment 2026-11-27 (B-293, D31); its consumer spec is mesh-ai
`specs/0149-finding-reviews-in-work.md`. Where this spec and those texts differ, the client's ADR governs what the
client relies on; this spec governs the hub.

Builds on RL-2 (review records, the fold, item rows per lineage), RL-4 (debrief steps, `disposeStep`, the debrief
pre-read), RL-6 (calibration after a dismissal), RL-9 (sinks into "Clean audits" goals), RL-11 (trial goals),
RL-15 (overlap `supersede`, carry, the debrief SLA) and RL-22 (act-for writes: `X-Mesh-On-Behalf-Of`, `via` on the
events). Release: the first mesh-harness release after 0.1.45 (planned 0.1.46). Owner constraint carried over:
nothing tied to costs.

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY" and
"OPTIONAL" in this document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when,
and only when, they appear in all capitals, as shown here.

## Problem

1. **A review is decided only in a held session.** `disposeStep` (src/hub/service.ts:2099) takes one decision at a
   time and only while the debrief step is `claimed` or `paused` and held by the caller; the round's review record
   (`submitReview`, :1563) and `doneStep` (:3196) need the same hold, and a claim needs a session. A person who
   reads the findings in a client and knows the answer still has to open a terminal, run `mesh debrief <step>` and
   walk the items with an agent. On the live hub on 2026-11-27 nine reviews holding 15 confirmed S2 items had
   waited since 2026-11-20.
2. **Open reviews pile up per lineage.** Under the default overlap `skip` a goal that only waits on its debrief
   does not block a fire (`runningGoal`, :7258: "Only machine work blocks"), so a weekly pulse opens a new review
   every week while the older one is still `ready`. The newer debrief lists the same confirmed fingerprints (G70
   listed G51's items). RL-15's `supersede` overlap ends the older goal, but only for pulses set to `supersede`, and
   at fire time, before the new run has produced a review (a failed audit leaves no open review at all).

### Facts verified in the code (0.1.45)

| # | Fact | Evidence |
|---|---|---|
| F-1 | Item state is one row per `(lineage, fp)`; the lineage is `preset × repo × raising agent` and does not name the goal or the pulse. | `lineageOf`, src/core/review.ts:103; `store.getItem(lineage, fp)` |
| F-2 | The fold keeps an item's decision across runs: a repeat keeps `accepted` and `dismissed` (a dismissed item reopens only when its evidence hash changed, mark `regression`), and keeps `deferred` until `until` is today or earlier, then `open`. | `foldItems`, src/core/review.ts:198-239 |
| F-3 | A debrief lists only the items of its debrief set whose row is in a consumed state (`policy.consumes`, `confirmed` in the routine presets). A decided item is therefore not presented again, in this run or a later one, while F-2 keeps its state. | `debriefData`, src/hub/service.ts:1904-1934 |
| F-4 | A decision in one open debrief removes the item from every other open debrief of the same lineage (the row is shared). | F-1, F-3 |
| F-5 | RL-15 `supersede` (src/hub/service.ts:7297) carries a waiting goal's undecided debrief items into the new slot (`carry`), runs its undone sinks, drops it with reason `superseded` and emits `pulse.superseded`. | src/hub/service.ts:7297-7332 |

Carry-over by fingerprint (owner proposal C) therefore holds today (F-2 to F-4): an item accepted, dismissed, or
deferred with `until` in the future is not presented again. This spec pins it with a test (AC-12) and changes no
fold rule.

## Terminology

- **Review**: a debrief step (`policy.mode: debrief`) of a pulse goal.
- **Open set**: the items `GET /v1/steps/:id/debrief` lists now for the review (its `items`, F-3).
- **Decision**: one `{fingerprint, disposition, reason, until?, requires?}` for an item of the open set.
- **Decision set**: the decisions of one request, one per item of the open set.
- **Assignee**: the review's resolved assignee (`debriefAssignee`; `@owner` is the goal owner).
- **Newer / older run**: of two pulse goals, the one with the later / earlier `createdAt` (ties: goal id order).

## Scope

In:
- `POST /v1/steps/:id/decisions`: a person (or a service acting for one) records the decision set of a review and
  finishes it in one transaction.
- A new `DispositionVia` value `review-submit`.
- Supersede at review time: when a pulse goal's review becomes `ready`, older open reviews of the same lineage that
  no one has started deciding are ended, their undecided items carried into the new review.
- The event `review.superseded`; the `/healthz` feature `review-decisions`.
- Docs: events, concepts, operations upgrade note.

Out:
- The hub web UI and the `mesh` CLI: no change. `mesh debrief` and `mesh_dispose` keep working as in 0.1.45.
- A change to the fold, to carry-over rules or to the RL-15 overlap policies.
- Partial submission (some items now, the rest later) from a client: a client that wants that uses `mesh debrief`.
- Superseding a review that has a decision in its current round, a `claimed` review, a trial goal's review, or a
  person goal's review.
- A new service scope: the route reuses `goals:decide`.

## Requirements

### Decide a review from a client

- **REQ-REVDEC-1** `POST /v1/steps/:id/decisions` MUST take `ReviewDecisionsRequest` (§Protocol) and MUST be served
  to a member, and to a service token with scope `goals:decide` acting for a person (`X-Mesh-On-Behalf-Of`
  REQUIRED for a service caller, `onBehalfOfRequired`). The person (the caller, or the person acted for) is the
  **decider**.
- **REQ-REVDEC-2** The hub MUST refuse, with no write:
  - `409 not-a-review` when the step is not a debrief step;
  - `403 not-assignee` when the decider is not the assignee (no admin or owner exception, as RL-4's
    `refuseNonAssignee`);
  - `409 review-not-open` when the step is not `ready`, `paused`, or `claimed` by the decider (a step `claimed` by
    another person, or `done`, `skipped`, `dropped`, `parked`, `failed`, `blocked`);
  - `409 review-recorded` when the current round already has a review record.
  A review whose goal was dropped (superseded, REQ-REVSUP-2) is `dropped` and answers `409 review-not-open`; the
  message names the newer review (`superseded by <R*>`) when the drop was a supersede. The hub reads that text from
  the `by` of the step's latest `review.superseded` event (REQ-REVSUP-2); no field is stored on the goal or step. A body that fails
  `ReviewDecisionsRequest` (a missing or empty `reason`, a malformed `until`, an unknown key, more than 500
  decisions) answers `400` from the route's schema check, before every check above.
- **REQ-REVDEC-3** The hub MUST refuse with `422` and a `problems` list (`string[]`, one entry per failing
  decision, the RL-21 shape `submitReview` uses), with no write, a decision set that: leaves an item of the open set without a decision
  (`review-incomplete`); names a fingerprint not in the open set (`review-unknown-item`); lists a fingerprint twice;
  sets a disposition not in the step's `may_set`; gives `deferred` without `until`, or `until` that is not a real
  calendar date later than the hub's current UTC date (`new Date(now).toISOString().slice(0, 10)`, the fold's
  today); gives `requires` on a disposition other than `accepted`. The code of the answer is the first failing kind in that order; `review-invalid` covers the kinds
  after the first two.
- **REQ-REVDEC-4** Every decision MUST carry a `reason` of 1 to 2000 characters (as `RecordDisposition`). A client
  MAY send a fixed reason for an accept or a deferral; a dismissal's reason is the person's text (the client's
  rule; the hub cannot tell).
- **REQ-REVDEC-5** An empty decision set MUST be accepted only when the open set is empty (a review emptied by
  auto-accept, or by decisions made in another review of the lineage, F-4); it finishes the review with zero counts.
- **REQ-REVDEC-6** An accepted request MUST, in one `goalTx` transaction, with round `n` = the step's current round:
  1. apply each decision with `applyDisposition` (decider `{kind: "person", user: <decider>}`, via `review-submit`,
     `seenAt` = this goal, step and round), so the RL-9 finding-step sync runs as for a debrief decision, and add the
     step note `debrief: <disposition> <fp> "<title>": <reason>` per decision (as `submitReview` does for a debrief);
  2. store the round's review record and its `review` artifact, built by the hub: `{ subject: {}, coverage:
     "complete", assessment: "issues" when one decision of the round is `accepted` else "clean", items: [],
     dispositions: <the round's earlier decisions, then the decision set>, summary: "<a> accepted, <d> dismissed, <f> deferred by <decider>" }` (counts over the whole
     round), `decider` the person. The round's **earlier decisions** are this step's round-`n` `debrief-session`
     disposition rows that are still the item's latest change (`isRevertable`) and whose fingerprint is not in the
     decision set: a session decision later reverted is not one (its item is in the open set again and is decided by
     the decision set);
  3. finish the step `done` with a round `{ n, user: <decider>, outcome: "done", summary: <the record summary> }`
     (no `sid`; `read` from `step.read` when it is this round), from `ready`, `paused` or `claimed` alike, with no
     `step.claimed` event. Unlike `finish` (src/core/claims.ts:91), the holder fields are cleared by design: no
     session finished the step. When the step had a `holderSid`, the hub MUST send that session a message
     `MESH: <step> was finished from a client by <decider> (<a> accepted, <d> dismissed, <f> deferred)`, as it
     messages a session for a reopen;
  4. settle the goal's steps as `doneStep` does, so the downstream `file` step becomes `ready` when an accepted item
     is consumed (`when: {open: true}`, `consumes: [accepted]`) or is skipped otherwise, run `sinkAfter` for the
     settled steps, and complete the goal when `goalComplete` holds;
  5. run `calibrationAfterDismissal` once when one decision is `dismissed` (RL-6, as `disposeStep`).
- **REQ-REVDEC-7** The request MUST emit these types in this relative order (other events the existing code emits
  meanwhile, such as RL-9 finding-step sync, a calibration goal's events or offer-ended events, keep their place and
  are not part of the order): per decision `item.disposed` (`via: "review-submit"`, `decider: "person"`, `round`)
  then its `step.noted`; `review.recorded` (`dispositions` = the count in the record, `already` = the count of the
  round's earlier session decisions); `step.done`; then the events of the settle (`step.ready`, `step.skipped`,
  `goal.done`) as `doneStep` emits them.
  `user` on each is the decider. Under act-for RL-22 puts the service in `payload.via`; `item.disposed` already
  uses `via` for the disposition route, so on `item.disposed` the service MUST go in `payload.service` instead and
  `via` MUST stay `review-submit`. Every other event of the request carries RL-22's `via`.
- **REQ-REVDEC-8** The answer MUST be `200 ReviewDecisionsResult` (§Protocol): the counts (over the round), the
  round, the steps the settle changed with their new state, and `sink`: `{ topic, title }` when a downstream step
  with `sink` became `ready` in this settle, else `null`. The title is `Clean audits: <topic> on <repo name>` for
  the lineage repo, as RL-9 names the goal; an item retargeted to another repo (RL-10) lands in that repo's goal,
  which the title does not name.
- **REQ-REVDEC-9** `DispositionVia` MUST add `review-submit`. `DEBRIEF_VIAS` MUST include it, so a `review-submit`
  decision is listed in the debrief view's `decided`, is revertable by `POST /v1/steps/:id/dispositions/revert`
  while it is the item's latest change, and is listed in `GET /v1/debriefs` `decided` with the `debrief-session`
  ones. RL-6 calibration and the agent statistics MUST count a `review-submit` decision as a person's debrief
  decision wherever they count `debrief-session` today.
- **REQ-REVDEC-10** An `Idempotency-Key` MUST be honoured as on the other act-for writes (a repeat with the same key
  answers the stored result and writes nothing).

### A newer run supersedes an older open review

- **REQ-REVSUP-1** When a write moves a review `R` of a non-trial pulse goal from `blocked` to `ready`, the hub
  MUST, in the same transaction and as its **last** step (after the caller's own events, its `sinkAfter` and its
  goal-completion check, in `doneStep`, `resumeStep`, `decideReview` and every other settle path), take the group `S` of open reviews (`ready`, `claimed` or `paused`, `R` included)
  of non-trial goals that are not `done` or `dropped`, whose goal has the **same pulse** (`refs.pulse`) as `R`'s and
  whose lineage (`debriefSet(·).lineage`) equals `R`'s. Let `R*` be the review in `S` of the newest goal `N`. Every
  other review `R'` in `S`, of goal `O`, MUST be superseded into `R*` when all hold: `R'` is `ready` or `paused`
  (a `claimed` review is never superseded); `R'` has no disposition recorded in its current round (by any decider
  or via); and REQ-REVSUP-3 allows `O`. This covers both orders: a newer review becoming ready ends the older ones,
  and an older review becoming ready after a newer one is open ends itself into the newer one. Reviews of another
  pulse are never touched, so a supersede never moves items to another owner's review.
- **REQ-REVSUP-2** Superseding `R'` MUST: add `R'`'s undecided items (its open set) to the `carry` of `N`'s slot for
  the local id of `R*` and the lineage (merged with an existing entry, unique, sorted, at most 1000, as RL-15); run
  `O`'s undone sink steps (`runSink`, as RL-15); drop `O` with `dropGoal(O, "superseded", now, { comment:
  "superseded by <R*>" })`; and emit `review.superseded` (§Events). It MUST NOT emit `pulse.superseded` (that event
  stays RL-15's fire-time record). Event order in the request: the settle events that made `R` ready (its
  `step.ready`), then per `O` in goal order: `goal.dropped`, its `step.dropped` events, `review.superseded`.
- **REQ-REVSUP-3** A goal `O` that also has another open step that is `claimed` or `paused` (other than `R'`) or
  machine work (`overlapBusy`) MUST NOT be superseded (RL-15's `waitingGoal` rule, with `R'` itself allowed to be
  `paused`).
- **REQ-REVSUP-4** Superseding MUST NOT change an item row, a disposition or the fold: decisions carry over by
  fingerprint only through F-2 and F-3. After the supersede, `R*`'s open set MUST be its run's record items and the
  carried items that are in a consumed state.
- **REQ-REVSUP-6** A consuming step downstream of a debrief step `D` in the same goal (the `file` step) MUST work
  from the union of its run's record fps and `D`'s carry (the carried part of `D`'s debrief set), so a carried item
  accepted in `D` is filed. This applies to `holdsFor` (its `when`), `dispositionsInput` (its `dispositions` input;
  a carried item's evidence and proposal come from the record its row's `last` names, `lastRecordItem`) and the
  `runFps` check of `submitReview` for a non-debrief consuming record. Without a carry the behaviour is 0.1.45's.
- **REQ-REVSUP-5** RL-15 `supersede` at fire time MUST keep working unchanged; both rules MAY apply to the same
  pulse.

### Feature, compatibility, docs

- **REQ-REVDEC-11** `HUB_FEATURES` MUST list `review-decisions` when REQ-REVDEC-1 to -10 and REQ-REVSUP-1 to -6 are
  served.
- **REQ-REVDEC-12** The change MUST be backwards compatible: no route, field, event or code is removed or renamed;
  the store schema number is unchanged (no migration); a client of 0.1.45 keeps working. Two behaviour changes are
  visible to an old client: a pulse goal can now be dropped with reason `superseded` when its review is overtaken
  (REQ-REVSUP-1), and a disposition can carry via `review-submit`.

### Decisions this spec takes

- **One write for the whole review (REQ-REVDEC-3, -6).** The client's owner asked for one submit that finishes the
  review. Taking the whole set keeps the round's review record, the step's end and the downstream `file` step one
  transaction, so a client never leaves a half-decided review that no session holds.
- **Any open state, no claim (REQ-REVDEC-2, -6).** A client has no session, so the hub does not ask for a claim; it
  refuses only a review another person holds. A `paused` review is the assignee's own (only the assignee can hold
  a debrief, RL-4), so the decider's submit ends it.
- **Reuse `goals:decide` (REQ-REVDEC-1).** Deciding a review is a decision like a gate or a plan; the client's token
  holds the scope already, so no re-mint is needed.
- **Same pulse only (REQ-REVSUP-1).** The lineage names neither the pulse nor the owner; two pulses of one preset,
  repo and agent may belong to two people, and only a review's assignee may decide it (RL-4). Keeping the rule
  inside one pulse keeps the items with the person who owns the run.
- **Carried items are filed (REQ-REVSUP-6).** RL-15 carry fed only the debrief; with supersede on every pulse, an
  accepted carried item would otherwise stay `accepted` with no link and never be filed.
- **Supersede at review time, only an untouched review (REQ-REVSUP-1).** At fire time (RL-15) the new run has not
  yet produced a review; at review time it has. A review with a decision in its round has accepted items its own
  `file` step still has to file, so it is left alone; its decided items have already left every other open set
  (F-4).
- **`service` on `item.disposed` (REQ-REVDEC-7).** RL-4 gave `item.disposed` a `via` before RL-22 gave act-for
  events one; renaming either breaks a consumer, so the act-for service takes a new key on this one event.

## Interface contracts

### Protocol (src/protocol/review.ts, src/protocol/hub.ts, src/protocol/hub-api.ts)

```ts
// review.ts
export const DispositionVia = z.enum(["stage", "debrief-session", "auto-accept", "review-submit"]);

// hub.ts
export const ReviewDecision = RecordDisposition.omit({ link: true }); // fingerprint, disposition, reason, until?, requires?
export const ReviewDecisionsRequest = z.object({ decisions: z.array(ReviewDecision).max(500) }).strict();
export interface ReviewDecisionsResult {
  step: string;
  goal: string;
  round: number;
  counts: { accepted: number; dismissed: number; deferred: number };
  next: { step: string; state: StepState }[]; // steps the settle changed, in step order
  sink: { topic: string; title: string } | null;
}
// HUB_FEATURES: + "review-decisions"
```

### Service (src/hub/service.ts)

- New `decideReview(actor, id, body)` in `goalTx`: REQ-REVDEC-2 to -8. The open set is `debriefData(step, goal,
  steps).items`. Steps 3 and 4 MAY share code with `doneStep` (the round, `finish`, `settleSteps`, `sinkAfter`,
  `goalComplete`); the record of step 2 MAY share code with `submitReview`.
- `DEBRIEF_VIAS` (:475) adds `review-submit`; `debriefs` (:2084) filters `DEBRIEF_PERSON_VIAS` (`debrief-session`,
  `review-submit`) instead of `debrief-session`; src/core/calibration.ts (:70-71) reads the same set.
- New `supersedeReviews(goal, step, now)` called last in the transaction of every write whose `settleSteps` moved a
  debrief step from `blocked` to `ready` (REQ-REVSUP-1 to -4). The caller's answer is built before it and MAY still
  list the review as ready (for example `doneStep`'s `nowReady` when the review was itself superseded); a client
  re-reads.
- `holdsFor`, `dispositionsInput` and `submitReview`'s `runFps`: REQ-REVSUP-6 (a helper `consumedSet(step, goal,
  steps)` = run record fps ∪ the carry of the debrief the step depends on). The per-goal body of `supersede` (:7297) MAY be factored and shared.
- `HUB_FEATURES` (src/protocol/hub.ts:862) adds `review-decisions`.

## Compatibility

Additive (REQ-REVDEC-12). No new table and no schema step: `DispositionVia` is a JSON field, so stored rows parse;
a hub downgraded to 0.1.45 after a `review-submit` row exists refuses to parse it (the operations note says to
back up first, as for every release). The mesh-ai client gates its controls on `review-decisions` and falls back to
the `mesh debrief` hand-off without it (mesh-ai ADR-0025 D31).
