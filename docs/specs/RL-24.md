## Problem

1. **No single action stops new unattended work.** During a bad agent release, a broken shared
   branch or a leaked credential an operator wants "start nothing new unattended, now". Today that
   is one `POST /v1/pulses/:id/pause` per pulse, and only its owner or an admin may pause it.
2. **Pausing pulses is not enough.** Goals already planned keep offering their headless steps:
   the pulse attempt (`attempt`, service.ts:6421), a goal's stick (`emitReady`, service.ts:780),
   `POST /v1/steps/:id/assign` with a headless run (RL-21) and `POST /v1/goals/:id/assign`
   all reach `offerStepMessage` (service.ts:712), and a daemon accepts an `auto` headless offer and
   starts `claude -p` (daemon.ts:851, runs.ts:484).
3. **A daemon starts queued runs on its own.** A run accepted while the machine was at
   `maxSessions` waits in the daemon's queue and starts when a session ends (runs.ts:721); the hub
   holds no lever on it.
4. **A dashboard cannot pull the switch.** A service token never runs with a person's admin role:
   `actingFor` returns `roles: ["member"]` by design (service.ts:2245-2257).
5. **Nobody can see that the fleet is paused.** No probe, read or event says so.

## Scope

In:
- `POST /v1/fleet/pause { reason }` and `POST /v1/fleet/resume { reason? }`.
- A new service scope `fleet:pause`; act-for on both routes **keeping the person's `admin` role**,
  and on no other route (§Rights).
- The stored fleet state, one row; `paused` on `GET /healthz` (and `/health`); `paused` in the
  `POST /v1/sync` reply.
- Hub behaviour while paused: pulse slots that would fire (due or queued) recorded `skipped` with
  reason `fleet_paused`, no headless offer made by any path, open headless offers withdrawn at the
  pause, headless accept refused, manual pulse fire refused (§Effects).
- Daemon behaviour while paused: no queued run started; a one-time notification on each change;
  `mesh status` says so (§Daemon).
- Events `fleet.paused` and `fleet.resumed` with `user` and `payload.via`.
- CLI `mesh fleet pause <reason…>` and `mesh fleet resume [reason…]` (the hand-off a client shows).
- `/healthz` feature `fleet-pause`; a stable `code` on every refusal this spec adds.

Out:
- Stopping, signalling or messaging any running process: running headless runs, claimed steps and
  interactive sessions go on (B-252 stops them).
- Interactive (non-headless) offers, `auto` or not, and sessions claiming steps by hand: unchanged.
- Per-pulse pause and resume (`/v1/pulses/:id/pause|resume`): unchanged and independent; a fleet
  resume never enables a pulse that its owner paused.
- A pause scoped to a repo, a person or a pulse kind; a scheduled or self-expiring pause.
- The hub's own web pages (a banner there is a later item; the client shows its own banner).

## Requirements

- **REQ-FLEETPAUSE-1** `POST /v1/fleet/pause` MUST store the pause (`since`, `by`, `via?`,
  `reason`) and emit exactly one `fleet.paused` event, inside one transaction; `POST /v1/fleet/resume`
  MUST clear it and emit exactly one `fleet.resumed` event, inside one transaction.
- **REQ-FLEETPAUSE-2** Both routes MUST be refused unless the effective actor holds the `admin`
  role: an admin with their own token, or a service token with scope `fleet:pause` acting for a
  person who holds `admin` (§Rights).
- **REQ-FLEETPAUSE-3** Act-for MUST keep the person's `admin` role on `POST /v1/fleet/pause` and
  `POST /v1/fleet/resume` and MUST NOT keep it on any other route of `HUB_API`.
- **REQ-FLEETPAUSE-4** Every `fleet.paused` and `fleet.resumed` event MUST carry `user` = the
  person; when a service acted, `payload.via` = the service user id; otherwise no `via`.
- **REQ-FLEETPAUSE-5** While the fleet is paused, a pulse slot that the hub would fire (a due slot
  that is in its window or caught up under `missed: catch-up-once`, and a `queued` slot that
  `releaseQueued` would release) MUST be recorded `skipped` with reason `fleet_paused` and MUST NOT
  create a goal; a due slot the hub would not fire MUST be recorded as 0.1.41 records it
  (`missed`/`hub_down`). The pause state that counts is the stored one read in the transaction of
  the tick that handles the slot (ticks run every `tickMs`, 30 s by default): a slot that fell due
  before a resume but is handled by the first tick after it fires as today. A slot that the hub
  recorded `skipped`/`fleet_paused` MUST NOT fire or be caught up after a resume (no burst).
- **REQ-FLEETPAUSE-6** While the fleet is paused, the hub MUST NOT make a headless offer by any path,
  and MUST refuse the accept of a headless offer with `409 fleet-paused`.
- **REQ-FLEETPAUSE-7** The pause MUST withdraw, in its transaction, every open headless offer, and
  MUST NOT change any claimed step, running run, session or interactive offer. The resume MUST
  offer again only steps the pause held back (§Resume step 4); it MUST NOT offer a step whose offer
  was declined or expired, or withdrawn by anything other than the pause. When a withdrawn offer
  is the run step offer of a pending pulse slot, the pause MUST remove that offer's undecided try from
  the slot's `tried` list, so that the machine stays a candidate after the resume.
- **REQ-FLEETPAUSE-8** `GET /healthz` MUST report `paused: FleetPause | null` without a database
  read; on a replica other than the one that served the change it MUST reflect the change within
  5 s.
- **REQ-FLEETPAUSE-9** The `POST /v1/sync` reply of a hub of this release MUST carry `paused`
  (`null` or the stored pause). A daemon of this release whose last sync reply says paused MUST NOT
  start a queued headless run until a sync reply says not paused.
- **REQ-FLEETPAUSE-10** A pending pulse slot whose window ends while the fleet is paused, and whose
  run has not started, MUST be recorded `missed` with reason `fleet_paused`, and its goal MUST be
  dropped as 0.1.41 drops a missed slot's goal.
- **REQ-FLEETPAUSE-11** A daemon of this release with notifications on MUST send exactly one
  notification for each change of the fleet pause between two sync replies, and MUST NOT notify for
  the first reply after it starts or for a reply that does not change the pause.
- **REQ-COMPAT-1** A response of a route that exists in 0.1.41 MUST NOT lose a field or change a
  value when the fleet is not paused; a hub that was never paused MUST behave as 0.1.41 apart from
  the additive fields of §Compatibility.

### Rights

The route rule is `member` with scope `fleet:pause`, so `allowed()` (src/core/roles.ts:53) lets in a
member token and a service token with the scope; the handler then requires `admin` on the effective
actor (after `actingFor`) and answers `403 not-admin` otherwise.

| Caller | `X-Mesh-On-Behalf-Of` | Result |
|---|---|---|
| a person with `admin`, own token | absent | 200; `by` = the person, no `via` |
| a person without `admin`, own token | absent | `403 not-admin` |
| a person's own token | present | `403 on-behalf-of-not-service` (today's rule) |
| service with `fleet:pause` | absent | `400 on-behalf-of-required` |
| service with `fleet:pause` | a person with `admin` | 200; `by` = the person, `via` = the service |
| service with `fleet:pause` | a person without `admin` | `403 not-admin` |
| service with `fleet:pause` | unknown id or a service account | `403 user-unknown` (today's rule) |
| service without `fleet:pause` | any | `403 forbidden` (route rule) |

The person's roles are read from the store at request time (`actingFor` already loads the user), so
a person whose admin role was removed is refused on the next request.

Mechanism. `HubApiRoute` (src/protocol/hub-api.ts) and the app's `Route` (src/hub/app.ts) carry
`onBehalfOfRoles?: readonly ("approver" | "admin")[]`: the person's roles, besides `member`, that
act-for keeps on that route. `actingFor` takes it as `route.keep` and returns
`roles: ["member", ...person.roles ∩ keep]`. RL-22 defines the same field with `"approver"` only;
whichever spec is built first adds the field and the other widens or uses it. The two fleet routes
set all three act-for fields: `onBehalfOf: true` (without it `actingFor` is called with
`allowed: false`, app.ts:588, and every act-for call answers `400 on-behalf-of-not-accepted`),
`onBehalfOfRequired: true` and `onBehalfOfRoles: ["admin"]`. A unit test over `HUB_API` MUST
assert that the set of routes whose `onBehalfOfRoles` contains `"admin"` is exactly these two
(REQ-FLEETPAUSE-3); the docstring of `actingFor` names the exception and MESH-OQ-AIOPS-12.

Idempotency keys work as on every act-for route (`<service>><person>`, app.ts:590): a relay that
retries the same `Idempotency-Key` gets the first reply and no second event.

### Stored state

A new table, one hub migration (the next schema number at build time; 13 when no other spec of the
programme migrates first), in both the SQLite and the Postgres migration lists:

```
CREATE TABLE IF NOT EXISTS hub_state (k TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at INTEGER NOT NULL);
-- Postgres: updated_at BIGINT NOT NULL
```

Row `k = 'fleet'`, `value` = JSON `FleetPauseRow` while paused; no row (or the row deleted) means
not paused. `FleetPauseRow` is hub-internal (never in a reply, `/healthz` or an event):

```
FleetPauseRow = FleetPause & {
  held: string[],   // step ids the pause held back (§Pause step 4, §Effects stick rows); no duplicates
  skipped: number,  // slots recorded skipped / fleet_paused during this pause
  missed: number,   // slots recorded missed / fleet_paused during this pause
}
```

Every write that changes `held`, `skipped` or `missed` reads and rewrites the row inside the same
`goalTx` that records the step or slot, so the values hold across replicas. `HubStore` gains
`getFleetPause(): Promise<FleetPauseRow | undefined>` and
`setFleetPause(p: FleetPauseRow | undefined, now: number)`. `mesh hub migrate --from … --to postgres://`
copies the table.

### Pause: `POST /v1/fleet/pause`

Inside `goalTx` (so it serialises with every offer, fire and accept):
1. Not admin → `403 not-admin`.
2. Already paused → `409 fleet-already-paused`, `error`: `the fleet is already paused since <ISO> by
   <by>: <reason>`; nothing changes.
3. Store `{ since: now, by: actor.userId, via?: actor.via, reason, held: [], skipped: 0, missed: 0 }`.
4. Withdraw every open headless offer: each step in state `ready` whose `offer.state === "offered"`
   and whose offer or policy is headless (`offer.mode === "headless"` or `policy.mode ===
   "headless"`) goes through the existing `withdrawOffer` path (service.ts:2155) with reason
   `fleet paused`. As today, that saves the step and emits `step.offer_withdrawn` (reason
   `fleet paused`, `user` = the person) and sends **no message**; this spec adds none. The goal's
   stick is kept. Each withdrawn step's id is appended to `held`.
   **Pulse run steps.** When the step is the run step of a pending pulse slot (the slot that
   `pendingSlotOf(goal, step)` returns, service.ts:5528), the pause also rewrites that slot in the
   same transaction: if the slot's last try has no `outcome` and its `machine` equals the withdrawn
   offer's `to.machine`, that try is removed from `tried`; every other try is kept. Without this,
   the next `advanceSlot` would record the try as `timeout` (`syncLastTry`, service.ts:5553, maps a
   `withdrawn` offer to `timeout`) and `pulseCandidates` would leave the machine out
   (src/core/pulse.ts:101), so a single-machine pulse could never be offered again after the
   resume. The removed try is the one the pause cut short; the machine did not refuse anything.
5. Emit one `fleet.paused`: `user` = the person, payload `{ reason, withdrawn: <number of offers
   withdrawn>, via? }`.
6. Update this replica's cache (§`/healthz`).

Reply `200 { paused: FleetPause }`.

### Resume: `POST /v1/fleet/resume`

Inside `goalTx`:
1. Not admin → `403 not-admin`.
2. Not paused → `409 fleet-not-paused` (`the fleet is not paused`).
3. Clear the row.
4. Re-offer by stick, **only the held steps**: every step whose id is in the row's `held` list, that
   is still `ready` with no open offer, whose goal is not `done` or `dropped` and still has a stick,
   is offered as `emitReady` offers it (the same guard `headlessGuard`, the same target), without
   emitting a second `step.ready`. The test is the stored `held` list read in this transaction; no
   event scan. A ready headless step not in `held` (for example one whose offer was declined,
   `declineStep`, or expired, the MM-3 tick, before or during the pause) is left as 0.1.41 leaves
   it: nothing offers it again. **Excluded:** the run
   step of a pulse goal, that is a step whose goal has `refs.pulse` set and whose id is
   `runStepOf(goal)` (service.ts:5521). `attempt` sets a stick on every pulse goal it offers
   (service.ts:6454), so without this exclusion the resume would offer the run step outside the
   slot's `tried` bookkeeping; the pending slot's next attempt (the next tick) offers it instead.
   Other headless steps of a pulse goal are re-offered by stick like any goal's. A headless offer
   withdrawn by the pause from a goal with no stick (for example one made by
   `POST /v1/steps/:id/assign`) is not re-offered: its offerer assigns it again.
5. Emit one `fleet.resumed`: `user` = the person, payload `{ pausedAt: <since of the pause>,
   pausedBy: <by>, skipped: <row.skipped>, missed: <row.missed>, reason?, via? }`. `skipped` counts
   the slots recorded `skipped`/`fleet_paused` during the pause (due and queued slots of
   REQ-FLEETPAUSE-5); `missed` counts those recorded `missed`/`fleet_paused` (REQ-FLEETPAUSE-10).
   Both are the stored counters of §Stored state, read in this transaction.
6. Update this replica's cache.

Reply `200 { paused: null }`.

The resume does not fire any pulse, does not move any `nextAt` and does not enable any disabled
pulse.

### Effects while paused

Every check below reads the stored row inside the transaction that acts; the `/healthz` cache is
never used for enforcement.

| Path | Today | While paused |
|---|---|---|
| Tick, a due pulse (`firePulseTx`, service.ts:6801) | `fires = inWindow \|\| missed === "catch-up-once"`; when `fires`, the latest due slot fires (`fireSlot`) and older due slots are `missed`/`hub_down`; when not, every due slot is `missed`/`hub_down` | the `hub_down` records are exactly as today. `fleet_paused` replaces exactly the `fireSlot` call: when `fires` (and no `error`), the latest due slot is recorded `skipped`, reason `fleet_paused` (no goal, no overlap check, no retire, no catch-up; the row carries `catchUp: true` exactly when today's `fireSlot` would set it, that is when the slot fires only because of `catch-up-once`), `row.skipped` is incremented, and `pulse.skipped` is emitted with `{ pulse, slot, reason: "fleet_paused" }`. When not `fires`, the latest due slot is `missed`/`hub_down` as today. `nextAt` moves on as today |
| Tick, a pending slot (`advanceSlot`, service.ts:6391) | started, missed at the window end, or one attempt | started handling as today; **no attempt**. A slot whose window ends while paused, not started, is recorded `missed` with reason `fleet_paused` (instead of `no_machine`, `not_accepted`, …), its open offer withdrawn and its goal dropped as today, and `row.missed` is incremented (REQ-FLEETPAUSE-10) |
| Tick, a `queued` slot (`releaseQueued`, service.ts:6751; RL-15 `overlap: queue`) | once no goal of its pulse runs, `slotGoal` creates its goal and makes an attempt | the slot is checked as today (pulse gone or not `queue`, owner not a member, pulse disabled, a goal still running: unchanged handling). Where today's code would call `slotGoal`, the slot is instead recorded `skipped`, reason `fleet_paused`, `decidedAt` = now, `row.skipped` is incremented, and `pulse.skipped` is emitted with `{ pulse, slot, reason: "fleet_paused" }`; no goal is created. A queued slot whose running goal is still running stays `queued`; if that goal ends after the resume, the slot is released as today. No new slot becomes `queued` while paused, because a paused due slot skips the overlap check |
| `POST /v1/pulses/:id/fire` (manual and `trial`) | fires | `409 fleet-paused`; no slot row. Checked after today's checks: unknown pulse `404` and `ownerOrAdmin` `403` come first, so a caller who may not fire the pulse gets `403` as today |
| Stick offer on `step.ready` (`emitReady`) | offers | where today's code would call `offerStep` for a headless step (every earlier guard, `headlessGuard` included, passed), the step is not offered, stays `ready`, and its id is appended to `held` (the resume offers it); a non-headless step is offered as today |
| `POST /v1/steps/:id/assign` | offers | `409 fleet-paused` when the offer would be headless (declared headless, or `mode`/`profile` of RL-21); a non-headless assign as today |
| `POST /v1/goals/:id/assign` | offers every offerable ready step | a headless step whose `headlessGuard` passes is left out for the pause (a step the target cannot run is skipped as today, before the pause check). If no step is left to offer and `stick` is not set: `409 fleet-paused` when at least one step was left out for the pause alone, else today's `409 … has no ready step to offer` (no code). With `stick` set, the steps left out for the pause are appended to `held`. Non-headless steps are offered as today |
| `POST /v1/steps/:id/accept` of a headless offer | claims | `409 fleet-paused`; the offer stays as it is (the pause already withdrew it, so this is only reached by a race inside the hub's own ordering, which `goalTx` excludes, or by an offer created by a hub version without this check during a rolling upgrade) |
| Any other route | — | unchanged |

`SlotReason` (src/protocol/pulse.ts) gains `fleet_paused`. A slot recorded `skipped` with
`fleet_paused` counts as `skipped` in `GET /v1/health` and the pulse run reads (RL-11, RL-12, RL-15),
like an overlap skip.

### `/healthz`

`Liveness` (src/protocol/hub-api.ts:64) gains `paused: FleetPause.nullable()`, present on every
answer of a hub of this release (also on `/health`, which returns the same body).

`/healthz` asks nothing of the database (RL-11), so each replica keeps the value (the `FleetPause`
part of the row, without `held`, `skipped` and `missed`) in memory:
- loaded once at start, before the server listens;
- set by the replica that commits a pause or resume, after the commit;
- re-read by every replica (leader or not) from the store on its own timer (one primary-key read),
  so the other replicas follow within 5 s (REQ-FLEETPAUSE-8). With SQLite (one process) the timer
  is harmless.

`startHub` (src/hub/server.ts) gains the option `pauseRefreshMs` (default 5000; `0` = no timer, as
`tickMs: 0`). `RunningHub` gains `refreshPause(): Promise<void>`, the one re-read the timer calls, so
tests with `pauseRefreshMs: 0` call it by hand. `RunningHub.stop()` clears this timer with the tick
timer.

A failed re-read keeps the last value and logs once per failure streak. `HUB_FEATURES` gains
`fleet-pause` (sorted). The reason is visible to anyone who can reach `/healthz` (public, like the
version); docs/guide/operations.md MUST say so ("do not put secrets in the reason").

### Daemon

A daemon of this release keeps `fleetPaused: FleetPause | null | undefined` from the last sync
reply that carried the field (`undefined` = the hub never said: an older hub; treated as not
paused).

- **Queue.** `queuePass` (runs.ts:721) starts no queued run while `fleetPaused` is set. A queued run
  past its deadline is still released as today (its step returns to the hub). After a sync reply
  with `paused: null`, the next pass starts queued runs as today (REQ-FLEETPAUSE-9).
- **Offers.** No change: the daemon calls accept as today. The hub refuses a headless accept with
  `409 fleet-paused`, which the existing 4xx path acks `failed` with the hub's `error` (runs.ts:520).
  The daemon does not decline: a decline would count against the machine.
- **Running runs and sessions.** Untouched.
- **Notification.** On each change of `fleetPaused` between two sync replies (set → null, null →
  set, or a new `since`), when `notifyChannels(config).any`, the daemon sends one notification
  through `desktopNotify` / the terminal channel (src/mux/notify.ts) with title `mesh` and body
  `fleet paused by @<by>[ via <via>]: <reason>` or `fleet resumed`. The first reply after the daemon
  starts sets the value without notifying.
- **Status.** The daemon's status (`GET /local/status` of the local control API, daemon.ts:1656;
  read by `client.ts:123`) gains `fleetPaused?`;
  `mesh status` prints, while it is set, one line `fleet paused since HH:MM UTC by @<by>[ via
  <via>]: <reason> (no pulses or headless offers; running work goes on)`.

### CLI

- `mesh fleet pause <reason…>` posts `POST /v1/fleet/pause` with the person's own token and prints
  `fleet paused: <reason> (<n> headless offer(s) withdrawn)`; `mesh fleet resume [reason…]` prints
  `fleet resumed`. A refusal prints the hub's `error` and exits 1. Both are subcommands of the
  existing `mesh fleet` (machinesCommand, src/cli/machine-commands.ts:47): a first positional word
  `pause` or `resume` selects the subcommand; with no positional word, or any other one, the command
  lists machines as today, with its flags (`--label`, `--json`) unchanged. `mesh machines` is the
  same `machinesCommand` (name `"machines"`), so `mesh machines pause` and `mesh machines resume`
  are accepted and behave the same; help names them under `mesh fleet` only. `mesh --help` and
  `mesh fleet --help` list both. This is the hand-off a client shows when it cannot relay.
- `mesh hub token --service <name> --scope fleet:pause` mints a token with the scope (the scope list
  is the enum; no code beyond `SERVICE_SCOPES`).

### Compatibility

- **Members' own tokens and every 0.1.41 route:** unchanged while the fleet is not paused, except the
  additive `paused` on `/healthz`, `/health` and the sync reply. Liveness parsers that are not strict
  (zod `object`, the default) accept the field.
- **Clients MUST gate on the feature.** A client enables its pause control only when `/healthz`
  lists `fleet-pause`. An older hub answers `404` on `/v1/fleet/pause` (no route) and has no
  `paused` field; a client MUST read an absent `paused` as "unknown", not as "not paused".
- **Service tokens** minted before this release lack `fleet:pause` and are refused `403 forbidden`.
- **New enum values.** `SlotReason` gains `fleet_paused` and the event feed carries two new types.
  A client that parses slot reasons or event types with a closed enum MUST be updated (the mesh-ai
  gateway's hub feed parser is one; that change belongs to mesh-ai row B-250's client part). The feed
  itself (`GET /v1/events`) is unchanged in shape. The slot reason is `fleet_paused` (underscore, the `SlotReason`
  style); the refusal code is `fleet-paused` (hyphen, the `code` style). The mesh-ai analysis §8.24
  spells the slot reason `fleet-paused`; the client part MUST use `fleet_paused`.
- **Older daemons** (before this release) ignore `paused` in the sync reply. They never get a
  headless offer while paused (the hub makes none and refuses their accept), but they **do** start a
  run already queued locally when a session frees up; docs say so. Interactive behaviour is the same
  for old and new daemons.
- **Older CLIs:** `mesh fleet pause` does not exist there; an older `mesh fleet pause …` lists
  machines and pauses nothing. Checked against 0.1.41: `parseArgs` (src/cli/context.ts:55) collects
  the extra words as positional arguments and `machinesCommand` reads none of them.
- **Rolling upgrade (Postgres, several replicas):** an old replica during the upgrade does not check
  the pause; a pause stored during a rolling upgrade is fully enforced once every replica runs this
  release. Docs RECOMMEND finishing the upgrade before pausing.
- **Downgrade:** the migration adds a table; an older hub refuses a database with a newer schema
  (today's rule), so a downgrade restores the pre-upgrade database as for any migration.
- **Solo hubs** carry the same routes; a person who is the Solo hub's admin can pause their own
  machine's pulses.

## Open questions

1. `/healthz` is public and carries `by` and `reason` (the owner-approved design, analysis §8.24).
   A reason MAY name an incident. The spec keeps the field as asked and has the docs warn against
   secrets in it; a reviewer MAY ask the client's owner whether `/healthz` should carry only
   `{ since }` with the details behind a `goals:read` read.
2. Older daemons start runs already queued locally while paused (§Compatibility). Making the hub
   refuse such a start needs a hub round-trip before a queued run starts, which no daemon version
   makes today; this spec accepts the gap and documents it.
3. Queueing this spec in docs/later.md is left to the release that builds it; the request is already
   owner-approved on the client side.
