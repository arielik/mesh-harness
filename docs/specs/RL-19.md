# Spec RL-19: Findings roll-up per preset and repo

## Status
Approved after review round 2 (`reviews/RL-19/r2-approved.md`). Revision 4 (with the implementation)
words the `mesh preset ls` line as `invalid: kind must match …`, like any other invalid preset file,
and makes `presetKindProblem` take the preset text. Revision 3 applies the round-2 suggestions
1–4. Revision 2 answered round 1 (`reviews/RL-19/r1-changes-requested.md`).

Source: a request from a dashboard client for a findings table per audit type and repo (severity
counts and the latest report). Builds on RL-1 (hub-stored artifacts), RL-2 (review records, items,
lineages), RL-4 (dispositions), RL-9 (clean-audit goals), RL-10 (an item's target repo), RL-11 (trial
goals, `/healthz` features) and RL-12 (`GET /v1/health` `findings`). Release 0.1.38.

## Problem

1. **Findings by repo take one call per lineage.** `GET /v1/health` counts findings by severity per
   **pulse**, not per repo, and gives no report. `GET /v1/items?lineage=` has each item's severity
   and target repo, but one lineage at a time; `GET /v1/pulses/:id/runs` lists report ids per run,
   with item counts not split by severity. A dashboard that shows "per audit and repo, open and
   accepted findings by severity, and the latest report" makes one call per lineage plus one per pulse.
2. **The hub cannot say what kind of audit a preset is.** A client maps presets to its own audit
   types by name only, because a preset carries no kind.

## Scope

In:
- `GET /v1/findings/rollup`: one row per `(preset, repo)` over the lineages audited in a window of
  days, with open and accepted item counts by severity, the newest report, the pulse and the kind.
- An optional top-level `kind` in a preset (a slug the hub stores in the snapshot text and never
  interprets).
- A new `/healthz` feature name: `findings-rollup`.
- Two store reads that keep the route to a fixed number of queries (below).

Out:
- Anything about cost: no cost field, ratio or cost per finding in the new route.
- A composite score: the hub returns counts; a client weighs them.
- A `url` for the report: the hub has no person-openable page for an artifact (the web app's routes
  are `#/`, `#/goals`, `#/goal/<id>`, `#/mine`, `#/roster`, none shows artifacts; `GET
  /v1/artifacts/:id` is an authenticated JSON route), and it does not know its own public origin. The
  row gives the artifact id; a client fetches `GET /v1/artifacts/<ref>`.
- Changes to `GET /v1/health` (the roll-up is its own route), CLI commands, events, stored fields
  other than the preset text's own `kind`.
- A team or owner dimension: the client joins repos to its teams.

## Interface contracts

### Common rules

- Rule `member`, service scope `goals:read`, as `GET /v1/health` (RL-12). Not wrapped for a person:
  a service that sends `x-mesh-on-behalf-of` gets 400 `on-behalf-of is not accepted on this route`;
  it reads with its own token.
- The route reads in one store transaction and writes nothing.
- Times are milliseconds since the epoch. `now` is the hub clock at the read.
- An unknown query parameter is ignored.

### Terms

- A **lineage** is `<preset>|<repo>|<agent>` (RL-2). Its **preset** is the text before the first
  `|`, its **lineage repo** the text between the first and the last `|` (`lineageRepo`). Goals
  without a preset have preset `-`.
- An item's **target repo** is its `repo` when set, else its lineage repo (RL-10 `targetRepo`).
- A raising review record (`StoredReview.raising`, RL-2) **counts** when:
  - its `at` is in the window `[now − days × 86 400 000, now]` (both ends included);
  - its goal exists (in any state: a record of a later dropped goal still counts) and is not a
    calibration goal (`calibration`) nor a spot-check goal (`spotCheck`). The steps of those goals
    submit raising records with no items (their presets `calibrate` and `spot-check` have `output:
    review-record` and no `consumes`); they are not audits, and counting them would add a zero row per
    calibrated or checked repo;
  - its goal is not a trial goal, unless `trial=include`.
  Complete and partial records count alike (both are audits that ran).
- A **selected lineage** is the lineage of a counted record.
- **Row key.** An item counts under `(preset of its lineage, its target repo)`. Justification: the
  table is "findings per repo"; RL-10's `repo` exists to say which repo a finding is about, and the
  clean-audit goal and sink of a retargeted item already follow its target repo (RL-10). Counting
  under the lineage repo would show a finding in the repo that was audited instead of the repo that
  must change.
- **Rows.** For each selected lineage `L` with preset `P`: the row `(P, lineageRepo(L))`, and the row
  `(P, R)` for each target repo `R` of an item of `L` in state `open`, `confirmed` or `accepted`. A
  row's **contributing lineages** are the selected lineages that produced it by either rule. So an
  audit that ran and found nothing (or only dismissed or resolved items) still has its row with
  zeros, and a repo that only receives retargeted findings has a row too.
- A row's **home lineages** are its contributing lineages whose lineage repo is the row's repo (the
  audits that ran in that repo); its **source lineages** are its home lineages when it has any, else
  all its contributing lineages (a repo that only receives retargeted findings). `kind`, `pulse`,
  `lastRaisedAt` and `latestReport` come from the source lineages, so the row of an audited repo
  names its own audit and report, not those of an audit of another repo that retargeted an item to it.
- Several agents and lineages of one `(preset, repo)` aggregate into one row: counts add up over all
  items that count under the row (an item belongs to exactly one lineage, so it counts once).

### Types (src/protocol/hub.ts, exported from src/protocol/index.ts)

`HUB_FEATURES` gains `findings-rollup` (the array stays sorted).

`BySeverity` is the existing `{S1, S2, S3, S4}` of whole numbers (`src/protocol/hub.ts`); it becomes
exported (type and schema), unchanged.

**`RollupReport`**: `{ref, at, goal, step, round, title?, pruned?}`

| Field | Meaning |
|---|---|
| `ref` | the artifact id (`a-` + ULID); its content is at `GET /v1/artifacts/<ref>` |
| `at` | the artifact's `createdAt` |
| `goal`, `step`, `round` | the artifact's goal, full step id and round |
| `title` | the artifact's `title`, absent when it has none |
| `pruned` | `true` when the artifact's content was pruned (`prunedAt` set); absent otherwise |

**`RollupRow`**:

| Field | Meaning |
|---|---|
| `preset` | the lineage preset (`-` for goals without a preset) |
| `repo` | the repo (target repo of the items, lineage repo for the audited repo) |
| `kind` | the preset's kind (the request's name for it): the `kind` declared in the preset text (`goal.preset.text`, read with `presetKind`) of the goal of the row's **newest source record** (below); absent when that preset declares none or the goal has no preset |
| `pulse` | `refs.pulse` of the goal of the row's newest source record **whose goal names a pulse that exists and is not deleted**; absent when no source record has one |
| `lineages` | the number of contributing lineages |
| `lastRaisedAt` | the `at` of the row's newest source record |
| `open` | `BySeverity`: the items counting under the row in state `open` or `confirmed` now (as RL-12 `findings.open`) |
| `accepted` | `BySeverity`: the items counting under the row in state `accepted` now (with or without a `link`, as RL-12 `findings.accepted`) |
| `latestReport` | `RollupReport`: the newest stored artifact of kind `report` (by `createdAt`, then `id`) of the steps of the row's source records (any round of those steps, pruned ones included); absent when those steps have none. This is deliberately not RL-12's `runReportOf` rule (highest round first, for one run): across runs and steps the newest upload is the latest report. |

The row's **source records** are the counted records on its source lineages; the **newest** is the
one with the largest `at`, ties broken by the later insertion order of `listReviews`. Items in
states `dismissed`, `deferred` and `resolved` are not counted in any field.

**`FindingsRollup`**: `{window: {since, until, days}, rows: RollupRow[]}`, `until` = `now`, `since` =
`now − days × 86 400 000`. `rows` ordered by `repo`, then `preset` (binary string order).

### `GET /v1/findings/rollup`

| Parameter | Meaning | Invalid → 400 with |
|---|---|---|
| `days` | 1–365, default 30: the window of the counted records. Valid only as 1 to 3 decimal digits (`^\d{1,3}$`) with a value from 1 to 365; an empty `days=` is invalid | `days must be a whole number from 1 to 365` |
| `repo` | only rows whose `repo` equals it (exact) | — |
| `preset` | only rows whose `preset` equals it (exact) | — |
| `trial` | `exclude` (default) or `include` | `trial must be exclude or include` |

- **What `days` windows.** The window chooses **which lineages** are in the table: those with a
  counted raising record in it, i.e. audits that ran in the last `days`. The counts are the **current
  states** of those lineages' items, whatever the time of their last change. A lineage whose newest
  raising record is older than the window is left out, so a retired audit drops off the table instead
  of showing stale counts forever. Counting by item activity instead would leave out an open finding
  that every run repeats without changing its state. The default 30 covers weekly and monthly audits;
  365 covers quarterly ones.
- **What `trial` filters.** Which records count (so which lineages are selected), and therefore
  `lastRaisedAt`, `pulse`, `kind` and `latestReport`. Item states and the `open`/`accepted` counts are
  lineage-level (RL-11, RL-12): a trial run's record folds like any other, so they include what trial
  runs did on a selected lineage's items.
- **Filters** apply to rows after they are built: `repo` and `preset` never change a row's counts.
  `repo` is the row repo, not the pulse's `params.repo` (unlike `GET /v1/health`).
- **Rows come from any goal** with counted raising records, not only pulse goals: a relay started
  with `mesh goal new --preset` or ingested is an audit too. `pulse` tells the two apart.
- **Pulse choice.** When several pulses share a preset and repo, the row names the pulse whose goal
  raised the newest source record (one pulse per row; a client that needs all of them reads
  `GET /v1/pulses`). No pulse → absent.
- **No paging.** The table has at most one row per preset and repo the hub has audited in the
  window: tens to a few hundred rows. No cap; the reply is one page.

### Preset `kind`

- A preset may declare a top-level `kind:` (a string matching `^[a-z][a-z0-9-]{0,39}$`, e.g.
  `code-audit`). It names the kind of routine for a client; the hub stores it only inside the preset
  text and never interprets it. The built-in presets declare none.
- Core (`src/core/presets.ts`, pure):
  - `PRESET_KIND_RE` = `^[a-z][a-z0-9-]{0,39}$`;
  - `presetKindProblem(text)`: for a preset text (none when the YAML does not parse), `kind must match ^[a-z][a-z0-9-]{0,39}$`
    when it has a top-level `kind` that is not such a string, else none;
  - `parsePreset` reads a valid `kind` into `Preset.kind` (optional) and **leaves an invalid one out
    without throwing**: the hub re-parses stored snapshots when a pulse fires (`instantiate(parsePreset(…))`
    in `fireSlot` and in the pulse update checks), and a snapshot stored before this release with an
    invalid `kind` must keep firing;
  - `presetText` writes `kind` when set (after `description`), so the text the CLI sends keeps it;
  - `presetKind(text)`: the YAML parsed, the top-level `kind` when valid, else none; never throws (an
    unparsable text gives none).
- CLI: `findPresetSource` (used by `mesh pulse add`, `mesh pulse update --preset`, `mesh goal new
  --preset` and the relay start, which all send `presetText(parsePreset(…))`) checks the file's text
  with `presetKindProblem` and fails with that text (`.mesh/presets/<name>.yaml: kind must match …`,
  nothing sent; exit 2 for `mesh pulse add` and `mesh pulse update`, which report a usage error, and
  exit 1 for `mesh goal new --preset` and the relay start, whose errors are not usage errors). So a
  person sees a bad kind instead of having it dropped silently. `mesh preset ls`, which parses the
  files itself, lists such a file as `invalid: kind must match …` (as it lists any
  other invalid preset file) instead of hiding it.
- Hub: the same problem (422) for a client that posts its own text, checked only on a preset **sent
  in the request**: pulse create, a pulse update whose body has `preset`, and ingest (`POST
  /v1/goals/from-preset`). A pulse update with only `params` re-checks the stored snapshot through
  `presetChecks` but not its `kind`, so a snapshot stored before this release with an invalid `kind`
  still updates and fires; such a snapshot has no kind in the roll-up.
- It is a preset field, not a pulse param: the kind belongs to the routine, and a param could differ
  per pulse of the same preset.

### Reads (implementation contract)

The route makes a fixed number of queries, never one per lineage, step or goal:
1. `listGoals()` once (trial, calibration, spot-check, `refs.pulse`, preset text).
2. `listPulses({})` once (which pulses exist and are not deleted).
3. `listReviews({raising: true, since})` once: `listReviews` gains `since?: number`
   (`created_at ≥ since`, in SQL; `created_at` is the record's `at`).
4. `listItemsIn(lineages)`: a new store read, the item rows of several lineages
   (`WHERE lineage IN (…)` on the primary key), in chunks of at most 500 lineages per query, ordered by
   `lineage`, then `fp` (binary order on both stores) across chunks.
5. `listArtifacts({steps})`: `listArtifacts` gains `steps?: string[]` (`step IN (…)`, on the
   `artifact_step_round` index), chunked at 500 steps; the report filter (`kind = report`) is applied in
   code (kind is in the JSON value). Metadata only, never content.

`review_record.created_at` has no index (only `(lineage, raising, complete)`), so read 3 scans the
record table once, filtering in SQL and parsing only the window's records; no index is added (that
would be a migration). The guide says the route reads every raising record of the window and is meant
for a page load, not a poll every few seconds.

### Compatibility

No migration (schema 12), no new event, no stored field (the preset `kind` lives in the snapshot text
the hub already stores). A client detects the route by `findings-rollup` in `/healthz` `features`.
A preset with `kind` also works on an older hub, which ignores an unknown top-level key (and has
no roll-up). An older CLI parses the preset file and sends `presetText` of it, which drops `kind`
without a word; only a 0.1.38 CLI sends it. No daemon change.
