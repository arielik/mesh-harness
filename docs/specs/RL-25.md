Source: an external request (mesh-ai row B-251, the per-person delivery of its AI-ops action item
AIOPS-12; mesh-ai `docs/analysis/2026-11-26-ai-ops-usability-analysis.md` §8.12 "Routing to a

"OPTIONAL" in this document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when,
and only when, they appear in all capitals, as shown here.

## Problem

1. **No inbound alert path.** The hub has no route that accepts an alert. Alertmanager, which the
   lab already runs, can deliver a webhook (`webhook_configs`) with a bearer token, but nothing on
   the hub receives it.
2. **Notify is local only.** `desktopNotify` and `terminalNotify` (src/mux/notify.ts) are called by
   the daemon for its own sessions (`maybeNotify`, daemon.ts:1245; offers, daemon.ts:838). The hub
   cannot ask a person's machines to show a notice: the daemon handles only one machine-wide message
   kind, `offer` (daemon.ts:764); any other kind is acked `failed` (`unknown session`,
   hub-link.ts:441).
3. **Alertmanager repeats and resolves.** Alertmanager re-sends a group on every `group_interval`
   change and every `repeat_interval`, may send the same notification from two cluster peers, and
   sends `resolved` when `send_resolved: true`. Without dedup and resolve handling a person would be
   notified many times for one condition and never told it ended.

## Terminology

- **Alert**: one element of the webhook's `alerts` array.
- **Fingerprint**: Alertmanager's `fingerprint` of the alert (a hash of its label set).
- **Episode**: one firing period of one fingerprint for one person, identified by the alert's
  `startsAt`. It ends with a `resolved` alert of the same fingerprint.
- **Notice**: one machine-wide inbox message of kind `alert` to one machine.
- **Reminder**: a second or later firing notice of the same episode.

## Scope

In:
- A service scope `alerts:notify` and the route `POST /v1/alerts/webhook`, which accepts the
  Alertmanager webhook body (version `"4"`).
- Person resolution from the alert label `person` (exact hub user id).
- Per-episode dedup, a fixed reminder interval, and resolve handling with cancellation of notices
  not yet delivered.
- One hub table for episodes (a migration), pruned by the hub tick.
- A machine-wide message kind `alert`, and its handling by the daemon through the existing
  `desktopNotify` / `terminalNotify` path, under the machine's existing `notify` setting.
- One new event type `alert.notified`; `/healthz` feature `alert-notify`; docs.

Out:
- The Alertmanager receiver, route and token secret (`wwt-lab-coordinator`, mesh-ai row B-241).
- The alert rules and the `/metrics` gauges (mesh-ai row B-241).
- Act-for (`X-Mesh-On-Behalf-Of`) on this route; fleet pause; run or session stop; team-machine
  offers.
- Any notice channel other than desktop and terminal (no mail, chat, push service).
- A per-person or per-machine alert opt-out beyond the daemon's existing `notify` setting
  (`mesh setup --notify off`).
- A list of alerts in the TUI, the web dashboard or the CLI.
- Labels other than `person` naming the recipient (no group or team fan-out).

## Requirements

- **REQ-ALERTHOOK-1** `POST /v1/alerts/webhook` MUST be refused unless the caller is a service token
  that carries the scope `alerts:notify`; a member's or an admin's own token MUST be refused with
  `403 service-only`.
- **REQ-ALERTHOOK-2** The route MUST accept the Alertmanager webhook body of version `"4"` and MUST
  answer `200` for every well-formed body, including one whose alerts name no person, an unknown
  person, or (for a firing alert) a person with no recipient machine; such alerts MUST be reported
  in `skipped` and MUST NOT change any state.
- **REQ-ALERTHOOK-3** The person of an alert MUST be the hub user whose id equals the alert's
  `labels.person` exactly (case-sensitive), after `trim()` of the label value as `actingFor` does
  for the act-for header (service.ts:2253); a service account MUST NOT be a person.
- **REQ-ALERTHOOK-4** For a firing alert that starts a new episode, the hub MUST queue exactly one
  notice to each recipient machine (§Recipients) and MUST emit one `alert.notified` event.
- **REQ-ALERTHOOK-5** A firing alert of an episode already notified less than 4 hours ago MUST NOT
  queue any notice or emit any event, whatever the number of times or the replica it arrives on.
- **REQ-ALERTHOOK-6** A firing alert of an episode notified 4 hours ago or more MUST queue one
  reminder notice per recipient machine and MUST first cancel every notice of that episode to that
  machine that is still `pending`.
- **REQ-ALERTHOOK-7** A resolved alert of a firing episode MUST cancel every `pending` notice of that
  episode, MUST queue one resolved notice to each machine that acked any firing or reminder notice
  of that episode as `delivered`, and MUST mark the episode resolved, whether or not the person
  has a recipient machine at that time; a resolved alert with no firing episode MUST change
  nothing.
- **REQ-ALERTHOOK-8** The daemon MUST show an `alert` notice through `desktopNotify` and/or
  `terminalNotify` according to its `notify` setting and MUST ack it; with `notify: off` it MUST
  show nothing and ack it `delivered` with method `off`.
- **REQ-ALERTHOOK-9** Older daemons and older hubs MUST keep working unchanged: an older daemon acks
  an `alert` notice `failed`; an older hub answers `404` on the route.

## Interface contracts

### Scope (src/protocol/hub-api.ts)

`SERVICE_SCOPES` gains `"alerts:notify"`, appended after the last scope present when this item
lands (after `steps:assign`, or after the scopes of RL-22 when RL-22 lands first).

Why a new scope: the route makes notices appear on people's desktops; none of the existing scopes
(`goals:read`, `goals:write`, `live:read`, …) is that reach, and the Alertmanager token needs no
other. The token is minted once by an admin:
`mesh hub token --service alertmanager --scope alerts:notify`.

### Route

```
{ method: "POST", path: "/v1/alerts/webhook", rule: "member", scope: "alerts:notify",
  tag: "admin", body: AlertWebhook, response: AlertWebhookResult,
  summary: "Alertmanager webhook (version 4): notify each alert's person on their machines." }
```

No `onBehalfOf`: a request that sends `X-Mesh-On-Behalf-Of` gets `400 on-behalf-of-not-accepted`
(today's `actingFor` rule). The `member` rule lets a member token past `allowed()`; the service
method refuses any actor that is not a service (role `service` without `member`) with
`403 service-only` before reading the body's alerts (REQ-ALERTHOOK-1). An `Idempotency-Key`, if
sent, is honoured as on every POST; Alertmanager sends none, and dedup (§Episodes) does not depend
on it.

### Body (`AlertWebhook`, src/protocol/hub.ts, zod)

The Alertmanager webhook body; unknown keys are stripped.

```
AlertWebhook = z.object({
  version: z.string(),                          // MUST be "4", else 400 alert-version
  status: z.enum(["firing", "resolved"]),
  receiver: z.string().max(200).optional(),
  groupKey: z.string().max(2000).optional(),
  externalURL: z.string().max(2000).optional(),
  truncatedAlerts: z.number().int().min(0).optional(),
  alerts: z.array(AlertItem).max(1000),
})
AlertItem = z.object({
  status: z.enum(["firing", "resolved"]),
  labels: z.record(z.string(), z.string()),
  annotations: z.record(z.string(), z.string()).default({}),
  startsAt: z.string(),                         // RFC 3339; parse failure → 400 alert-body
  endsAt: z.string().optional(),
  generatorURL: z.string().optional(),
  fingerprint: z.string().min(1).max(64),
})
```

A body that fails the schema → `400 alert-body` with the zod issues as `details`. The per-alert
`status` decides (§Episodes); the top-level `status` is informational.

### Reply (`AlertWebhookResult`)

```
200 {
  received: number,          // alerts in the body
  notified: number,          // new episodes notified
  reminded: number,          // reminders sent
  resolved: number,          // episodes resolved (whether or not a resolved notice was sent)
  suppressed: number,        // repeats within 4 h, resolved alerts with no firing episode
  skipped: { fingerprint: string, reason: "no-person" | "person-unknown" | "no-machine" }[]
}
```

`received = notified + reminded + resolved + suppressed + skipped.length`.

### Recipients

The recipient machines of a person are the machines with `userId = person` and
`lastSeen ≥ now − 14 days`, at the time of the request. Recipients matter for a firing alert
only: a firing alert whose person has none is skipped with `no-machine` and no episode state is
written, so a later repeat is tried again. A resolved alert needs no recipient (§Episodes). Shared machines of
other people and service accounts' machines are never recipients.

### Episodes (dedup and resolve)

Store: one table, one row per `(fingerprint, person)`:

```
alert_episode (fingerprint TEXT NOT NULL, person TEXT NOT NULL, state TEXT NOT NULL,
               starts_at BIGINT NOT NULL, value TEXT NOT NULL, updated_at BIGINT NOT NULL,
               PRIMARY KEY (fingerprint, person))
value = { alertname?, severity?, summary, notifiedAt, resolvedAt?,
          notices: { machine: string, message: number }[] }   // every firing and reminder notice of the episode
```

The whole request runs in one store transaction that holds the hub's serialize lock (as
`goalTx`), so two replicas, or two Alertmanager peers, that receive the same notification decide
from one current row (REQ-ALERTHOOK-5). `notices` holds every firing and reminder notice queued in
the episode (at most one per recipient per 4 hours); a new episode starts it empty. For each alert
with a person (a resolved alert), or with a person and at least one recipient (a firing alert):

| Alert | Row | Effect | Counted as |
|---|---|---|---|
| firing | `state = resolved`, same `starts_at` (a late repeat, e.g. from a second Alertmanager peer) | nothing | `suppressed` |
| firing | none, or `state = resolved` with `starts_at ≠ startsAt`, or `firing` with `starts_at ≠ startsAt` | new episode: row `firing`, `starts_at = startsAt`, `notifiedAt = now`; one firing notice per recipient; cancel any `pending` notice of the row's previous episode | `notified` |
| firing | `firing`, same `starts_at`, `now − notifiedAt < 4 h` | nothing | `suppressed` |
| firing | `firing`, same `starts_at`, `now − notifiedAt ≥ 4 h` | cancel the row's `pending` notices; one reminder notice per recipient, appended to `notices`; `notifiedAt = now` | `reminded` |
| resolved | `firing` (any `starts_at`) | cancel the row's `pending` notices; one resolved notice to each distinct machine that has at least one message of `notices` in state `delivered`, whether or not it is a recipient now; row `resolved`, `resolvedAt = now` | `resolved` |
| resolved | none, or `state = resolved` | nothing | `suppressed` |

The 4-hour reminder interval is a constant (`ALERT_REMIND_MS`). It does not replace Alertmanager's
`repeat_interval`; it bounds what the hub forwards whatever that interval is.

**Cancel** is a new store method `cancelMessage(id, now)`:
`UPDATE message SET state = 'failed', method = 'cancelled', acked_at = ? WHERE id = ? AND state = 'pending'`.
A cancelled notice is no longer in the machine's inbox; no `message.delivered` event is emitted for
it (`cancelled` is a message method only, visible on the message row). Consequence: a machine that was offline for the whole episode shows nothing, and a machine
offline for a long firing episode holds at most one pending notice of it.

**Prune**: the hub tick deletes rows with `state = resolved` and `updated_at < now − 7 days`. A
firing row whose alert never resolves (Alertmanager configured without `send_resolved`) stays until
it resolves; docs require `send_resolved: true`.

### Notice (machine-wide message, kind `alert`)

Queued with the existing `machineMessage(machine, fromUser, kind, text, data)`
(service.ts:686), which wakes the machine's daemon:

- `toSid: ""`, `kind: "alert"`, `fromUser` = the service user id.
- `text`: `MESH ALERT <SEVERITY>: <summary>` for a firing notice and a reminder,
  `MESH ALERT resolved: <summary>` for a resolved notice. `<SEVERITY>` is the upper-cased
  `labels.severity`, omitted with its space when absent. `<summary>` is the first present of
  `annotations.summary`, `annotations.description`, `labels.alertname`, the fingerprint; control
  characters replaced by spaces; at most 200 characters.
- `data`: `{ alert: { fingerprint, status: "firing" | "resolved", reminder: boolean, alertname?,
  severity?, summary, startsAt: <ms>, runbook?: annotations.runbook_url,
  dashboard?: annotations.dashboard, url?: generatorURL } }`. `dashboard` carries the link that
  mesh-ai spec 0124 puts on its rule `MeshAttentionWaitingOnPerson`; values longer than 2000
  characters are dropped.

### Daemon (src/daemon/daemon.ts)

`receive` gains a second machine-wide kind: `m.toSid === "" && m.kind === "alert"` → the daemon
handles it and returns `"handling"`. Every other machine-wide kind except `offer` stays `"unknown"`.

Handling, in order:
1. `notifyChannels(config).any` is false → ack `delivered`, method `off`; nothing shown.
2. The notice's `createdAt` is more than 24 hours old → ack `delivered`, method `stale`; nothing
   shown.
3. Otherwise the notice joins a batch; the batch is shown 2 seconds after its first notice
   arrives, as **one** call of `deps.notify(title, body, target)`:
   - one notice: title `mesh · alert`, body the notice `text` without its `MESH ALERT ` prefix;
   - n > 1 notices: title `mesh · <n> alerts`, body the first notice's text without the prefix,
     then ` (+<n−1> more)`.
   - `target` (for the terminal channel) is the live, non-ended session of this machine of kind
     `interactive` with the latest `lastEventAt` that has a `pid` or a `pane`; none → no target
     (the terminal channel then shows nothing, as `main.ts` already does without a target).
4. `deps.notify` resolves truthy → each notice of the batch is acked `delivered` with the method
   named by the configured channels, `notifyChannels(config)`: `desktop`, `terminal` or `both`.
   `deps.notify` resolves falsy or throws → each is acked `failed` with method `no-channel`. The
   method is the configured channel set, not a per-channel result: `deps.notify` returns one value
   (main.ts returns `sent.some(Boolean)`). Consequence: under `notify: terminal` with no target,
   main.ts shows nothing and returns false, so the notice is acked `failed`/`no-channel`.

The daemon reuses the offer bookkeeping for alert ids: `offersInFlight` holds an alert id from its
arrival until its ack is sent, including while it waits in the 2-second batch; `offersHandled`
records its ack; `offersAwaitingRetry` holds an ack the hub did not take, retried on the next pull.
`forgetOffers` therefore never forgets an alert id that is still batched or unacked, and a re-pull
before the ack reaches the hub does not show a notice twice; `forgetOffersOfOtherHub` clears alert
ids as it does offer ids. While the hub is unreachable, no notice arrives and nothing is shown; there is no local
alert source.

`deps.notify` gains no new argument; `main.ts` is unchanged.

### Events

New type `alert.notified`, one per episode transition that queued at least one notice or resolved
an episode: `user` = the service user id; payload `{ fingerprint, person, status: "firing" |
"resolved", reminder: boolean, alertname?, severity?, startsAt, machines: string[] (the machines
messaged; [] for a resolved episode whose firing notices were all cancelled) }`. Suppressed and
skipped alerts emit nothing. `message.delivered` is emitted for notices as for every message
(the daemon's ack); a cancelled notice emits none. docs/events.md gains the row.

Event consumers that switch on `type` MUST ignore unknown types; mesh-ai's gateway already reads
`GET /v1/events` by known types only.

### Codes

| Status | `code` | `error` | When |
|---|---|---|---|
| 401 | `login-required` | `login required` | no or bad token |
| 403 | `forbidden` | `forbidden` | a service token without `alerts:notify` |
| 403 | `service-only` | new: `only a service token posts alerts` | a member's or admin's own token |
| 400 | `on-behalf-of-not-accepted` | as today | the act-for header is sent |
| 400 | `alert-version` | new: `webhook version <v> is not supported; expected 4` | `version ≠ "4"` |
| 400 | `alert-body` | new: `invalid alert webhook body` (zod issues in `details`) | schema failure, more than 1000 alerts, unparsable `startsAt` |

Alertmanager does not retry a `4xx`; these refusals are configuration errors seen in its log.

### Compatibility

- **Older daemons** (any version before this release): an `alert` notice is a machine-wide message
  of an unknown kind; `receive` returns `"unknown"` and hub-link acks it `failed`
  (`unknown session`). Nothing is shown, nothing breaks; the notice leaves the inbox. A resolved
  notice is then never sent to that machine (its firing notice is not `delivered`). People see
  notices after upgrading their CLI.
- **Older hubs**: the route is `404`; the feature is absent.
- **mesh-ai spec 0124 (row B-241)**: its receiver URL placeholder `<B-251 path>` is
  `/v1/alerts/webhook` (0124 assumed `/v1/alerts/alertmanager` and defers to this spec); its
  `credentials_file` path is the one in the docs example above; its `annotations.dashboard`
  reaches the notice as `data.alert.dashboard`.
- **Members' and existing service tokens**: unchanged; no existing route changes.
- **Downgrade**: a downgraded hub ignores the `alert_episode` table (it opens a newer schema as
  today's rule says) and never calls the route.
- No change to the `offer` handling, to `notify` config values, or to `deps.notify`.
