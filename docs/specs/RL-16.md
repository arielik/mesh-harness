# Spec RL-16: Profile fitting from denials and tool use

## Status
Approved after review round 2 (`reviews/RL-16/r2-approved.md`). Revision 3 applies its suggestions
12–14 (wording). Revision 2 answered round 1 (`reviews/RL-16/r1-changes-requested.md`, B1, B2,
S3–S11).

Source: [harness efficiency and insights](../analysis/2026-11-19-harness-efficiency-and-insights.md),
item I-6 (profile fitting from denials and tool use), with the r2 critique §6 (C-4: a denial can be
the profile doing its job; it is a profile gap only when the same command is denied in most runs;
C-5: no composite score in the hub). Builds on RL-1 (permission profiles, `parseProfile`,
`compileProfile`, `profile.saved`) and RL-11 (run telemetry `toolsUsed` and `denied`, `GET /v1/runs`,
trial goals, `/healthz` features). Release `0.1.33`.

## Problem

1. **A profile is tuned by guesswork.** A headless run's telemetry says which commands were denied
   (`denied`, the first word of a `Bash` command) and which tools it was offered (`tools`) and called
   (`toolsUsed`). To decide "allow `cargo`, drop `CronCreate`" a person pages `GET /v1/runs`, keeps
   the rows of one profile, counts denials per run, diffs offered against used tools, and then
   checks by hand that the rule they want is one a profile may hold at all.
2. **A dashboard cannot show the gap per profile** without repeating that join and the profile
   rules (the built-in denies, the refused rules) in its own code.

## Scope

In:
- `GET /v1/profiles/:name/fit`: a read-only **fit report** of one profile over a window of days:
  the runs per profile hash, the denied tools and command words with how many runs hit them, the
  tools offered but never used, and a proposed change (`allow` rules to add, tools to `deny`), each
  observation either suggested or held with a reason.
- `mesh profile fit <name> [--days N] [--include-trial] [--json]`: prints the report.
- A pure function in `src/core/profile-fit.ts` that builds the report from a profile and its runs
  (the hub calls it; the rules live in one place).
- `/healthz` feature `profile-fit`.

Out:
- Writing the profile. Neither the route nor the CLI saves anything; the person edits the YAML and
  saves it with `mesh profile add` (the change shows up as `profile.saved` with a new hash).
- A before/after comparison beyond the per-hash run and denial counts of `hashes` (I-8).
- Narrower Bash rules than `Bash(<word> *)`: the telemetry keeps only the first word of a denied
  command (RL-11), so the fit cannot know `cargo test` from `cargo publish`. The guide tells the
  person to narrow the rule before saving.
- Paths of denied `Read`/`Edit` calls, other tools' inputs: not in the telemetry.
- A score or a ratio: the report carries counts; thresholds only decide `suggest`.
- Runs that closed no round (as RL-11).
- The web UI.

## Interface contracts

### Terms

- **The profile's runs**: every round (of any step of any goal, any state, moved-away and dropped
  steps included) that has `telemetry` with `telemetry.profile` equal to `:name` (exact, case
  sensitive), whose `finishedAt` is in the window, whose goal exists and that passes `trial`
  (`goal.trial === true` is a trial run). This is the set of `GET /v1/runs?since=<since>&until=<until
  + 1>&trial=<trial>` rows (over all pages) whose `telemetry.profile` is `:name`.
- **The current hash**: the `sha256` `GET /v1/profiles/:name` shows now (for a built-in, the hash
  of its compiled settings).
- **The sample**: the profile's runs whose `telemetry.profileHash` equals the current hash. Only the
  sample is used for `denied`, `unused` and `diff`: a run at an older hash ran under other rules, and
  a denial it met may already be fixed. Runs at other hashes are counted in `hashes` only.
- **Tool runs**: the runs of the sample whose telemetry has both `tools` and `toolsUsed`. `unused`
  is built from them only: a run without `toolsUsed` comes from a daemon older than 0.1.30 or called
  no tool, and says nothing about which tools were used.
- **Compiled rules**: the current snapshot's `settings.permissions.allow` and `.deny` (built-in rules
  first, then the profile's checks, `allow` and `deny`, as `compileProfile` builds them).
- **The profile file**: for a registered profile, `parseProfile(text).file` of its stored text; for a
  built-in, the file `{extends: <name>}`.

### Thresholds (constants, reported in the reply)

`PROFILE_FIT = {minRuns: 5, minShare: 0.5}` (`src/protocol/hub.ts`).
- **Small sample**, per list: `sample.runs < minRuns` for `denied`; for `unused`, `sample.toolRuns <
  minRuns` or the tool's own `offeredRuns < minRuns` (one run that offered a tool is no evidence that
  it is never needed). Nothing is suggested from a small sample; observations are still listed (held
  `few-runs`). The two lists are judged apart: a sample of 5 runs of which 2 are tool runs still gets
  allow suggestions.
- **Frequent**: a denial is frequent when its `runs ≥ ceil(minShare × sample.runs)`, that is
  denied in at least half the runs of the sample (with at least `minRuns` runs, at least 3) (C-4: "denied in most runs" is a profile gap; a rare
  denial is the profile doing its job).

### Rule syntax

- `WORD = ^[A-Za-z0-9_][A-Za-z0-9._+-]*$` (a command word a rule can hold without quoting or glob
  characters) and `TOOL = ^[A-Za-z_][A-Za-z0-9_.-]*$` (a tool name, `mcp__<server>__<tool>`
  included).
- The **allow rule** of a denial: for `tool: "Bash"` with a `command` matching `WORD`:
  `Bash(<command> *)` (the built-ins' prefix form, as `Bash(git log --no-ext-diff *)`); for any other
  tool matching `TOOL`: the tool name alone (`Task`). None otherwise.
- The **drop rule** of an unused tool matching `TOOL`: the tool name alone, added to `deny` (Claude
  Code does not offer a tool that a bare-name deny rule names).
- `RUNS_ANYTHING` (`src/core/profile-fit.ts`): command words that run another command or arbitrary
  code, for which `Bash(<word> *)` would be as wide as `Bash(*)`: `bash`, `sh`, `zsh`, `dash`, `ksh`,
  `fish`, `csh`, `tcsh`, `env`, `sudo`, `su`, `doas`, `xargs`, `eval`, `exec`, `nohup`, `timeout`,
  `nice`, `ionice`, `time`, `watch`, `command`, `builtin`, `source`, `ssh`, `python`, `python3`,
  `node`, `perl`, `ruby`, `php`, `deno`, `bun`, `npx`, `pnpx`, `bunx`, `uvx`, `uv`, `pipx`, `awk`,
  `gawk`, `mawk`, `nawk`, `lua`, `tclsh`, `pwsh`, `busybox`, `setsid`, `stdbuf`, `unbuffer`, `flock`,
  `chroot`, `nsenter`, `strace`, `ltrace`, `gdb`, `parallel`, `script`. The list is best effort; the
  guide says that build tools (`make --eval`, `cargo --config`, `npm run`) also run what the repo or
  the arguments say, so a suggested `Bash(make *)` is a starting point to narrow, not a safe rule.
- A deny rule **covers** an allow rule `R`:
  - `R = Bash(<w> *)`: the deny rule is `Bash`; or it is `Bash(<p>)` and the first word of `<p>`
    (up to its first space or `:`) either equals `<w>` or contains `*` with the part before that `*`
    a prefix of `<w>` (so `Bash(git * --output*)` and `Bash(git push *)` cover `Bash(git *)`,
    `Bash(find *-exec*)` covers `Bash(find *)`, and `Bash(*)`, `Bash(* --x)` and `Bash(c*)` cover
    `Bash(cargo *)`);
  - `R = <tool>`: the deny rule is `<tool>` or starts with `<tool>(`; and for `<tool>` =
    `mcp__<server>__<name>` (`<server>` = the text after `mcp__` up to the next `__`), also
    `mcp__<server>` or `mcp__<server>__*` (a server-wide rule).
- An allow rule **names** a tool `T` by the same test (`T`, `T(…)`, and for an MCP tool its server's
  `mcp__<server>` or `mcp__<server>__*`).

### Building the report (`fitProfile` in `src/core/profile-fit.ts`, pure)

Signature (exported from `src/core/index.ts`):

```ts
interface FitRun { finishedAt: number; telemetry: RunTelemetry }
interface FitInput {
  profile: { name: string; builtIn: boolean; base: ProfileBase; sha256: string; settings: ProfileSettings; text?: string };
  runs: readonly FitRun[];   // the profile's runs (all hashes), already windowed and trial-filtered
  window: { since: number; until: number; days: number };
  trial: "exclude" | "include";
}
function fitProfile(input: FitInput): ProfileFit;
```

The hub fills `profile` from `GET /v1/profiles/:name`'s view (`text` for a registered profile) and
`runs` from the rounds described in *Terms*; the order of `runs` does not change the result.

**Denied.** Over the sample, group the `telemetry.denied` entries by `(tool, command)`:
`runs` = the number of sample runs whose `denied` has the group, `count` = the sum of their
`count`s. Order: `runs` descending, `count` descending, `tool`, then `command` (absent first), in
UTF-16 code-unit order. For each group, in this order, the first matching reason holds it:

| `held` | When |
|---|---|
| `no-command` | `tool` is `Bash` and `command` is absent |
| `not-a-word` | no allow rule can be built (`command` not matching `WORD`, or a non-Bash tool not matching `TOOL`) |
| `runs-anything` | `tool` is `Bash` and `command` is in `RUNS_ANYTHING` |
| `already-allowed` | the rule is already one of the compiled allow rules |
| `denied-by-profile` | a compiled deny rule (a built-in's or the profile's own) covers the rule |
| `few-runs` | small sample (`sample.runs < minRuns`) |
| `rare` | not frequent |
| `refused` | `parseProfile` refuses the profile file with the rules of `diff` so far and this rule added to `allow` (below); `refusal` carries its error text |

A group that no reason holds is **suggested**: `suggest: true`, and its rule is appended to
`diff.allow`.

**Unused.** Over the tool runs: a tool is unused when it is in `tools` of at least one tool run and
in `toolsUsed` of none (a denied call is a call: Claude Code's stream has its `tool_use` block, so
it is in `toolsUsed`). `offeredRuns` = the number of tool runs that offered it. Order: `offeredRuns`
descending, then `tool`. Reasons, first match:

| `held` | When |
|---|---|
| `mesh-tool` | the tool starts with `mcp__mesh__`, or is `Skill` (mesh's own tools, and the tool that loads the mesh skill, are never dropped) |
| `allowed` | a compiled allow rule names the tool (the profile meant it to be available) |
| `already-denied` | a compiled deny rule is the tool's name (defensive: Claude Code should not offer such a tool, but `tools` is what the run reported) |
| `not-a-word` | the tool does not match `TOOL` |
| `few-runs` | `sample.toolRuns < minRuns` or `offeredRuns < minRuns` |
| `refused` | `parseProfile` refuses the profile file with `diff` so far and this tool added to `deny` |

A tool no reason holds is suggested, and its name is appended to `diff.deny`.

**Validation (`refused`).** The candidate file is the profile file with `allow` = its `allow` (or
`[]`) followed by `diff.allow` so far and the candidate, and `deny` = its `deny` followed by
`diff.deny` so far (and the candidate, for an unused tool), serialized with `yaml`'s `stringify` and
passed to `parseProfile` (the check `POST /v1/profiles` applies: the refused rules such as any
`mcp__mesh__` rule other than the four mesh tool rules, `Bash`, `Bash(*)`, `Bash(:*)`, any rule
containing `git push`, and the limits of 100 rules of at most 300 characters). Denied groups are
checked first, in their order, then unused tools, in theirs; so the whole `diff` together passes
`parseProfile`. When the stored text of a registered profile no longer parses (a later release
tightened a rule), every candidate that reaches this check is held `refused` with that error.

### Types (`src/protocol/hub.ts`, exported from `src/protocol/index.ts`)

`HUB_FEATURES` gains `profile-fit` (sorted).

`FitHeld` = `"no-command" | "not-a-word" | "runs-anything" | "already-allowed" | "denied-by-profile" |
"few-runs" | "rare" | "refused" | "mesh-tool" | "allowed" | "already-denied"`.

**`ProfileFit`** (the reply):

| Field | Meaning |
|---|---|
| `profile` | the profile name |
| `builtIn` | `true` for a built-in profile |
| `base` | the profile's base (`read-only`, `read-only+checks`, `propose-via-branch`) |
| `sha256` | the current hash |
| `window` | `{since, until, days}`: `until` = the hub clock at the read, `since` = `until − days × 86 400 000`; both ends included; milliseconds since the epoch |
| `trial` | `exclude` or `include`, as applied |
| `thresholds` | `PROFILE_FIT` |
| `hashes` | `ProfileFitHash[]`: the current hash first (always, also with 0 runs), then every other hash that has a run among the profile's runs, by `lastAt` descending, then `sha256` |
| `sample` | `{runs, toolRuns}`: the sizes of the sample and of its tool runs |
| `denied` | `FitDenied[]`, at most 200, in the order above |
| `unused` | `FitUnused[]`, at most 200, in the order above |
| `truncated` | `{denied, unused}`: how many entries were cut from each list; absent when none was (suggestions are made before the cut, so `diff` may hold a rule whose entry was cut) |
| `diff` | `{allow: string[], deny: string[]}`: the suggested rules in suggestion order (`[]` when none) |

**`ProfileFitHash`**: `{sha256, current, runs, toolRuns, deniedRuns, denials, firstAt?, lastAt?}`:
over the profile's runs with that `profileHash`: `runs` their number, `toolRuns` those with `tools`
and `toolsUsed`, `deniedRuns` those with `permissionDenials.count > 0`, `denials` the sum of
`permissionDenials.count`, `firstAt` and `lastAt` the oldest and newest `finishedAt` (absent with 0
runs). `current` is `true` for the current hash.

**`FitDenied`**: `{tool, command?, runs, count, rule?, suggest, held?, refusal?}`: `rule` the
allow rule when one can be built (absent with `no-command` and `not-a-word`); `held` absent exactly
when `suggest` is `true`; `refusal` present only with `held: "refused"`.

**`FitUnused`**: `{tool, offeredRuns, suggest, held?, refusal?}`: same rules for `held` and
`refusal`.

### `GET /v1/profiles/:name/fit`

| Parameter | Meaning | Invalid → 400 with |
|---|---|---|
| `days` | 1–90, default 14; parsed as `GET /v1/health` does (`^\d{1,2}$`, so `014`, `1.0` and ` 5` are refused) | `days must be a whole number from 1 to 90` |
| `trial` | `exclude` (default) or `include` | `trial must be exclude or include` |

`trial=only` is not offered: a fit proposes a change to the profile production runs use, and trial
runs alone are the tuning runs of an agent, not of its profile; `include` adds them while tuning.
The parameters are checked before the profile is read: a bad parameter gives 400 also for an unknown
profile.

- Rule `member`, service scope `goals:read` (there is no `profiles:read` scope; `GET
  /v1/profiles/:name` uses `goals:read`). Not wrapped for a person: a service that sends
  `x-mesh-on-behalf-of` gets 400 `on-behalf-of is not accepted on this route`.
- Unknown profile → 404 `no profile <name>` (as `GET /v1/profiles/:name`).
- An unknown query parameter is ignored. No paging: the reply is an aggregate, its lists capped.
- One store transaction, nothing written, no event. Reads the profile and steps with
  `listSteps({updatedSince: since})` (as `GET /v1/runs`), and the goals of the matching rounds.

### CLI: `mesh profile fit <name> [--days N] [--include-trial] [--json]`

- Calls `GET /v1/profiles/<encodeURIComponent(name)>/fit?days=<N>` (`days` only when given;
  `--days` is a value option, also `--days=N`) with `&trial=include` when
  `--include-trial` is given. A hub refusal → its text on stderr, exit 1 (as the other `mesh
  profile` subcommands). No name → usage on stderr, exit 2. `mesh profile --help` lists the
  subcommand.
- `--json`: the reply, `JSON.stringify(reply, null, 2)`, exit 0.
- Otherwise text, exit 0, lines in this order (`<h12>` = the first 12 characters of a hash):
  1. `Profile <name> (sha256 <h12>): <runs> runs in the last <days> days at this hash, <toolRuns> with tool data.`
     followed by ` Trial runs included.` with `trial: include`.
  2. When other hashes have runs: `Other hashes: <h12> <runs> runs, <h12> <runs> runs.` (in `hashes`
     order, `1 run` for one).
  3. When `sample.runs < thresholds.minRuns`: `Fewer than <minRuns> runs: no allow rule is suggested from a small sample.`
     When `sample.toolRuns < thresholds.minRuns` (also when `sample.runs` is): `Fewer than <minRuns>
     runs with tool data: no tool is suggested for dropping.` (Both lines when both hold.)
  4. `Denied:` then one line per `denied` entry: `  <label>  <runs>/<sample.runs> runs, <count> denials  <verdict>`,
     where `<label>` is `<tool> <command>` or `<tool>` and `<verdict>` is `→ allow <rule>` when
     suggested, else `held: <held>` (with `: <refusal>` for `refused`); `Denied: none.` when empty.
  5. `Offered, never used: no runs with tool data.` when `sample.toolRuns` is 0 (this wins);
     else `Offered, never used: none.` when `unused` is empty; else `Offered, never used:` then
     `  <tool>  <offeredRuns>/<sample.toolRuns> runs  <verdict>` (`→ drop (deny <tool>)` or
     `held: …`).
  6. When `truncated` is present: `(<n> more denied and <m> more unused entries not shown)`.
  7. `Proposed change:` then `  allow: + <rule>` per `diff.allow` rule and `  deny:  + <tool>` per
     `diff.deny` tool; `Proposed change: none.` when both are empty.
  8. When the diff is not empty: for a registered profile `Nothing was saved. Narrow the Bash rules if
     you can, add them to the profile's YAML and run: mesh profile add <name> --file <profile.yaml>`;
     for a built-in `Nothing was saved. <name> is built in: register a profile with "extends: <name>"
     and these rules (mesh profile add <new name> --file <profile.yaml>) and use it in the step.`

### Compatibility

No migration (schema 11), no new event, no stored field. A client detects the route by
`profile-fit` in `/healthz` `features`. Runs reported by daemons older than 0.1.30 have no `denied`
or `toolsUsed`; they count in `sample.runs` and `hashes` but add no denied group and are not tool
runs.
