# Spec RL-17: Change markers and before/after

## Status
Approved after review round 1 (`reviews/RL-17/r1-approved.md`). Revision 2 applies its suggestions
S1–S14 (wording, notes and AC detail; no contract change).

Source: [harness efficiency and insights](../analysis/2026-11-19-harness-efficiency-and-insights.md),
item I-8 (change markers and before/after), placed in §6.5 order 7. Builds on RL-1 (headless runs,
telemetry, the profile registry), RL-3 (pulses, preset snapshots), RL-5 (roster, catalog pushes,
pins), RL-6 (agent statistics), RL-11 (`GET /v1/runs`, run rows, trial goals) and RL-12 (the run
aggregate of `GET /v1/health`). Release 0.1.34.

## Problem

1. **Nobody can tell when something changed.** Every run carries the hash of its agent definition
   (`telemetry.agentHash`) and of its permission profile (`telemetry.profileHash`); every goal made
   from a preset keeps the preset text. When a person edits an agent, saves a profile or updates a
   pulse's preset, the new hash simply starts to appear. To find "what changed, when, and who did
   it", a client pages the whole event log, reads every step's rounds and every goal, and joins them.
2. **"Did that change help?" needs a spreadsheet.** `GET /v1/agents/:key/stats` lists one agent's
   numbers per hash over a window, but it has no end time, no repo filter, and no run-level waste
   parts (`GET /v1/runs`). Comparing the runs before an edit with the runs after it means paging the
   run rows and summing them by hand.

## Scope

In:
- `GET /v1/changes`: a timeline of agent, profile and preset hashes, one entry per `(kind, key,
  hash)`, with when it first appeared, the hash before it for the same key, and the event that
  introduced it. Derived from stored rows and events; paged.
- `GET /v1/agents/:key/compare?from=&to=`: the run aggregate (RL-12 `runs`) and the item counts
  (RL-6 statistics) of two hashes of one agent key, side by side, with the run counts.
- Two event payload fields so that a pulse change can be tied to the hashes it introduced:
  `pulse.created` gains `agents`; `pulse.updated` gains `preset`, `sha256` and `agents` when the
  update re-snapshots the preset.
- Two names in `/healthz` `features`: `agent-compare` and `changes`.

Out:
- A composite score, a significance test, a "better/worse" verdict or any ratio: the hub reports
  sums and counts; a client divides and judges.
- The harness hash of interactive sessions (`session.provenance`): sessions are not runs; a later
  release may add a `harness` kind.
- Repo agent files a machine reports (`agents.reported`): their reports carry no hashes in events and
  keep no first-report time; a repo agent's hash appears in the timeline through its first run.
- A CLI command for either route.
- Any migration, stored field or new event type.
- Goal pins (`goal.agents`) as a sighting source: a replan can change them after the goal was
  created, so their time is not known. A pin is sighted by its pulse event, its catalog push or
  its first run.
- A hash that changes and later changes back: the timeline lists each hash once, at its first
  sighting, so the change back is not shown (a later release may list every switch).

## Interface contracts

### Common rules

- Rule `member`, service scope `goals:read`, as `GET /v1/agents/:key/stats` and `GET /v1/runs`. Not
  wrapped for a person: a service that sends `x-mesh-on-behalf-of` gets 400 `on-behalf-of is not
  accepted on this route` (`docs/guide/auth.md`).
- Each route reads in one store transaction and writes nothing.
- Times are milliseconds since the epoch.
- `since`, `until`: as `GET /v1/runs` (RL-11): a whole number of milliseconds (`^\d{1,15}$`) or an
  ISO-8601 time matching the RL-11 pattern; invalid → 400 `since must be milliseconds since the epoch
  or an ISO time` (same for `until`); both given and `since ≥ until` → 400 `since must be before
  until`. **No default:** an absent `since` means from the beginning, an absent `until` means no end.
- `trial`: `exclude` (default) or `include`; another value → 400 `trial must be exclude or include`.
  With `exclude`, what belongs to a trial goal (`goal.trial === true`, RL-11) is left out.
- An unknown query parameter is ignored.

### Hashes and keys

Three kinds:

| `kind` | `key` | `hash` |
|---|---|---|
| `agent` | the agent key as runs carry it (`telemetry.agentKey`, `<repo name>/<agent name>`; a catalog definition's canonical key `CatalogDefView.key`, whose repo name is the last segment of the source id, so two sources whose ids end alike share keys, as they already do in runs and statistics) | the definition's hash (`telemetry.agentHash`, `AgentDef.hash`, `CatalogDefView.hash`) |
| `profile` | the profile name (`telemetry.profile`, `profile.saved` `name`) | the profile's sha256 (`telemetry.profileHash`, `profile.saved` `sha256`) |
| `preset` | the preset name (`PresetSnapshot.name`, `goal.preset.name`) | the SHA-256 hex of the preset text in UTF-8 (`PresetSnapshot.sha256`; for a goal, computed from `goal.preset.text`) |

### Sightings

A **sighting** is one place where the hub recorded a `(kind, key, hash)` at a time. There are three
sources:

1. **Run** (`agent`, `profile`): every round, of any step of any goal (any state, also moved-away and
   dropped steps), that has `telemetry` — the rows of `GET /v1/runs`. At `round.finishedAt`. It
   sights `(agent, telemetry.agentKey, telemetry.agentHash)` when both are present, and always
   `(profile, telemetry.profile, telemetry.profileHash)`. Its repo is `step.repo`; it is a trial
   sighting when its goal is a trial goal. Refs: `goal`, `step`, `round`, `runId`.
2. **Goal** (`preset`): every goal with a `preset`. At `goal.createdAt`. It sights `(preset,
   goal.preset.name, sha256(goal.preset.text))`. Its repo is `goal.primaryRepo`; trial as above.
   Refs: `goal`. (A goal's preset never changes after creation. Calibration goals carry the built-in
   `calibrate` preset, so it appears as a preset entry too.)
3. **Event** (registration, no repo, never trial). At `event.at`:
   - `profile.saved`: `(profile, payload.name, payload.sha256)`.
   - `pulse.created`: `(preset, payload.preset, payload.sha256)`; and, from 0.1.34, for each entry
     `{key, hash}` of `payload.agents`, `(agent, key, hash)`.
   - `pulse.updated` from 0.1.34, when the payload has `sha256`: `(preset, payload.preset,
     payload.sha256)` and each `(agent, key, hash)` of `payload.agents`.
   - `catalog.pushed`: for each stored catalog definition `D` of the pushed source
     (`D.source = payload.repo`) whose stored `commits` contain `payload.commit`, `(agent, D.key,
     D.hash)`. Only the earliest such event per definition counts (a later push of the same
     definition is not a new sighting by rule *first seen*). A definition keeps at most its 50
     newest commits (RL-5), so after 50 pushes of one unchanged definition its first push may no
     longer be identifiable; then the earliest push still listed is its sighting.
   Refs: `pulse` (`payload.pulse`) for the two pulse events.

Events older than the hub's event retention (`hub.events_pruned`) are gone; their sightings are
gone with them. Runs and goals are never pruned, so every hash a run or goal used stays in the
timeline.

Which sightings count: with `repo` given, only run and goal sightings whose repo equals it (event
sightings have no repo and are left out); with `trial=exclude`, no trial sighting.

### `GET /v1/changes`

| Parameter | Meaning | Invalid → 400 with |
|---|---|---|
| `kind` | `agent`, `profile` or `preset`: only entries of that kind | `kind must be agent, profile or preset` |
| `agent`, `profile`, `preset` | key filters: when any is given, an entry passes when its kind's filter is given and equals its key (so `agent=x&profile=y` lists x's agent entries and y's profile entries) | — |
| `repo` | count only the sightings of that repo (above) | — |
| `since`, `until` | entries whose `firstSeen` is in `[since, until)` | as in *Common rules* |
| `trial` | `exclude` (default) or `include` | `trial must be exclude or include` |
| `limit` | 1–500, default 100 | `limit must be a whole number from 1 to 500` |
| `cursor` | the `next` of a previous page | `cursor is not valid` |

Entries: one per `(kind, key, hash)` that has at least one counted sighting. Its **first sighting**
is the counted sighting with the smallest time; ties are broken by source (event, then goal, then
run), then event `seq`, goal id, or `(step, round)` ascending as binary strings and numbers.

**`ChangeEntry`**:

| Field | Meaning |
|---|---|
| `kind`, `key`, `hash` | as above |
| `firstSeen` | the first sighting's time |
| `previous` | the `hash` of the next entry of the same `(kind, key)` in entry order (below), that is the one first seen just before this one (on a tie in `firstSeen`, the one ordered after it); absent for the first hash of a key. Computed over every entry the counted sightings give (before `since`, `until`, `limit` and `cursor` apply), so the oldest entry in a window still names its predecessor. |
| `source` | `event`, `goal` or `run`: the first sighting's source |
| `goal`, `step`, `round`, `runId` | the first sighting's refs (run: all four; goal: `goal`); absent for an event sighting |
| `pulse` | the event's `payload.pulse` for a `pulse.created` / `pulse.updated` sighting; absent otherwise |
| `event` | `{id, seq, type, at, user?}` of the **introducing event**: for an event sighting, that event; for a goal sighting, the `goal.created` event of the goal; for a run sighting, the `run.finished` event of the step whose `payload.runId` equals the run's `runId` (the first one when several). `user` is the event's user when it has one. Absent when that event no longer exists (retention) or never existed (a round from before `run.finished` carried the id). |
| `sightings` | the number of counted sightings of the entry (runs, goals and events together) over all time: `since`, `until`, `limit` and `cursor` do not change it. A catalog definition is sighted once however often it is pushed unchanged; each `profile.saved` of the same text is a sighting. |

Order: `firstSeen` descending, then `kind`, `key`, `hash` ascending as binary strings (newest change
first). The reply is `{changes: ChangeEntry[], next?: string}`; `next` is present when more entries
match, and passing it as `cursor` (with the same filters) returns the entries after the last one
returned. `next` is opaque and encodes the sort key of the last entry returned.

What the event `user` means per type: `profile.saved` the person who saved it (or for whom a service
did), `pulse.created`/`pulse.updated` the person who saved the pulse, `catalog.pushed` the user of
the pushing machine, `goal.created` the goal's owner, `run.finished` the user of the reporting
machine.

### `GET /v1/agents/:key/compare`

`:key` is the agent key, `/` percent-encoded, validated as `GET /v1/agents/:key/stats` validates it
(400 `an agent key is <repo>/<name>`).

| Parameter | Meaning | Invalid → 400 with |
|---|---|---|
| `from`, `to` | the two agent hashes, required (absent or empty → `from is required` / `to is required`), each 1–200 characters, compared exactly with `telemetry.agentHash` and the raising record's `decider.hash` (no prefix match) | `from is required` / `to is required`; `from must be at most 200 characters` (same for `to`) |
| `since`, `until` | the window (as in *Common rules*; no default) | as in *Common rules* |
| `repo` | only runs, records and dispositions of steps of that repo (below) | — |
| `trial` | `exclude` (default) or `include` | `trial must be exclude or include` |

`from` and `to` may be equal (both sides then show the same numbers). A hash with nothing in the
window gives a side of zeros.

Without `since`, the route reads every run of the key (all time); the guide says so.

Reply **`AgentCompare`**: `{key, since?, until?, repo?, trial, from: HashSide, to: HashSide}` with
`since`, `until`, `repo` as given (times as milliseconds), `trial` the value used.

**`HashSide`**: `{hash, runs, items, firstAt?, lastAt?}`:

- `runs` (schema `CompareRuns`: the fields of the RL-12 health `runs` plus `costRuns`) — the run
  aggregate over this hash's runs: the rounds with telemetry whose
  `telemetry.agentKey` = `key` and `telemetry.agentHash` = `hash`, `finishedAt` in `[since, until)`,
  step `repo` = `repo` when given, trial as `trial`. These are exactly the rows of `GET
  /v1/runs?agent=<key>&since=<since>&until=<until>&repo=<repo>&trial=<trial>` (all pages) whose
  `telemetry.agentHash` = `hash` (`GET /v1/runs` defaults `since` to 30 days; the equality holds for
  a given `since`). Fields, each from those rows' `RunRow`:
  - `count`: the number of runs;
  - `durationMs`, `turns`: the sums of `telemetry.durationMs` and `telemetry.turns` (milliseconds;
    turns);
  - `costUsd`: the sum of `telemetry.costUsdEstimate` over the runs that have one, unrounded and
    added in run order (as RL-12 health); absent when none has;
  - `costRuns`: the number of runs that have `costUsdEstimate` (so a mean is computable);
  - `failed`, `overBudget`, `allDismissed`: the number of runs whose `waste` part of that name is
    `true`; `denials`: the sum of `waste.denials`.
- `items` — the **RL-6 statistics** of this hash with the same window, repo and trial:
  `{raised, new, regressions, carried, accepted, dismissedByAgents, dismissedByPeople}`, each defined
  as the field of that name in `GET /v1/agents/:key/stats` (`AgentHashStats`), with the window's
  lower bound `since` (0 when absent) instead of `now − days`, an upper bound `until` (exclusive,
  none when absent) on the same times (a record's `at`, a disposition's `at`), and with `repo`: only
  records whose `step`'s repo, and dispositions whose recording `step`'s repo (the step that recorded
  the disposition, not the step that raised the item), equals it. `until` and `repo` filter only what
  is counted; which agent raised an item (the newest raising record of the goal and lineage, RL-6)
  is decided over all records as in the stats route. With
  `since` = `now − days × 86 400 000`, no `until` and no `repo`, each equals the stats route's field
  for the hash under the same `trial` (or 0 when the stats route leaves the hash out).
- `firstAt`, `lastAt`: the smallest and greatest `finishedAt` of the side's runs; absent when
  `runs.count` is 0.

Small samples stay visible: the hub never hides a side with few runs; `runs.count` is always
present.

Note: the stats route's own `runs` and `failures` count only rounds of steps whose policy is
`headless`; `GET /v1/runs` (and so `HashSide.runs`) counts every round with telemetry. The daemon
reports telemetry only for headless runs, so the two agree unless a replan changed a step's mode
after its run.

### Event payloads (src/hub/service.ts)

- `pulse.created` gains `agents`: `[{key, hash}]`, one per entry of `pulse.agents` (the roster pins,
  RL-5) as `{key: def.key, hash: def.hash}`, sorted by `key` then `hash` and de-duplicated; absent
  when the pulse pins none.
- `pulse.updated` gains, when the update re-snapshots (its body has `preset` or `params`): `preset`
  (the preset name), `sha256` (the preset's) and `agents` as above (absent when none). An update
  without `preset` or `params` carries none of them.
- No other event changes; no new event type.

### Types (src/protocol/hub.ts, exported from src/protocol/index.ts)

`ChangeEntry`, `ChangesPage`, `HashSide`, `AgentCompare` as above. `HUB_FEATURES` gains
`agent-compare` and `changes` (sorted: `["agent-compare", "changes", "commits", "health",
"pulse-runs", "runs", "trial"]`).

### Reads (implementation contract)

- `/v1/changes` reads every step (`listSteps({})`) and every goal once, the events of the four
  registration types with one SQL query filtered on `type` (a new store read `eventsOfTypes(types)`;
  the event table has no index on `type`, so this is a scan of the event table in the database, not
  in the hub), the catalog definitions once (`listCatalogDefs({})`), and for the entries of the
  returned page only, the introducing `goal.created` / `run.finished` event through the indexed
  `goal` / `step` columns (a new store read `eventsOf({goal|step, type})`).
- `/v1/agents/:key/compare` reads as the stats route (`calibrationScan`) plus the run rows of the
  key's runs. `computeAgentStats` (src/core/calibration.ts) gains optional `until` and a step filter;
  the stats route passes neither, so its numbers are unchanged.
- The guide says both are meant for a page load, not a poll every few seconds.

### Compatibility

No migration (schema 11), no stored field, no new event type. Pulse events written before 0.1.34
carry no `agents` and `pulse.updated` no `sha256`: a preset changed by such an update is sighted by
the first goal made from it, and a pin by its catalog push or its first run. A client detects the
routes by `changes` and `agent-compare` in `/healthz` `features`.
