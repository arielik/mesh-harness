# Spec RL-13: The commit of each round

## Status
Approved after review round 3 (`reviews/RL-13/r3-approved.md`). Revision 4 applies its suggestions
R1–R3 (wording). Revision 3 answered round 2 (N1–N7), revision 2 round 1 (B1, B2, S1–S10).

Source: [harness efficiency and insights](../analysis/2026-11-19-harness-efficiency-and-insights.md),
item I-17 (links to the outside), promoted to MUST in §6 ("the head commit per round"). Builds on M4
(rounds, `mesh_done`), RL-1 (headless runs, the `run` report, close-as-fail), RL-11 (`GET /v1/runs`)
and RL-12 (run cards). Release v0.1.32.

## Problem

1. **Work and CI cannot be joined exactly.** A step's round records `branch` and `mr` when the agent
   passes them, never the commit. A dashboard that wants "the pipelines of the commits this step
   made" or "the CI minutes of this goal" can only guess by repo and time window, and a branch moves.
   CI systems and code-analysis servers key everything by commit.
2. **A headless run's result has no commit either.** The daemon knows the commit the run started
   from (`baseCommit`) and, for `propose-via-branch`, the commit it pushed, but neither reaches the
   hub. A run row (`GET /v1/runs`) has `repo` and `branch` only.

## Scope

In:
- `commit` on a **round**: the head commit of the step's work when the round closed.
- The daemon fills it in `mesh_done` from the session's checkout; an agent may pass it.
- A headless run's `finished` report carries the commit the run ended on, which replaces the
  round's commit.
- `commit` in `GET /v1/runs` rows, in run card stages (`GET /v1/pulses/:id/runs`), in the `step.done`,
  `step.failed` and `run.finished` event payloads, in the step record (`.mesh/goals/.../steps/*.md`
  rounds) and in the ledger schema of a step record's round.
- `commits` in `/healthz` `features`.

Out:
- `refs` on steps (the other half of I-17): a later release.
- Any CI, merge request or analysis-server data in the hub: the hub records the commit; clients
  join on it.
- A `commit` filter on `GET /v1/runs` (clients join locally; the page is small).
- Whether the working tree had uncommitted changes when the round closed.
- A commit on `Step` itself: the commit belongs to a round (a later round may have none).

## Interface contracts

### The commit value

`Commit` (src/protocol/goal.ts): a full object name in lowercase hex, 40 characters (SHA-1) or 64
(SHA-256): `/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/`. An abbreviated or upper-case name is refused where an
agent can pass one (below); the daemon only ever sends `git rev-parse` output, which is full and
lower case.

### Round

`Round` gains `commit?: Commit`.

### `POST /v1/steps/:id/done` (`DoneRequest`)

Gains `commit?: Commit`. The hub stores it on the round it creates. A body with a malformed
`commit` is a 400 (zod), like any other invalid field. `closeAsFail` bodies may carry one too (the
daemon does not send one; see the `run` report).

### `POST /v1/steps/:id/run` (`RunReport`)

Gains `commit?: Commit`, allowed with `state: "finished"` and a `round` only (a `started` report or
one without `round` that carries `commit` is a 400 `commit needs a finished report with a round`,
checked before the step lookup, the state check and the 403).
It sets the round's `commit`, replacing one the round had. Like `branch`, it is stored only when the
reporter may report on that round (the round's user or an admin, the existing 403 otherwise). A
finished report that carries only `commit` (no `telemetry`, no `branch`) still updates the round.

### `mesh_done` (MCP tool, src/protocol/tools.ts)

Gains `commit: z.string().optional()`, described as "the commit your work ends on, only when it is
not in this session's checkout (mesh reads it from the checkout otherwise)".

The daemon (src/daemon/tools.ts) resolves the commit to send, in this order:
1. `args.commit` when given: trimmed and lower-cased; when it is not a `Commit`, the tool fails with
   `commit must be a full commit id (40 or 64 hex characters)` and nothing is sent.
2. In a headless run's session (`host.runOf(sid)` is set, or `host.isRunSession(sid)`; decided
   before the POST, without `isHeadlessCall`'s step-mode test, since an interactive session may hold
   a step whose policy says headless), no
   commit: the run's `finished` report sets it (below), so a commit only the run's worktree had
   never reaches the hub or the `step.done` event.
3. Otherwise, from the repo root of the session's current cwd (`findRepoRoot(s.cwd)`). That
   checkout is used only when it is the step's repo: the repo of the checkout root actually read,
   by the daemon's `repoForCwd(root)` (a new optional `ToolHost.repoForCwd`, wired to the daemon's
   `deps.repoForCwd`), must match the step's repo by `repoMatches`. The session's `s.repo` (set
   once, when the session started) is not used: a session that started in the step's repo and
   moved into another repo records nothing. The step's repo is read from the step cache; on a miss
   (a step bound by the autopilot chain, an offer or the TUI before any `mesh_context`) the daemon
   reads the step from the hub first (a read only; it fills the cache). Any failure of that read
   (offline, an error status, a timeout) means no commit; `done` is still sent as before. An unknown checkout repo, an unknown step repo, a mismatch, no checkout, or no
   `host.git` means no commit. Then:
   - with `branch` given: `branch` is used as given (no `origin/` or `refs/heads/` is stripped).
     It must pass `git check-ref-format --branch <branch>` (revision syntax such as `~2` or `^`
     fails it; a name it accepts that is not a plain branch, such as `@{-1}` or `origin/x`, finds
     no ref below and so gives no commit); then `git rev-parse
     --verify -q refs/heads/<branch>^{commit}`, else `refs/remotes/origin/<branch>^{commit}`; the
     first that answers. An invalid name or a branch neither ref knows means no commit;
   - without `branch`: `git rev-parse --verify -q HEAD^{commit}` (an unborn `HEAD`, a repository
     without commits, answers nothing: no commit).
   A git failure (not a repository, unknown branch, timeout) sends no commit; it never fails the
   tool.

The body sent to the hub (online or queued while offline) carries `commit` when one was resolved;
an offline `mesh_done` puts it on the round of the locally written step record too.

The result text of an accepted `mesh_done` is unchanged.

### Headless runs (src/daemon/runs.ts)

The `finished` report of a run that closed a round (`round` set) carries the run's **result
commit**, decided once, after the push step (`pushDone`) and before the report:
- the push step pushed a branch (`propose-via-branch`, push succeeded): the head `push()` read
  before pushing (`git rev-parse HEAD`), which is now the pushed branch's head;
- otherwise, `baseCommit` (the commit the worktree was made from, which exists in the checkout).
  This covers a run that made no commits, a profile that does not push, and a push that failed:
  a commit only the detached, soon removed worktree had is never reported.
- no `baseCommit` (it was not read at start) and nothing pushed: no commit.
- a run whose push was done by a 0.1.31 daemon (end record without the pushed commit) and is
  finished by a 0.1.32 daemon after an upgrade: `baseCommit`. Accepted for the upgrade window.

`push()` returns the commit it pushed (the worktree head it read before pushing), and that value is
the result commit; the worktree head is not read a second time. The result commit is saved in the
run's end record (`RunEnd`, beside `branch`) before the report is
sent, so a retried report (hub offline, daemon restarted) sends the same value. It replaces the
round's commit (a run session's `mesh_done` sends none, so normally there is none to replace). A
close-as-fail run gets its commit the same way (pushed head when a `propose-via-branch` run
committed and the push succeeded, else `baseCommit`). A run whose done was
refused (no round) sends no report with a round, so no commit.

### Hub reads

- `RunRow` (`GET /v1/runs`) gains `commit?: Commit`: the round's commit.
- `StageCard` (`GET /v1/pulses/:id/runs`) gains `commit?: Commit`: the commit of the step's newest
  round, when that round has one.
- `GET /v1/goals/:id` and every route that returns steps return rounds with `commit` (no change
  beyond the schema).

### Events

- `step.done` and `step.failed` (from `POST .../done`): payload gains `commit` when the round has
  one. Other events about the step (`step.parked`, gate decisions) do not repeat it; the round
  holds it.
- `run.finished`: payload gains `commit` when the report carried one.

docs/events.md lists the field on these three.

### Step record (src/core/trail.ts) and ledger

Each round of a step record gains `commit: <hex>` when the round has one. `LedgerStep`'s round
schema (src/protocol/ledger.ts) gains `commit: Commit.optional()` (the same pattern); `pnpm schemas`
regenerates the generated schema files (the ledger JSON schema and the OpenAPI document).

### `mesh show`

A step line shows the first 9 characters of its newest round's commit, after the `mr`, when that
round has one; a step claimed again for a fix cycle keeps showing the previous round's commit until
its next round closes.

### `/healthz`

`HUB_FEATURES` = `["commits", "health", "pulse-runs", "runs", "trial"]`.

### Docs

- docs/guide/concepts.md: the commit in the round description (where rounds, `branch` and `mr` are described)
  and in `## Runs` and `## Pulse health` (stage `commit`), with one sentence on joining CI by commit.
- The mesh skill (src/protocol/skill.ts → skills/mesh/SKILL.md): `mesh_done` step 4 says mesh records
  the commit from the checkout of the step's repo; when the work is on a branch, pass `branch` (mesh
  reads that branch's head); pass `commit` only when the work is in a checkout mesh cannot see.
- docs/guide/operations.md: `## Upgrading to 0.1.32` (no migration, daemons should be upgraded to send commits;
  an older daemon's rounds have none), and `commits` in Probes.
- docs/events.md as above; docs/plan/implementation-plan.md: the `mesh_done` and `/run` rows mention `commit`.

### Compatibility

All fields are optional. Old rounds and rounds from 0.1.31 daemons have no `commit`. A 0.1.32 daemon
talking to a 0.1.31 hub: the hub's `DoneRequest` and `RunReport` are not strict objects (zod strips
unknown keys), so the commit is dropped and nothing fails. No migration (schema 11).

## Acceptance criteria

- **AC-01** `mesh_done` without `commit` or `branch` in a git checkout of the step's repo sends
  `HEAD`'s full id, also for a step bound without a cached context (autopilot chain); the round,
  the `step.done` event and `GET /v1/goals/:id` have it.
- **AC-02** With `branch` given, the daemon sends that branch's local head, else `origin/<branch>`,
  else no commit; a branch name with revision syntax (`main~1`) sends no commit; outside a git
  checkout, in a repository without commits, in a checkout of another repo than the step's, or after
  the session's cwd moved from the step's repo into another repo, no commit and the tool still
  succeeds.
- **AC-03** An explicit `commit` wins over the checkout and is lower-cased; an abbreviated or non-hex
  value fails the tool and sends nothing; the hub refuses a malformed `commit` with 400 on `done` and
  `run`.
- **AC-04** An offline `mesh_done` queues the commit and the local step record's round has it; the
  replay stores it on the hub.
- **AC-05** A headless run's own `mesh_done` sends no commit. Its `finished` report carries the
  result commit: the base commit for a run without commits (done or close-as-fail) and for a
  non-pushing profile that committed; the pushed commit for a `propose-via-branch` run that
  committed and pushed; the base commit when that push failed; the round and `run.finished` have
  it; a retried report sends the same value.
- **AC-06** `POST .../run` with `commit` on a `started` report or without `round` is a 400; by a
  user other than the round's (not admin) a 403; a finished report with only `commit` updates the
  round.
- **AC-07** `GET /v1/runs` rows and run card stages carry the commit; absent when the round has
  none.
- **AC-08** The step record round has `commit`; the ledger round schema refuses a malformed
  `commit`; the generated ledger JSON schema and the OpenAPI document (`DoneRequest`, `RunReport`,
  `RunRow`, `StageCard`) contain `commit`.
- **AC-09** `mesh show` prints the short commit.
- **AC-10** `/healthz` features include `commits`; docs, skill, schemas and version 0.1.32.
