# Spec RL-21: A service assigns a step for a person

## Status
Approved after review round 2 (`reviews/RL-21/r2-approved.md`). Revision 3 applies its suggestions
N1–N5 and the client's feature name `step-assign-for`. Revision 2 answered round 1 (B1, S1–S8).

Source: an external request (a dashboard lets a team member start a ready step of an existing goal
on one of their own registered machines, or in one of their own idle sessions there). It builds on
MM-3 (offers, assign targets, accept policies), MM-4 (suggest), RL-1 (headless offers, profiles),
RL-3 (a goal's pinned profiles) and the act-for pattern of v0.1.29 (`X-Mesh-On-Behalf-Of` on the
pulse write routes, `POST /v1/profiles` and `GET /v1/fleet`, docs/guide/auth.md). Release 0.1.40.
Owner constraint: nothing tied to costs (no budget or `usd` field is added anywhere).

## Problem

1. **A service cannot assign for a person.** `POST /v1/steps/:id/assign` and
   `GET /v1/steps/:id/suggest` are `member` routes without a service scope (src/hub/app.ts:480-481),
   so `allowed()` (src/core/roles.ts:53) refuses a service token with `403 forbidden` before
   `actingFor` (src/hub/service.ts:2135) runs. A dashboard that holds a service token cannot start
   a step on a person's machine even when that person asks it to.
2. **A non-headless step cannot be launched headless.** `offerStep` attaches the profile snapshot
   only when `step.policy.mode === "headless"` (service.ts:688), so a person who wants a fresh
   `claude -p` run of an interactive step has no way to ask for one.
3. **Refusals are text only.** The hub answers `{ error: <message>, details? }`
   (app.ts:546). A client that must tell "machine not yours" from "step not ready" parses
   messages, which change.

## Scope

In:
- A new service scope `steps:assign`. With it, a service token may call
  `POST /v1/steps/:id/assign` and `GET /v1/steps/:id/suggest`, **only** acting for a person
  (`X-Mesh-On-Behalf-Of` is required on both).
- Rights rules for an act-for assign (§Rights): the target machine and, for a session target, the
  live session must be the person's own.
- `mode: "headless"` and `profile` in the step assign body (any caller), with the headless guard,
  the goal's pinned profiles and an own-machine rule.
- Attribution: `via` on the offer, in `step.offered`, in `GET /v1/offers` and in the offer message.
- A stable `code` on every refusal of these two routes and of `actingFor`, added beside the
  unchanged `error` text.
- The assign reply gains `message` (the offer message id) for outcome tracking (HX5, §Outcome).
- `/healthz` feature `step-assign-for`.

Out:
- Act-for on any other route: `POST /v1/goals/:id/assign`, `GET /v1/goals/:id/suggest`,
  accept, decline, withdraw, claim. They keep refusing a `steps:assign` service with `403`.
- A launch-outcome object or route (HX5 is answered by existing state and events, §Outcome).
- A per-goal membership check (the hub has none; any member may assign today).
- CLI and MCP flags for `mode`/`profile` (`mesh assign`, `mesh_assign`): the hub accepts them from
  any caller, the CLI gains no flag in this item.
- A fresh *interactive* launch target, rate limits, budgets of any kind.
- A migration: offers live in the step's JSON value (schema stays 12).

## Interface contracts

### Scope `steps:assign` (src/protocol/hub-api.ts)

`SERVICE_SCOPES` gains `"steps:assign"` (appended after `profiles:write`). Routes:

| Route | rule | scope | act-for | header required for a service |
|---|---|---|---|---|
| `POST /v1/steps/:id/assign` | member | `steps:assign` | yes | yes (write) |
| `GET /v1/steps/:id/suggest` | member | `steps:assign` | yes | **yes** (new: a read that requires the header) |

Why a new scope and not `goals:write`: `goals:write` today lets a service create goals **owned by
the service account** (auth.md), a write that touches no person's machine. An assign starts work on
a person's machine under that person's name, and the existing scopes are one per kind of write
(`pulses:write`, `profiles:write`). Folding it into `goals:write` would silently grant every
existing goal-creating service token (example tokens in auth.md carry `goals:write`) the power to
start sessions on people's machines. A new scope is least privilege, is granted only by minting a
new token, and matches the pattern. `suggest` uses the same scope because its only act-for purpose
is choosing an assign target; a service that may not assign has no need to rank a person's machines.
The cost of this choice: an existing service token must be re-minted with `steps:assign` (an owner
step, `mesh hub token --service <name> --scope …,steps:assign`); that is deliberate.

`HubRoute.onBehalfOf` keeps its meaning; both `HubRoute` (src/protocol/hub-api.ts) and the app's
`Route` type (src/hub/app.ts) gain `onBehalfOfRequired?: true` (suggest only). The OpenAPI
generator documents `X-Mesh-On-Behalf-Of` on both routes and says it is required for a service.
`app.ts` passes `write: route.method === "POST" || route.onBehalfOfRequired === true` to
`actingFor`, so a `steps:assign` service calling suggest without the header gets
`400 on-behalf-of-required` (it never runs as the service account, so `team=1` can never list the
team's machines to it).

### Act-for (unchanged mechanism, `actingFor`)

As v0.1.29: a service token (role `service` without `member`) with the route's scope sends
`X-Mesh-On-Behalf-Of: <user id>`. The hub looks the id up **exactly** (`store.getUser`, a
case-sensitive `=` on SQLite and Postgres; no trimming beyond the existing `trim()`, no nickname,
no `@`). A missing user or a service account is refused `403 user-unknown`. The request then runs
as `{ userId: <person>, roles: ["member"], via: <service user id> }` with **no** `machineId`:
never the person's admin or approver role. Idempotency keys are per `<service>><person>` (app.ts,
unchanged).

### `POST /v1/steps/:id/assign` body (`StepAssignRequest`, src/protocol/hub.ts)

`StepAssignRequest = AssignRequest.extend({ mode: z.literal("headless").optional(), profile: ProfileName.optional() })`.
`AssignRequest` (also the body of `POST /v1/goals/:id/assign`) is unchanged, so goal assign keeps
stripping `mode`/`profile`. Fields: `to` (as today), `sid`, `stick`, `note` (as today), `mode`,
`profile` (new).

### Rights (act-for, `actor.via` set)

Checked in `assignStep` in this order, each refusal with its code (§Codes):

1. Step: unknown → `step-unknown`; gate → `step-gate`; not `ready` → `step-not-ready`; debrief →
   `step-debrief`; open offer → `step-offered` (today's order, today's messages).
2. Fields the service may not send for a person: `sid` (the offering session; the service has
   none) and `stick: true` (a standing target for every later ready step of the goal) →
   `400 on-behalf-of-option`. `note` is allowed.
3. Target resolution (`resolveTarget`, unchanged parsing of `<machine>`, `<machine>/<session>`,
   `<user>/<nickname>`, `<user>/<nickname>/<session>`), **with the machine ownership check made
   immediately after the machine is found and before any session lookup**: a machine whose
   `userId !== person` → `403 machine-not-yours`, whatever the session part says. No machine →
   `404 machine-unknown`.
4. Session: looked up only on the person's own machine among live sessions (`findSessionOn`); none
   → `404 session-unknown`; several → `409 session-ambiguous`; found but `hs.userId !== person` →
   `403 session-not-yours`.
5. Mode and profile (§Headless override), then the headless guard.

The rule is "resolve with today's resolver, then compare ids": `machine.userId === person` and
`session.userId === person` on the **resolved rows**. Every way a name can mean something else
(a bare nickname equal to another machine's id, `<other>/<nick>`, a 3-part form of another user,
a different case, a session sid prefix) either resolves to a row of another person, which is
refused, or resolves to nothing, which is a 404. No path offers to a row whose owner is not the
person. Acting for an admin grants nothing more: the actor has only `member` and assign has no
role-based branch.

For suggest under act-for: `team=1` → `400 on-behalf-of-option`; `any=1` is allowed. Candidates are
the person's machines only (`listMachines({userId})`) and the sessions passed to `suggest()` are
filtered to `userId === person`. `auto` is computed with `byUser = person` and no `byMachine` —
the verdict an act-for assign would get. Step checks as today (`step-unknown`, `step-gate`,
`step-not-ready`); a debrief or already-offered step is not refused by suggest (unchanged).

### Headless override (any caller)

Let `declared = step.policy?.mode === "headless"`. With the new body fields:

| Body | Step not headless | Step headless |
|---|---|---|
| neither field | interactive offer (today) | headless offer with `policy.profile ?? read-only` (today) |
| `mode: "headless"`, no `profile` | `400 profile-required` | as "neither" |
| `mode: "headless"`, `profile: P` | headless offer with `P` | as "`profile: P`" |
| `profile: P`, no `mode` | `400 profile-needs-headless` | `P` must equal `policy.profile` when the step declares one, else `409 profile-mismatch`; with no declared profile, `P` is used |

Further, when `mode` or `profile` is present:
- a session target → `400 headless-session-target` (a headless offer is never bound to a session;
  the daemon takes the `claude -p` branch, daemon.ts:852);
- `stick: true` → `400 headless-stick` (a stick stores only the target, so later offers would not
  carry the override);
- the target machine must be the caller's own (`machine.userId === actor.userId`) →
  else `403 machine-not-yours`. Choosing the permission surface of a run is the machine owner's
  choice; another person's machine keeps receiving only what the step declares.

Under act-for the service, not the machine owner, names the profile. So, when the goal pins no
profiles and the step declares none, an act-for `profile` must be a built-in or a registered
profile whose `createdBy` is the person; any other registered profile → `403 profile-not-yours`.
(A pinned goal admits only its snapshot; a declared profile admits only itself.) What this still
allows, stated in auth.md: a `steps:assign` service may choose a built-in profile (including
`propose-via-branch`, which edits, commits and pushes) or a profile registered for the person,
also one a `profiles:write` service registered for them; with the person's `self` accept rule such
an offer runs unattended. That is the reach the admin grants by minting both scopes, the same as
pulse act-for.

The headless guard (`headlessGuard`, service.ts:877) then runs with the effective profile name
(a new optional argument; `assignGoal`, `emitReady` and the pulse path keep calling it without one
and keep today's declared-only behaviour):
machine not headless-capable → `409 headless-unsupported`; the goal pins profiles (`goal.profiles`,
RL-3) and the name is not a key → `409 headless-profile-not-pinned`; no pin and the name is neither
a built-in nor a registered profile → `409 headless-profile-unknown`. Messages are today's. The
snapshot is the goal's pinned one when the goal pins, else the resolved profile.

`offerStep` attaches the headless offer data (`mode: "headless"`, `profile` snapshot,
`budget: effectiveBudget(step.policy)`, `deadline`, `agent` and roster data as RL-1) whenever the
offer is headless (declared or overridden). `effectiveBudget` of a step without a budget is the
default turns and minutes; no `usd`.

`StepOffer` gains `mode?: "headless"` (set on every headless offer, declared or overridden) and
`via?: string`.

**A headless offer is never accepted into a session.** `POST /v1/steps/:id/accept` with a `sid`, and
the accept branch of `POST /v1/steps/:id/claim` (a claim of a step offered to the caller's machine),
answer `409 offer-headless` (`<step> is offered to run headless; the machine's daemon starts it,
or withdraw it first (mesh withdraw <step>)`) when `offer.mode === "headless"` or
`step.policy.mode === "headless"` (the second covers offers made before the upgrade, which have no
`offer.mode`); the step stays offered. A headless run accepts without a `sid`
(runs.ts:518) and binds its session by a later claim of the step it already holds, so it is
unaffected. Today only the daemon refuses this, and only for declared headless steps
(daemon.ts:997, tools.ts:385); the hub check covers overridden offers and older daemons.

**Run-held.** A step is *run-held* when `step.policy.mode === "headless"` (today), or when its
offer is `accepted` with `mode: "headless"` **and** its holder session (`holderSid`) has
`kind: "print"` (the kind a headless run's session has). Narrowing by the holder session's kind
keeps an interactive hold after a fail, resume, plain claim or paused re-claim (which keep the
accepted offer, core/claims.ts:19-31, service.ts:2983/3076) interactive. Where the hub decides by
mode:
- the tick does not pause a run-held step when its holder session ends (service.ts:7034);
- `deciderOf` (service.ts:1323) gives a run-held step an agent decider (the run's agent key, else
  `<repo>/<step>` as for a declared headless step without an agent); it reads the holder session, so
  it becomes async.

Known gap, accepted: a run bound only through the daemon's fallback bind from a tool call
(daemon.ts:1120) keeps that session's kind (not `print`), so such an overridden run is not
run-held (the tick may pause it after `pauseGraceMs`; its review gets a person decider). The normal
start path registers the run session as `print`; no daemon change in this item.

Left on the declared mode, deliberately (no daemon change in this item): the run brief's
Grep/Glob hint (daemon tools.ts:151), the `mode` of run cards and efficiency rows
(service.ts:7348, core/efficiency.ts:84) and calibration counts (core/calibration.ts:244). An
overridden run therefore shows `mode: "interactive"` there and is not counted for calibration;
docs say so.

### Attribution

- `step.offer.by` = the person; `step.offer.via` = the service user id (absent otherwise);
  no `bySid`, no `byMachine` on an act-for offer. A `self` or `user:<person>` accept rule of the
  target therefore applies as if the person assigned; a `machine:<x>` rule never matches.
- `step.offered` event: `user` = the person; payload gains `via` (act-for only), and `mode:
  "headless"` and `profile` (name) on headless offers.
- The offer message to the machine: `fromUser` and `data.by` = the person; `data.via` added; the
  text keeps its prefix (`MESH: @<person> offers step <id> "<title>" (repo …`, parsed by the daemon,
  daemon.ts:834) and gains ` (via <service>)` at its end, so a reader can tell the service's `note`
  from the person's words.
- `OfferView` (`GET /v1/offers`) gains `via?`.
- Later events of the offer (`step.accepted`, `step.declined`, `step.offer_expired`,
  `run.started`) are made by the target machine, unchanged.

### Reply

`AssignResult` = `{ step: Step; auto: boolean; message?: number }`. `message` is the id of the
offer message sent to the target machine (always set by a 0.1.40 hub; `offerStep` returns the
`addMessage` row id). Status 200 as today.

### Outcome (HX5)

The hub cannot know the outcome synchronously: the daemon handles the offer after its next pull.
No new object. The outcome is read from existing state:

| Outcome | Where |
|---|---|
| listed (waits for the owner) | `message.delivered` with `payload.id = message`, `method: "listed"`; `step.offer.state` stays `offered`. For a **headless** offer nothing the owner can do starts it (a headless offer runs only when auto-accepted): it waits until declined, withdrawn or expired |
| accepted into a session | `step.accepted`; `step.offer.state = "accepted"`; method `accepted` |
| launched (interactive) | method `launched` |
| headless run started / queued | method `headless` / `queued`; `run.started` when it starts |
| declined | `step.declined`; `offer.state = "declined"`; method `declined` |
| expired / withdrawn | `step.offer_expired` / `step.offer_withdrawn`; `offer.state` |
| failed (the daemon could not handle it) | `message.delivered` with `state: "failed"`, `method` = the reason; the offer stays `offered` until it expires |

`GET /v1/steps/:id` gives `offer.state` but needs `goals:read` on the token (a `steps:assign`-only
token lacks it); `GET /v1/events` (service role) gives the events. `message.delivered` carries no
step id: the `message` of the reply is the only join key. docs/guide/auth.md states this table.

### Codes (HX4)

`HubError` gains an optional `code: string` (constructor `(status, message, details?, code?)`).
The error body becomes `{ error, code?, details? }`: `error` text is **unchanged** for every
existing refusal, `code` is added. Codes are lower-case kebab words, stable across releases.

| Status | `code` | `error` (existing text unless new) | Where |
|---|---|---|---|
| 401 | `login-required` | `login required` | route rule, every route |
| 403 | `forbidden` | `forbidden` | route rule (e.g. a service without the scope), every route |
| 400 | `on-behalf-of-required` | as today | actingFor |
| 400 | `on-behalf-of-not-accepted` | as today | actingFor |
| 403 | `on-behalf-of-not-service` | as today | actingFor |
| 403 | `user-unknown` | `unknown user "<id>"` | actingFor |
| 400 | `on-behalf-of-option` | new: `<field> is not accepted when a service acts for a person` | assign (`sid`, `stick`), suggest (`team`) |
| 404 | `step-unknown` | `no step <id>` | assign, suggest |
| 409 | `step-gate` | as today | assign, suggest |
| 409 | `step-not-ready` | as today | assign, suggest |
| 409 | `step-debrief` | as today | assign |
| 409 | `step-offered` | as today | assign |
| 404 | `machine-unknown` | `no machine <to>` | assign |
| 404 | `session-unknown` | as today | assign |
| 409 | `session-ambiguous` | as today | assign |
| 403 | `machine-not-yours` | new: `machine not yours: <to>` | assign (act-for, or `mode`/`profile`) |
| 403 | `session-not-yours` | new: `session not yours: <to>` | assign (act-for) |
| 400 | `profile-required` | new | assign |
| 400 | `profile-needs-headless` | new | assign |
| 400 | `headless-session-target` | new | assign |
| 409 | `profile-mismatch` | new | assign |
| 403 | `profile-not-yours` | new | assign (act-for) |
| 400 | `headless-stick` | new | assign |
| 409 | `offer-headless` | new | accept (with `sid`), claim (accept branch) |
| 409 | `headless-unsupported` | as today | assign |
| 409 | `headless-profile-unknown` | as today | assign |
| 409 | `headless-profile-not-pinned` | as today | assign |

Codes appear only where listed (the accept and claim routes gain only `offer-headless`); other refusals keep `{ error }`. The `step-unknown`,
`machine-unknown` and `session-*` codes are set at the call sites of `assignStep`/`suggestStep`
(the shared helpers gain an optional code argument), so the other routes' bodies are unchanged.
The OpenAPI error component (if any) gains `code`; a client that reads only `error` is unaffected.

### Compatibility

- Additive fields (`code`, `via`, `mode`, `message`); no `error` text of an existing refusal
  changes. An older hub: service refused `403 forbidden`, body fields dropped; the feature tells.
- A downgraded hub reading an offer with `mode`/`via` strips them (zod object); an accepted
  overridden headless step would then be paused by the tick if its run session ended, as before.
- Daemons: no change. A daemon of 0.1.15+ already runs any offer whose data has `mode: headless`.
- `offer-headless` is an intended change for declared headless steps too: a `mesh_claim` from a
  session on the target machine, or a claim without a sid from that machine's token, used to bind an
  offered declared headless step into that session; it is now refused (the daemon already refused
  `mesh_accept` and the local accept). An offerer whose own machine is the target gets
  `offer-headless` on claim instead of a withdraw.
- No migration (schema 12).

## Acceptance criteria

Tests in `test/step-assign-for.test.ts` (AC-14 in `test/step-assign-for-run.test.ts`) (World or pulse-kit; a person `ann` with machines `ann-box`
(nickname `box`, headless-capable, accept `self`) and `ann-two`; a person `bob` with machine
`bob-box` (nickname `box`, accept `self,user:ann`); an admin `root` with a machine; services
`svc` (`goals:read,steps:assign`) and `writer` (`goals:read,goals:write,live:read,pulses:write,profiles:write`)).

- **AC-01** Scope: `writer` (no `steps:assign`) gets `403` `code: "forbidden"` on assign and on
  suggest, with and without the header; a member's own token needs no scope (assign 200).
- **AC-02** Header required: `svc` without the header gets `400 on-behalf-of-required` on assign
  **and** on suggest (also with `team=1`); a member's own token sending the header gets
  `403 on-behalf-of-not-service`.
- **AC-03** Unknown person: header `nobody`, `Ann` (case), `" "` (one space, sent as is; the hub
  trims it to empty), `svc` (a service account) → `403 user-unknown`; no offer, no event.
- **AC-04** Own machine: act-for `ann` assign `to: "box"` → 200; `step.offer.by = "ann"`,
  `via = "svc"`, no `bySid`/`byMachine`; `auto = true` (ann's `self` rule); `step.offered` has
  `user: "ann"`, `payload.via: "svc"`; the inbox message has `data.by = "ann"`, `data.via = "svc"`;
  `GET /v1/offers` as ann shows `via`; the reply has `message` equal to that message's id.
- **AC-05** Other person's machine, by every name form, with bob's machine shared (`share: all`)
  so ann's own token could see its sessions: `to` = bob's machine id, `bob/box`,
  `bob/box/<bob session sid>`, `<bob machine id>/<bob session sid>`, `bob/box/no-such-session` and
  `<bob machine id>/no-such-session` → each `403 machine-not-yours` (never 404: the machine is
  checked before the session; bob's `user:ann` rule notwithstanding); `Bob/box` → `404
  machine-unknown`; no offer, no event.
- **AC-06** Own idle session: act-for `ann` `to: "box/<ann session name>"` and the 3-part
  `ann/box/<sid prefix>` → 200 with `offer.to.sid`; a session on bob's machine named through ann's
  machine is not found (`404 session-unknown`); a session record on ann's machine owned by another
  user (inserted in the store) → `403 session-not-yours`; an ended session → `404 session-unknown`.
- **AC-07** Admin: act-for `root` to bob's machine → `403 machine-not-yours` (a member assign by
  root's own token to bob's machine is 200 today: act-for grants less); act-for `root` to root's
  machine → 200 and `offer.by = "root"`.
- **AC-08** Step refusals with codes (act-for and own token alike): a gate `step-gate`, a non-ready
  step `step-not-ready`, a debrief step `step-debrief`, an offered step `step-offered`, an unknown
  step `step-unknown`; `error` texts equal today's.
- **AC-09** Options: act-for with `sid` or `stick: true` → `400 on-behalf-of-option`; suggest act-for
  `team=1` → `400 on-behalf-of-option`.
- **AC-10** Suggest act-for: returns only ann's machines (none of bob's or root's, also with
  `any=1`), sessions only ann's, `auto` computed for `byUser: ann` without a machine; the same
  call by ann's own token with `team=1` lists bob's machine (unchanged).
- **AC-11** Headless override: an interactive step, act-for `ann`, `{to: "box", mode: "headless",
  profile: "read-only"}` → the message data has `mode: "headless"`, the `read-only` snapshot, the
  default budget (no `usd`), a `deadline`; `offer.mode = "headless"`, `offer.profile.name =
  "read-only"`; `step.offered` payload has `mode` and `profile`. Without the fields the offer data
  has no `mode` (RL-1 AC-20 unchanged).
- **AC-12** Override refusals: `mode` without `profile` on an interactive step → `profile-required`;
  `profile` without `mode` on an interactive step → `profile-needs-headless`; `mode` with a session
  target → `headless-session-target`; `profile` ≠ a headless step's declared profile →
  `profile-mismatch`; a machine without headless capability → `headless-unsupported`; an unknown
  profile → `headless-profile-unknown`; a goal with `profiles` pinned (made from a preset) and a
  profile outside it → `headless-profile-not-pinned`; a profile inside it → 200 with the pinned
  snapshot's `sha256`.
- **AC-13** Own-machine rule for the override: ann's own token assigning bob's machine with
  `mode`/`profile` → `403 machine-not-yours`; without them → 200 (today).
- **AC-14** Overridden headless run end-to-end (relay-kit, fake claude): the target daemon accepts
  and runs `claude -p` under the profile; the step's holder is the run's own session (kind
  `print`); `run.started` carries the profile. (The tick on a run-held step whose run session ended
  is AC-19, at the hub with synced sessions.)
- **AC-15** No act-for elsewhere: `svc` with the header on `POST /v1/goals/:id/assign`,
  `GET /v1/goals/:id/suggest`, `POST /v1/steps/:id/accept`, `/decline`, `/withdraw`, `/claim` →
  `403 forbidden`.
- **AC-16** Idempotency: the same `Idempotency-Key` replays the first reply for (svc, ann) and makes
  no second offer; the same key for (svc, bob) is not replayed.
- **AC-18** Headless offers are not accepted into sessions: an overridden headless offer that is
  not auto (target accept unset) accepted with a `sid` → `409 offer-headless`, and a claim from a
  session on the target machine → `409 offer-headless`; the same for a declared headless step's
  offer whose stored offer has no `mode` (an offer from before the upgrade); the step stays
  offered; the machine's accept without `sid` succeeds.
- **AC-19** Run-held is narrow: an overridden step whose run failed, then resumed and claimed from
  an interactive session (kind `interactive`) is paused by the tick when that session ends, and a
  review record it submits has a person decider; an overridden step held by its run session (kind
  `print`) is not paused when that session ends and its record has an agent decider. (Two steps:
  a step closes `done` once its round has a record, so the failing one submits none first.)
- **AC-20** Profile choice under act-for: act-for with a registered profile created by bob → `403
  profile-not-yours`; created by ann → 200; a built-in → 200. ann's own token with `stick: true` and
  `mode` → `400 headless-stick`; act-for with `stick: true` and `mode` → `400 on-behalf-of-option`
  (the act-for option check comes first).
- **AC-21** Suggest round trip: act-for suggest's first suggestion's `to`, passed as `to` of an
  act-for assign, offers to the same machine id.
- **AC-22** The offer message text starts as today and ends with ` (via svc)` under act-for; it has
  no `via` text otherwise.
- **AC-17** Codes are additive: an existing refusal (e.g. pulse `machine not yours`) keeps its text;
  `/healthz` features include `step-assign-for`; the OpenAPI document lists `steps:assign` on both routes
  and `mode`, `profile` in the assign body; docs mention scope, codes and feature.

## Open questions

1. A **declared** headless step assigned to a session target keeps today's behaviour (the session is
   ignored by the daemon); only an explicit `mode` is refused with a session target. Changing the
   declared case would change existing person behaviour.
2. A `self` accept rule now also auto-accepts offers a service makes for the person (by = the
   person). A later opt-in rule (e.g. `via:<service>`) could separate them; not in this item. The
   docs say so.
